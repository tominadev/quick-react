# 变更留痕与撤回需求开发文档

状态：已实施（2026-09-04）。留痕、撤回、保留期清理与后台页面均已落地；仍未做的见 §14。

前置需求：[数据可见性与代用户操作](data-visibility-and-delegated-access.md)。

## 1. 背景

现有的审计只有两个字段：`created_duid` 与 `updated_duid` 记录"谁动过这一行"，但不记录**动了什么**。一行数据被改成什么样、原来是什么、谁在什么时候改的，事后无从查证；改错了也没有回退手段，只能靠人回忆原值手工改回去。

公共数据层已经拦截了全部写入（`server/database/sql.mts` 的 `insert`、`update`、`softDelete`、`restore`、`delete`），归属与审计字段都在那里统一填充。变更留痕挂在同一个位置，业务代码不感知。

## 2. 目标

- 受管表上**人做的每一次修改**都留下记录：动了哪张表哪一行、哪些字段、从什么变成什么、谁在什么时候做的。
- 每一条变更都能**撤回**，把数据还原到变更前的状态。
- 记录同时充当操作日志与审计凭据：既能给运维排查用，也能在事后追责时作为证据。
- 不引入新的凭证泄露面，不拖垮高频写入路径。

## 3. 受管范围

### 3.0 只审计 `update`

审计的对象是**人对已有数据做的修改**，而在公共层里这恰好就是一个动作：`update`。

`softDelete` 与 `restore` 都是 `updateManaged(table, { deleted_at: ... })`，SQL 层面就是 UPDATE，**挂一个钩子同时覆盖修改、删除与恢复**。

**`insert` 不审计。** 新增没有"变更前"可留，而行本身就是"新增了什么"的完整记录——`created_at` 与 `created_duid` 已经记下谁在什么时候创建了它。为新增再存一份快照是把同一份事实抄两遍。它也是量最大的一类写入（建会话、存短信、签发令牌），排除它去掉了审计表最主要的增长来源。

**物理 `delete` 不审计。** 本项目里人做的删除就是软删除：`sql.mts` 中 `delete` 的注释写明"仅供清理任务和明确的不可恢复操作使用"，AGENTS.md 也要求业务表统一软删除并提供回收站。现有 13 处物理删除调用中，12 处是会话与协议清理，属机器行为。

剩下 3 处是后台人工删除：`global_telegram_bots`、`global_cloud_object_storage_bindings`、`global_cloud_object_storage_binding_purposes`。它们的表都有 `deleted_at` 列，按项目约定本就应改用 `softDelete`；改过之后审计自然覆盖，无需为物理删除单开一条路径。在改动之前，这三处是已知的审计盲区。

**`upsert` 的改写分支也审计。** 配置就是这么写的（`base_configs` 的 `upsert`），不覆盖它等于把最该留证据的一类变更漏掉。不需要分支判断：审计按插入值去找原行，新插入时读不到原行、自然不产生记录，与"insert 不审计"是同一个结果。只有一个前提——冲突键的值必须全部推得出来（归属列没写进 INSERT 时按数据库默认值推），推不出来就整体不审计，宁可没有记录也不要一条指错行的记录。

只审计修改带来的简化：**钩子只有一个**，不需要整行快照（只记变化的列），表白名单也从必需降为可选——字段排除规则加上"逐列比对无变化就不记"已经把噪音挡住了。

范围由**三层**共同界定，三层都是白名单——审计要记的是人做的修改，凡是要靠"排除"才能挡住的，都会失败在敞开的一侧。

1. **有主体**：`subjectRoles !== null`。没有主体就不是人做的。
2. **表白名单**：哪些表的变更值得留证据。
3. **列白名单**：那张表里哪些列是人填的。

### 3.0.1 第一层：没有主体就不是人做的

`subjectRoles === null` 表示系统上下文——迁移、种子、鉴权自身、清理任务、OIDC 回调、Telegram webhook 全在这一类。**这个信号已经在可见性判定里用了**（`visibilityConditions` 的第一行），一个概念两处用，不需要新造判据。

它结构性地解决了一个在 SQL 层解不了的问题：`update('base_oidc_users', { profile })` 在登录回调里和管理员手工改，生成的语句一模一样，靠列名区分只是代价高的猜测。而适配器知道有没有人登录着。

### 3.1 表白名单

**审计范围是代码常量，不是配置，不进数据库**——与 `shared/system-fields.mts` 的 `SYSTEM_FIELD_NAMES` 同例。放进配置意味着运行时可以关掉审计，那正是审计最不该允许的事。

```ts
// shared/audit-tables.mts
export const AUDITED_TABLES = [
  'base_users', 'base_tenants', 'base_branches', 'base_hosts',
  'base_configs', 'base_bootstrap',
  'global_sites', 'global_site_hosts', 'global_cloud_credentials', ...
] as const;

/** 显式声明不审计的表，与白名单共同覆盖全部表，见 §3.4。 */
export const UNAUDITED_TABLES = [
  'base_sessions', 'base_devices', 'base_device_users', 'base_oidc_sessions',
  'base_audit_entries', 'global_schema_migrations', ...
] as const;
```

各业务站点按需把自己的表加进对应的一份。

排除 `insert` 与物理 `delete` 之后（§3.0），表这一层不再是必需的——字段规则已经能挡住高频写入。保留它的理由变成**显式声明审计面**：哪些表的变更值得留证据是一个业务判断，写下来比让它由过滤规则的副作用决定要好。

### 3.2 列白名单

受管表里也有机器维护的列。**逐表显式声明哪些列值得留证据**，没列进来的一律不记。

```ts
export const AUDITED_COLUMNS: Record<string, readonly string[]> = {
  base_users: ['name', 'password', 'roles', 'status', 'owner_uid'],
  global_sites: ['key', 'name', 'base_site_key', 'dsn', 'status', ...],
  ...
};
```

**为什么是白名单而不是排除清单。** 排除失败在敞开的一侧：新增一个机器维护的列，它会静默地开始产生噪音，只有等表撑大了才会被发现。这一点在实现过程中被证实了两次——`global_sites.migration_status` 和 `base_oidc_users.profile` 都是事后偶然发现的。改成白名单之后逐列过一遍 170 个业务列，又找出十来个同类：`pve_nodes.last_checked_at`/`last_error`（探活结果）、`pve_vms.pve_status`/`pve_config`/`error_message`（从 PVE 拉回的运行时状态）、`global_cloud_email_template_publications.content_hash`（发布流程算出来回填）、`global_sites.is_system`（建库时定死的只读标志）、`passport_telegram_accounts.chat_id`/`nickname`（webhook 按用户在 Telegram 侧改名同步）。**黑名单永远找不全这些，白名单强迫一个个看。**

`deleted_at` 是唯一的例外：它由公共层维护、不出现在任何一张表的白名单里，但它是软删除与恢复的唯一信号，受管表一律放行。

**一次更新如果一个白名单列都没碰，整条不产生记录**；混在机器列里一起提交时，只有白名单列进 `changes`。

### 3.3 字段规则不需要读原行

判断"这次更新是否只碰了排除列"**只看写入的列名**，不需要先读那一行。因此 `update('base_sessions', { expires_at })` 这类写入在进入公共层的第一步就短路：不多一次读、不产生记录、零成本。

只有确实在改业务列时才去读原行做逐列比对（§4.2）。**"每次受管写入多一次读"这个代价只落在真正的业务变更上**，不落在心跳路径上。

按 1000 日活、人均 50 次请求估算，仅会话续期一项每天就是 5 万次写入——两层过滤后它们一条记录都不产生。

### 3.4 遗漏必须变成构建失败

表白名单有一个危险的失败方向：**新增表时忘记登记，那张表就静默地没有审计**。审计里"漏"比"吵"严重得多——吵会被表体积立刻暴露，漏只有等到要查证时才发现，而那时已经来不及。

因此加一条测试：断言**每一张表要么在 `AUDITED_TABLES`，要么在 `UNAUDITED_TABLES`**，两边都不在即失败。新增表时必须主动做一次决定，不能靠"忘了"落进默认。

**列这一层同样如此**：受管表必须在 `AUDITED_COLUMNS` 里声明，白名单里出现 schema 中不存在的列也失败——列改名或删除时会立刻暴露，不会留下一条永远匹配不上的死规则。

## 4. 数据结构

### 4.1 `base_audit_entries`

| 字段 | 说明 |
| --- | --- |
| `table_name` | 被改动的表 |
| `row_id` | 被改动的行 |
| `action` | `update` / `soft_delete` / `restore`；三者都是 UPDATE，按写入的列区分。不含 `insert` 与物理 `delete`，见 §3.0 |
| `changes` | JSON：只记**变化了的列**的前后值 |
| `status` | `applied` / `reverted` |

加上统一的系统字段与归属字段。**操作者复用现成的机制**：`created_duid` 是真实操作者的 device-user，`owner_uid` 是作用账号——代用户操作时两者不同，正好还原出"客服 A 以用户 B 的身份改了这一行"。归属字段同时让审计记录自动落入正确的租户与分站，可见性因此免费获得（§8）。

### 4.2 只记变化的列

`update` 只记录**实际发生变化**的列。业务表单常常整体提交，未改动的字段一并写入；若照单全收，每条记录都会包含大量噪音，也让"改了什么"这个问题失去答案。

因此更新前读一次原行，与将写入的值逐列比对，**没有任何列变化时不产生记录**。

## 5. 凭证列：存值，但不显示

审计**原样记录所有列**的前后值，凭证列也不例外。它在活表里是什么形态，审计里就是什么形态——密码是哈希、外部 access key 是明文——**不额外加密**：解密密钥和数据库在同一台机器上，能脱库的人一样拿得到，应用层加密只增加复杂度，不增加安全性。

因此**撤回对所有列都有效**。改错了云凭据、误改了密码，都能还原，而这恰恰是最需要撤回的场景。写回旧哈希，旧密码就恢复了；服务端全程不需要知道原文。

限制只在**读取**这一侧：

```ts
// 存，但接口不返回值——只显示"该列已变更"
export const HIDDEN_VALUE_COLUMNS = [
  'password', 'dsn', 'dsn_password',
  'token', 'token_hash', 'secret_token', 'secret_hash',
  'access_key_secret', 'api_token_secret', 'client_secret',
  'authorization_code_hash', 'code_hash',
  'value',
] as const;
```

审计的列表与详情接口对这些列只返回"已变更"这一事实。撤回是服务端把记录里的值直接写回去，不经过接口，**不需要任何人看见它**。`base_configs.value` 整块 JSON 里混着 OIDC 客户端密钥、无法逐列区分，因此整列不显示。

## 6. 钩子落点与记录顺序

### 6.1 记录挂在 `runSql`，不挂在 `SqlBuilder`

`SqlBuilder` 是纯的：只生成 `{ query, values }`，不碰数据库。而审计要"读原行 → 写记录 → 再执行"，是有副作用的多步流程，放不进去。

因此 `update` 在返回值里附带元信息，由 `runSql` 据此完成记录再执行：

```ts
export type SqlQuery = {
	query: string;
	values: unknown[];
	/** 仅 update 附带；runSql 据此决定是否记录变更。业务代码不构造也不读取它。 */
	audit?: { table: string; values: Values; where: SqlCondition[] };
};
```

**不新开 `runAudited()` 之类的显式入口。** 审计不应依赖"记得调用哪个函数"——漏掉一处就少一条证据，而且这种遗漏没有任何征兆。`runSql` 已经是所有写入的必经之路，把判断放在那里，覆盖面由类型和调用路径保证，不由人的记性保证。

代价是 `runSql` 从"执行一条语句"变成"可能先做两次额外查询再执行"。这个代价只落在受管表的业务列变更上：白名单外的表、只碰排除列的更新，都在生成元信息之前就被排除了（§3.2、§3.3）。

### 6.2 记录时机与顺序

无事务可用（`server/database/d1.mts` 没有 `transaction`），记录与应用无法原子完成，因此**顺序是强制的：先记录，后应用**。

- 先记后做，中断留下"记了但没做"：可被发现、可重放、可核对。
- 先做后记，中断留下"做了但没记"：审计里最不能接受的状态，且事后无法察觉。

记录写入失败时**整个操作失败**，不允许"审计写不进去就跳过"——那等于给了绕过审计的开关。

## 7. 撤回

### 7.1 三种动作的逆操作

| 原动作 | 撤回 |
| --- | --- |
| `update` | 把 `changes` 里的前值写回那些列 |
| `soft_delete` | `deleted_at` 写回 0 |
| `restore` | `deleted_at` 写回原时间戳 |

三者是同一个操作：把 `changes` 里的前值写回去。删除与恢复只是碰的列恰好是 `deleted_at`。

### 7.2 按当前值校验

撤回时，对每一个要还原的列都要求它**当前仍等于审计记录里的 `after`**——也就是"这一列自那次变更之后没有被人动过"：

```sql
UPDATE base_users SET name = ?    -- before
WHERE id = ? AND name = ?          -- after
```

多列就多几个条件，仍然是一条语句，影响行数为 0 即拒绝并提示"该记录已被后续修改覆盖，无法撤回"。无事务下天然原子，与本项目其余的条件更新是同一手法。

`after` 为 `NULL` 时条件要写成 `col IS NULL`：SQL 里 `col = NULL` 求值为 unknown，永远不匹配。

**不用 `updated_at` 做乐观校验。** `updateManaged` 每次都会写 `updated_at`，包括那些被排除在审计之外的心跳更新（§3.2）。用它校验的话，`last_seen_at` 一动，那一行上此前的所有变更就永远撤不回来了——被一条我们根本没记录、也不关心的更新挡死。按当前值校验只关心真正要还原的那几列，别人改了同一行的其他列不受影响。

### 7.3 撤回本身也是一次变更

撤回产生一条**新的**审计记录（`action` 为对应的逆操作），同时把原记录的 `status` 置为 `reverted`。

`status` 是审计记录上**唯一可变的字段**，且只能从 `applied` 变为 `reverted` 一次。除此之外审计记录**不可修改、不可删除**，只能随保留期过期——可以被改写的审计没有意义。

### 7.4 多选撤回按倒序逐条执行

界面可以多选撤回，但它只是逐条执行的批量入口，**不是原子的级联回滚**——无事务环境下做不到，也不应假装做得到。

**执行顺序必须是倒序（新到旧）。** 这由 §7.2 的值校验直接决定：同一列经历 A → B → C 两次变更后，当前值是 C，只有先撤 B→C（`SET col=B WHERE col=C`）才能接着撤 A→B。正序则第一步就因为当前值是 C 而拒绝。

不涉及同一列的条目彼此独立，顺序对它们无影响；倒序只对同一列的链式变更是必需的。

**逐条独立判定，互不影响。** 某一条因值校验失败被拒绝时，其余条目照常执行，最后返回每一条的结果。不回滚已成功的部分——既无法回滚，也没有必要：每一条撤回本身都是一次可再撤回的变更（§7.3）。

顺序错了的后果只是撤不动，不会写坏数据。这是值校验相对 `updated_at` 校验的又一处好处：它让错误的顺序失败，而不是让它覆盖别人的修改。

## 8. 列表顺序与索引

**执行撤回时必须在实现里按 `created_at` 降序重新排序，不能沿用列表的显示顺序。** §7.4 的倒序是正确性要求，而显示顺序是用户可改的：按表名或操作者排一次序再多选撤回，链式变更就会全部撤不动。值校验保证了这不会写坏数据，但行为会变得莫名其妙——同样几条，按时间排能撤，按别的列排就撤不了。执行顺序必须与显示解耦。

列表**默认按 `created_at` 降序**，与项目现有 CRUD 一致（例如 `server/routes/base/api/panel/admin/base/users.mts` 的 `orderBy: id DESC`）。审计列表最常看的是"刚刚发生了什么"；升序分页还会因为新记录不断插入头部而让每页内容错位。用户可以自由改排序、筛选和分页，不影响撤回的正确性。

索引：审计查询几乎总是"某个范围内按时间倒序"，因此除了归属列本身，还需要 `(owner_tid, created_at)`、`(owner_bid, created_at)`、`(owner_uid, created_at)` 这类复合索引；只有 `(owner_tid, deleted_at)` 的话排序还要再排一次。

## 9. 可见性

审计记录带有完整的归属字段，因此直接适用前置需求 §4.2 的规则，不需要额外设计：

| 角色 | 能看到的审计范围 |
| --- | --- |
| `platform_admin` | 全部 |
| `tenant_admin` | 本租户 |
| `branch_admin` | 本分站 |
| `user` | 以自己为作用账号产生的记录 |

普通用户能看到自己的变更历史，是这个设计的自然结果，也是有用的。

**撤回权限单独收窄**：仅 `platform_admin`、`tenant_admin`、`branch_admin` 可以撤回，且只能撤回自己可见范围内的记录。普通用户只能查看。

实现上，审计接口挂在 `panel/admin` 下，那一层的角色门（`server/routes/base/api/panel/admin.mts`）已经把非管理员挡在外面，撤回因此天然受限；管理员之间的范围差异由公共层的归属判定收敛，接口里不再叠加条件。**面向普通用户的「我的变更记录」页面尚未提供**，见 §14。

## 10. 保留期

审计表只增不减，必须有保留期，规则与 `sms_messages` 一致：

- 由站点设置里的「变更审计保留天数」控制（`site-settings.auditRetentionDays`），按租户独立，默认 **365 天**，设为 `0` 表示不自动清理，上限十年。
- 到期记录**物理删除**，分批进行且可重入，以系统上下文运行（`purgeAuditRetention`）。
- 触发方式：本项目没有调度器，因此 Node 进程启动时跑一次、之后每 6 小时跑一次。漏跑一轮只是记录多留一会儿。Workers 部署没有常驻进程，要改用 cron 触发器调用同一个函数。
- 保留期只能由 `platform_admin` 修改——租户管理员能缩短自己的审计保留期，等于给了销毁证据的手段。

## 11. 操作原因与审批（设计已确认，未实施）

### 11.1 每次人工修改都要说明理由

审计现在记下了"谁在什么时候把价格从 100 改成 50"，但**没记为什么**。取证时前者的价值远低于"……因为客诉退款，工单 #1234"。`reason` 是让审计从日志变成证据的那一列。

因此提交修改时弹出**操作原因**输入框，内容写进审计记录。

**不能全量强制。** 改个昵称也要写原因，人会填"1"、"。"——**垃圾原因比没有原因更糟，它给了假的可信度**。只对敏感操作要求，清单复用 `AUDITED_COLUMNS` 的结构再标一个 `requiresReason`。

原因跟着**一次操作**走，不跟着单条语句走：一次更新命中多行会产生多条记录，它们共享同一个原因。因此由 API 中间件从请求体里取出 `_reason` 放进请求上下文，`runSql` 记录时带上——**业务路由一行都不用改**，与审计钩子同一个思路。

### 11.2 「立即生效」，不是「立即审批」

管理员勾选后跳过审批直接写库。**措辞必须是「立即生效」**：自己批自己不叫审批，叫跳过审批。记录里如实写成"无需审批（角色：platform_admin）"，不伪造一条审批记录——审计的价值全在诚实，这一处含糊会毁掉整份记录的可信度。

有权跳过的角色：`platform_admin`、`tenant_admin`、`branch_admin`，与 §9 的撤回权限一致。

```
提交（必填原因） ──┬─ 勾了立即生效 + 有权限 → 直接写库 + 审计留痕（带原因）
                   └─ 没勾 / 没权限        → 进审批队列，不写库
```

### 11.3 审批单与审计**不是同一张表**

早先设想过"同一张表两种状态：`status` 增加 `pending` 与 `rejected`"。这个判断站不住，最硬的理由就在 §7.3：

> 审计记录**不可修改、不可删除**，只能随保留期过期——可以被改写的审计没有意义。

而审批**必须可改**：申请人要能撤回、驳回后要能改了重交、审批人要写意见。一张表不可能同时要求"绝不可改"和"要能改"。合并等于把审计最核心的属性让掉。

其余错配都由这一条派生：

| | 审计 | 审批 |
| --- | --- | --- |
| 记的是 | 已发生的事实 | 尚未发生的意图 |
| 可变性 | 只有 `status` 能变一次 | 全程可改 |
| 保留期 | 365 天后物理删除 | 可能要作为业务档案长期保留 |
| 量级 | 每次变更一条，量大 | 少数敏感操作，量小 |
| 粒度 | **列级 diff** | **一次操作**（可能由多条语句组成） |
| 终态 | 只有"发生了" | 有"被驳回"这种正常结果 |

倒数第二行解释了一个实现上的现象：**多条语句构成的业务操作批不了**（例如 `setPrimaryAccountEmail` 是两条 UPDATE）。那不是实现难题，是模型不匹配——审计按语句记，审批按操作走。

正确的关系是**因果，不是同表**：

```
审批单（可改） --批准--> 走公共层写库 --> 审计自动留痕（不可改）
```

批准时就走正常的 `sql().update()`，`runSql` 的审计钩子自动记一条，不需要任何特殊处理。再给 `base_audit_entries` 加一列可空的 `request_id` 指向审批单，"这次变更经过审批"也能在审计里查到。

**该复用的是代码，不是表**：`changes` 的 JSON 形状、值校验的写法（`SET col=X WHERE col=Y`）、正反向 apply 的实现，抽成共享模块两边都用。

### 11.4 实现落点

`runSql` 命中"需审批且未勾立即生效"时，记下审批单、**不执行**，抛一个 `PendingApprovalError`；中间件把它转成 202「已提交审批」。抛异常的好处是**不用改任何路由**——异常一抛，后面那句 `return apiMessage(c, 200, '已保存')` 根本不会执行，这正是想要的。

唯一要小心的是受管表写入被 `try/catch` 包住的 7 处（例如 `users.mts` 的 `catch { return 409 '用户名已存在' }`），会把异常吞掉变成误导性提示，需要逐个改成重新抛出，并配一条测试——**漏一处就是一个静默错误**。

审批白名单只放**单语句操作**，这不是妥协，是把边界划在能保证正确的地方（见上表最后两行）。

## 12. 实施步骤

1. 新建 `base_audit_entries`，补四个迁移组 × 四种方言的迁移文件。
2. `shared/audit-tables.mts` 定义 `AUDITED_TABLES`、`UNAUDITED_TABLES`、`NON_AUDITED_COLUMNS` 与 `HIDDEN_VALUE_COLUMNS`，并加上 §3.4 的覆盖性测试。
3. 在 `update` 上记录变更（`softDelete`、`restore` 自动覆盖）：先按表白名单过滤，再按写入的列名判断是否只碰了排除列（不读行即可短路），确认可能有业务列变化后才读原行逐列比对，逐列一致时同样不记录。

   钩子落点见 §6.1。
4. 撤回接口与页面：列表、详情、撤回动作，带 §7.2 的乐观校验与 §8 的权限收窄。
5. 保留期配置与清理任务。
6. 冒烟用例覆盖 §13 全部条目（`npm run test:change-audit`、`npm run test:audit-tables`）。

第 3 步要注意：记录发生在公共层，业务代码不感知，因此**任何绕过公共层的裸 SQL 都会绕过审计**。AGENTS.md 已经要求所有 API 使用参数化数据库助手，这里是又一条理由。

## 13. 验收标准

- 白名单内的表发生业务字段变更时产生一条记录；只改动排除列（`last_seen_at`、`expires_at` 等）时不产生记录，且不发生额外读取。
- 每一张表都出现在 `AUDITED_TABLES` 或 `UNAUDITED_TABLES` 之一；新增表未登记时测试失败。
- 白名单外的表任何写入都不产生记录。
- 软删除与恢复各产生一条记录，`action` 分别为 `soft_delete` 与 `restore`。
- 新增与物理删除不产生记录。
- `update` 记录里只包含实际变化的列；提交未改动的字段不产生噪音，全部未变化时不产生记录。
- 凭证列的值不出现在审计列表与详情的接口响应里，只显示"已变更"；撤回这些列仍然有效。
- 代用户操作产生的记录中，`created_duid` 是客服的 device-user，`owner_uid` 是被代查的账号。
- 新增记录不产生审计条目。
- 撤回 `update` 后字段恢复原值；撤回 `soft_delete` 后记录回到未删除状态；撤回 `restore` 后 `deleted_at` 写回**原时间戳**而不是当前时间。
- 要还原的列在变更之后又被改过时，撤回被拒绝且数据不变。
- 同一行上与本次变更无关的列被改过，不影响撤回。
- 心跳列（`last_seen_at` 等）的更新不影响撤回。
- 撤回产生一条新记录，原记录 `status` 变为 `reverted`；再次撤回同一条被拒绝。
- 同一列的两次连续变更，多选后按倒序撤回全部成功，数据回到最初值。
- 同样两条按正序撤回时第一条即被拒绝，数据保持不变。
- 多选中某一条被拒绝时，其余条目照常撤回，结果逐条返回。
- 审计记录不能被修改或删除，接口层没有对应入口。
- 列表默认按时间降序；改用其他列排序后执行多选撤回，仍按时间降序执行并全部成功。
- `tenant_admin` 只能看到并撤回本租户的记录；`branch_admin` 限本分站；普通用户只能查看自己的。
- 超过保留期的记录被物理删除，未到期的不受影响。
- 审计写入失败时，业务写入一并失败。

## 14. 已知限制

- **审批队列今天不会有内容。** 后台 API 的角色门（`server/routes/base/api/panel/admin.mts`）本就只放三个管理员角色进来，而这三个角色都能勾「立即生效」，因此经后台发起的修改一条都不会进队列。今天唯一会进队列的是普通用户在个人中心、账户中心的自助操作（改昵称、绑邮箱）——恰恰是最不敏感的那些。这个功能要等 `agent` 或分站运营角色落地才真正有用；要让它现在就有意义，得把"能否跳过"从**按角色**改成**按操作**（改角色、改云凭据、跨租户过户即使管理员自己做也要复核，即四眼原则）。
- **不覆盖新增与物理删除。** 见 §3.0。三处后台的物理删除在改用软删除之前是审计盲区。
- **只覆盖经过公共层的写入。** 裸 SQL 与迁移脚本不产生记录，这是有意的（数据搬迁不是业务变更）。
- **凭证的历史值会在审计表里多留一段时间。** 存储形态与活表一致（§5），但保留期更长——已经轮换掉的密钥要等保留期到了才清除。
- **多选撤回不是原子回滚。** 逐条独立执行，见 §7.4。
- **业务变更每次多一次读。** 这是记录变更前值的代价；心跳写入按 §3.3 短路，不承担该成本。
- **审计表本身不被审计。** 否则会无限递归；它靠不可修改与保留期保证完整性。
- **没有面向普通用户的查看页面。** 归属字段已经让「只看自己的记录」免费成立（§9），但目前只有 `panel/admin` 下的管理员页面，普通用户没有入口。
- **撤回被拒绝时不产生噪音记录。** 撤回语句的 WHERE 里带着值校验条件，审计的 SELECT 用的是同一组条件，因此校验不通过时读不到行、也就不会记下一条没真正发生的变更。
- **受管表目前都没有心跳列。** §3.2 的字段排除清单因此暂时只在构建层生效（`updated_at`、`updated_duid` 本就写不进业务值），等 `sms_shortcut_tokens` 这类表建起来才会真正挡量。
