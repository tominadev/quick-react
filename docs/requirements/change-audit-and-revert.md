# 变更留痕与回滚需求开发文档

状态：已实施（2026-09-04）。留痕、回滚、保留期清理与后台页面均已落地；仍未做的见 §14。

前置需求：[数据可见性与代用户操作](data-visibility-and-delegated-access.md)。

## 1. 背景

现有的审计只有两个字段：`created_duid` 与 `updated_duid` 记录"谁动过这一行"，但不记录**动了什么**。一行数据被改成什么样、原来是什么、谁在什么时候改的，事后无从查证；改错了也没有回退手段，只能靠人回忆原值手工改回去。

公共数据层已经拦截了全部写入（`server/database/sql.mts` 的 `insert`、`update`、`softDelete`、`restore`、`delete`），归属与审计字段都在那里统一填充。变更留痕挂在同一个位置，业务代码不感知。

## 2. 目标

- 受管表上**人做的每一次修改**都留下记录：动了哪张表哪一行、哪些字段、从什么变成什么、谁在什么时候做的。
- 每一条变更都能**回滚**，把数据还原到变更前的状态。
- 记录同时充当操作日志与审计凭据：既能给运维排查用，也能在事后追责时作为证据。
- 不引入新的凭证泄露面，不拖垮高频写入路径。

## 3. 受管范围

### 3.0 判定的是「操作」，不是表和列

审计要记的是**人做的修改**。而这个信息在 SQL 层已经没有了：

```ts
update('base_oidc_users', { profile })   // 登录回调刷新上游快照？还是管理员手工改？
update('global_sites', { migration_status })  // 迁移状态机？还是管理员改了 DSN？
```

两种情况生成的语句**一模一样**。靠表名或列名去反推，只是代价很高的猜测——实现过程中按列排除试过两轮，两次都漏（`migration_status`、`profile` 都是事后偶然发现的），改成列白名单又会把真正的人工操作误伤：管理员吊销一台设备写的是 `passport_devices`，和登录时机器写的是同一张表。

**所以判定放在路由层，由调用方显式声明**：

```ts
await runOperation(c, database, [sql({ database }).update('base_users', values, { id })], { reason });
```

只有这里同时知道：这是哪个人、因为什么、勾没勾立即生效、这次操作包含哪几条写入。

### 3.1 三种写入路径

| 函数 | 用于 | 留痕 |
| --- | --- | --- |
| `runOperation` / `runOperationSql` | 人工操作 | **是** |
| `runSystemSql` | 人工请求里顺带推进的机器写入（验证码过期、会话续期） | 否 |
| `runSql` | 其余一切（登录、OIDC 回调、webhook、迁移、清理、CLI） | 否 |

第二行是必要的：一次表单提交里除了那个操作本身，还会顺带推进一些状态机。它们发生在人工请求里却不是人做的修改，用 `runSystemSql` 是一次**显式声明**，读代码的人一眼能看见，而不是靠一份列名清单去猜。

**一个表级例外都没有，审计表自己也不例外。** 它不需要被排除在外：递归是被 `runSystemSql` 挡住的——审计模块自身的写入（记录变更、审批状态）走那条路径，本来就不留痕。因此从「数据管理」改一条审计记录会照常留痕、照常走审批，留下的那条新记录就是「谁动了审计」的证据。改一条必然产生一条新的，想抹干净就得无限抹下去，**篡改因此总是可见的**。

**引导流程也不留痕。** 初始管理员注册（`/api/sign`）改的是 `base_bootstraps.value`，但那时还没有会话，操作者与作用账号都是空的；而 `value` 是脱敏列（§5），记下来只会得到一条「value：已变更」——既说不出谁，也说不出改了什么。「初始管理员是什么时候建的」由 `base_users.created_at` 回答，不需要再抄一遍。

### 3.2 `insert` 与物理 `delete` 仍然不审计

**`insert` 不审计。** 新增没有"变更前"可留，而行本身就是"新增了什么"的完整记录——`created_at` 与 `created_duid` 已经记下谁在什么时候创建了它。为新增再存一份快照是把同一份事实抄两遍。

**物理 `delete` 不审计。** 本项目里人做的删除就是软删除；`sql.mts` 中 `delete` 的注释写明"仅供清理任务和明确的不可恢复操作使用"。现有 13 处物理删除调用中，12 处是会话与协议清理，属机器行为。剩下 3 处后台人工删除（`global_telegram_bots`、两张对象存储绑定表）按项目约定本就应改用 `softDelete`；改过之后审计自然覆盖。

`softDelete` 与 `restore` 都是 `updateManaged(table, { deleted_at: ... })`，SQL 层面就是 UPDATE，因此**一条路径同时覆盖修改、删除与恢复**。

### 3.3 只记变化的列，且只在需要时读原行

判断"这次写入要不要记"完全不需要读表：`runSql` 与 `runSystemSql` 直接执行，只有 `runOperation` 才会去读原行做逐列比对（§4.2）。**"每次写入多一次读"这个代价只落在人工操作上**，登录续期、心跳、协议状态机一次都不多读。

按 1000 日活、人均 50 次请求估算，仅会话续期一项每天就是 5 万次写入——它们走 `runSql`，一条记录都不产生。

### 3.4 漏包必须立刻报错

把判定搬到路由层，就重新引入了一个风险：**忘了包 `runOperation`，那次操作就静默地没有审计**。审计里"漏"比"吵"严重得多——吵会被表体积立刻暴露，漏只有等到要查证时才发现。

两道防线：

1. **运行时断言。** `worker.mts` 按请求路径（`/api/panel/`）给适配器打上 `humanOperation` 标记，`runSql` 见到"人工请求 + 受管写入"直接抛错。忘了包就是立刻报错，而不是少一条证据。
2. **静态检查。** `npm run test:audit-scope` 扫描全部 `api/panel/**` 路由，断言里面不出现裸的受管写入。

`runSql` 因此从**记录者**变成了**看门人**：它不做记录，只保证没人绕过操作层。

## 4. 数据结构

### 4.1 `base_audits`

表名叫 `base_audits` 而不是 `base_audit_entries`：这里存的不是「谁看了什么」的审计流水，
而是每一次后台修改的**申请与它的去向**——待审批、已生效、已驳回、已撤销、已回滚。
审批与审计用同一张表（§11.4），命名跟着更常用的那一面走。

| 字段 | 说明 |
| --- | --- |
| `operation_id` | 同一次人工操作的多条写入共享它 |
| `reason` | 操作原因（§11.1）：审计记了「改了什么」，这一列记「为什么」 |
| `table_name` | 被改动的表 |
| `row_id` | 被改动的行 |
| `action` | `update` / `soft_delete` / `restore`；三者都是 UPDATE，按写入的列区分。不含 `insert` 与物理 `delete`，见 §3.0 |
| `changes_before` `changes_after` | 前后两份值，各一列：`{列名: 值}`，只记**变化了的列** |
| `scope` | `admin` / `self`：后台操作还是用户自助。与「要不要走审批」是同一条判定（§11.2），由 `operationScope()` 一处算出、两处使用 |
| `review_status` | 审批状态：`none` / `pending` / `approved` / `rejected` / `withdrawn`，见 §11.4 |
| `data_status` | 数据状态：`unwritten` / `applied` / `reverted`，见 §11.4 |
| — | 审批的时间、操作者与理由不占列：每一次追加一条 `base_audit_approvals`，见 §7.3 |

加上统一的系统字段与归属字段。**操作者复用现成的机制**：`created_duid` 是真实操作者的 device-user，`owner_uid` 是作用账号——代用户操作时两者不同，正好还原出"客服 A 以用户 B 的身份改了这一行"。归属字段同时让审计记录自动落入正确的租户与分站，可见性因此免费获得（§8）。

### 4.2 只记变化的列

`update` 只记录**实际发生变化**的列。业务表单常常整体提交，未改动的字段一并写入；若照单全收，每条记录都会包含大量噪音，也让"改了什么"这个问题失去答案。

因此更新前读一次原行，与将写入的值逐列比对，**没有任何列变化时不产生记录**。

**`changes` 里记的是逻辑值，不是存储形态。** SQLite 没有 JSON 类型，`roles` 这类列以文本存储、读回来也是文本，而写入侧传的是数组。直接记录会得到两边类型都对不上的结果：

```json
{"roles": {"before": "[\"platform_admin\"]", "after": ["platform_admin"]}}
```

判据取自**写入侧**：只要待写入的值能解析成 JSON 的对象或数组——本身就是对象／数组，或者是一段 JSON 文本——两边就都还原成逻辑值。存储细节不漏进审计记录。

只认对象与数组，不认数字、布尔与 `null`：那几种会把普通文本列误判成 JSON（`'123'` 会变成 `123`）。而一个业务字符串恰好以 `[` 或 `{` 开头、并且能整段解析，基本上就是 JSON。

写入侧的形态并不统一，这一点必须一起处理：路由层直接传数组或对象，而「数据管理」的表单传的是 JSON 字符串。只认其中一种的话，**同一列会因为从哪个页面改而记成两种样子**：

```json
{"roles": {"before": ["a"], "after": ["b"]}}          // 用户管理页
{"roles": {"before": "[\"a\"]", "after": "[\"b\"]"}}   // 数据管理页
```

即便某个业务列的值恰好长得像数组而被误判，来回一趟仍是同一串文本，回滚不受影响。

回滚时写回数组同样正确：各方言的适配器都会把数组 `JSON.stringify` 后入库（`sqlite.mts`、`mysql.mts`、`d1.mts` 三处一致），WHERE 里的条件值走同一条路径，因此和存储的文本能匹配上。

比对本身也要按类型来：BIGINT 各驱动返回的类型不一致（number / string / bigint），一律按字符串比；数组与对象按 JSON 比——`String(['a','b'])` 得到 `a,b`，两个不同的数组可能撞上。

## 5. 凭证列：存值，但不显示

审计**原样记录所有列**的前后值，凭证列也不例外。它在活表里是什么形态，审计里就是什么形态——密码是哈希、外部 access key 是明文——**不额外加密**：解密密钥和数据库在同一台机器上，能脱库的人一样拿得到，应用层加密只增加复杂度，不增加安全性。

因此**回滚对所有列都有效**。改错了云凭据、误改了密码，都能还原，而这恰恰是最需要回滚的场景。写回旧哈希，旧密码就恢复了；服务端全程不需要知道原文。

限制只在**读取**这一侧：

```ts
// 存，但接口不返回值——只显示"该列已变更"
export const HIDDEN_VALUE_COLUMNS = [
  'password', 'dsn', 'dsn_password',
  'token', 'token_hash', 'secret_token', 'secret_hash',
  'access_key_secret', 'api_token_secret', 'client_secret',
  'authorization_code_hash', 'code_hash',
  'value',
] as const;
```

审计的列表与详情接口对这些列只返回"已变更"这一事实。回滚是服务端把记录里的值直接写回去，不经过接口，**不需要任何人看见它**。`base_configs.value` 整块 JSON 里混着 OIDC 客户端密钥、无法逐列区分，因此整列不显示。

## 6. 钩子落点与记录顺序

### 6.1 记录在操作层，`runSql` 只看门

`SqlBuilder` 是纯的：只生成 `{ query, values, audit }`，不碰数据库。`audit` 是结构化的元信息（表、写入值、完整 WHERE、归属），供上层读原行、算差异——**它不判断这次写入算不算人工操作**，那个信息在这一层根本没有（§3.0）。

记录由 `server/modules/base/operation.mts` 完成："读原行 → 写记录 → 再执行全部语句"。放在这里有三个好处：

- **一次操作一个 `operation_id`**，多条写入共享同一条原因，不再是"一条语句一条记录"各自为政；
- 拿得到**操作原因**与后续的**立即生效**勾选（§11）；
- 审批可以在动手之前决定，要么全做要么全不做，不会出现批了一半的中间态。

代价是覆盖面不再由"所有写入的必经之路"自动保证，改由 §3.4 的两道防线保证——一道运行时断言，一道静态检查。

### 6.2 记录时机与顺序

无事务可用（`server/database/d1.mts` 没有 `transaction`），记录与应用无法原子完成，因此**顺序是强制的：先记录，后应用**。

- 先记后做，中断留下"记了但没做"：可被发现、可重放、可核对。
- 先做后记，中断留下"做了但没记"：审计里最不能接受的状态，且事后无法察觉。

记录写入失败时**整个操作失败**，不允许"审计写不进去就跳过"——那等于给了绕过审计的开关。

## 6.5 一套词，各管各的

这一页上会同时出现好几个「往回走」的按钮，词不统一的话读的人得先去看状态列才敢点。全站只用这一套：

| 词 | 动的是 | 审批动作 | 谁点 |
| --- | --- | --- | --- |
| **提交** | — | → `pending`（或自助操作直接 `applied`） | 任何人 |
| **批准** | 申请 + 数据 | `pending → approved` 且 `unwritten → applied` | 审批人（**第一次生效就是它**） |
| **驳回** | 申请 | `pending → rejected` | 审批人（只驳别人提的） |
| **撤销** | 申请 | `pending → withdrawn` | 申请人（只撤自己提的） |
| **恢复** | 新增申请 | `rejected`/`withdrawn` → `pending` | 放回队列，数据一个字不动。**只对新增开放** |
| **回滚** | 数据 | `applied → reverted` | 把已经生效的改回去 |
| **重新应用** | 数据 | `reverted → applied` | 把回滚掉的再写回去 |
| **还原** | 一行记录 | 回收站 → 列表 | 新提一条 `action=restore` 的申请 |
| **彻底删除** | 一行记录 | 物理删除 | 只给超级用户，不可逆也不留痕 |

几条容易踩的：

- **「撤销」只有一个词**。行上的按钮曾经叫「撤回」，审批页叫「撤销申请」——同一件事两种说法，读的人会以为是两个动作。
- **「重新应用」不叫「重做」**。这一页上已经有「撤销」，撤销/重做那一对会让人以为它俩相反，而它们根本不在同一根轴上。
- **「还原」不叫「恢复」**。前者动的是一行记录（回收站里捞回来，Windows 用的就是这个词），后者动的是一条申请。
- **「第一次生效」没有独立的名字**，它就是批准的效果：批准同时推两根轴，而重新应用只推数据那一根。

按钮上还要带上是哪一类申请：「撤销新增」「批准删除」「驳回还原」——撤销新增会让那一行进回收站，撤销修改一个字都不动数据，后果各不相同，而这正是点下去之前要知道的事。

## 7. 回滚

### 7.1 三种动作的逆操作

| 原动作 | 回滚 |
| --- | --- |
| `update` | 把 `changes_before` 里的值写回那些列 |
| `soft_delete` | `deleted_at` 写回 0 |
| `restore` | `deleted_at` 写回原时间戳 |

三者是同一个操作：把 `changes_before` 里的值写回去。删除与恢复只是碰的列恰好是 `deleted_at`。

### 7.2 按当前值校验

回滚时，对每一个要还原的列都要求它**当前仍等于审计记录里的 `after`**——也就是"这一列自那次变更之后没有被人动过"：

```sql
UPDATE base_users SET name = ?    -- before
WHERE id = ? AND name = ?          -- after
```

多列就多几个条件，仍然是一条语句，影响行数为 0 即拒绝并提示"该记录已被后续修改覆盖，无法回滚"。无事务下天然原子，与本项目其余的条件更新是同一手法。

`after` 为 `NULL` 时条件要写成 `col IS NULL`：SQL 里 `col = NULL` 求值为 unknown，永远不匹配。

**不用 `updated_at` 做乐观校验。** `updateManaged` 每次都会写 `updated_at`，包括那些被排除在审计之外的心跳更新（§3.2）。用它校验的话，`last_seen_at` 一动，那一行上此前的所有变更就永远撤不回来了——被一条我们根本没记录、也不关心的更新挡死。按当前值校验只关心真正要还原的那几列，别人改了同一行的其他列不受影响。

### 7.3 回滚是把记录翻到另一面，不是新开一条

回滚**不产生新的审计记录**：前后两份值都记着，`data_status` 说明这次变更当前停在哪一边。回滚错了就再翻回来（`reverted → applied`），不会堆出一串互相指向的记录。

```
一次变更 = 一条记录，永远
  applied  ──回滚──▶  reverted
         ◀──重新应用──
```

**三个「往回走」用三个词，不许混。** 它们动的东西完全不同：

| 词 | 动的是 | 审批动作 | 谁点 |
| --- | --- | --- | --- |
| **撤销** | 还没生效的申请 | `pending → withdrawn` | 申请人（只能撤自己的） |
| **驳回** | 还没生效的申请 | `pending → rejected` | 审批人（只能驳别人的） |
| **恢复** | 被否掉的**新增申请** | `rejected`/`withdrawn` → `pending` | 放回队列，数据一个字不动。**只对新增开放** |
| **回滚** | 已经生效的**数据** | `applied → reverted` | 把改动改回去 |
| **重新应用** | 被回滚的**数据** | `reverted → applied` | 把改动再写回去 |

「恢复」在审批轴，「重新应用」在数据轴。不叫「重做」：这一页上已经有「撤销」了，撤销/重做那一对会让人以为它俩相反，而它们根本不在同一根轴上。状态上互斥——被驳回的 `data_status` 是 `unwritten`，满足不了重新应用的起点；回滚过的 `review_status` 是 `approved`，满足不了恢复的起点——但两者**可以先后发生在同一条记录上**（驳回 → 恢复 → 批准 → 回滚 → 重新应用），所以时间/操作者各占一组列。

（回收站里那个把删掉的记录捞回来的按钮叫**还原**——Windows 回收站用的就是这个词。它不是一次审批动作，而是**新提一条 `action=restore` 的申请**，照样要审批。）

**但只翻状态不够。** 原记录的 `created_duid`、`created_at`、`reason` 属于**原操作者**——"张三上午十点因为客诉改了价格"，不能拿来表示"李四下午三点把它撤了"。因此每一次审批都另存自己的操作者、时间与理由。

**每一次审批追加一条事件，不往列里塞。** `base_audit_approvals` 只追加不修改：

```
base_audit_approvals
  audit_id   指向 base_audits
  kind          approve / reject / withdraw / requeue / revert / redo
  reason        这一次的理由（撤销没有理由，留空）
```

业务列只有三个——**谁和什么时候由公共层的 `created_duid` / `created_at` 顺带填上**，那是每张表都有的系统列。

原先是每种审批动作各占三列（`reviewed_*`、`withdrawn_*`、`reverted_*`、`reapplied_*`、`requeued_*`，共 14 列）。放弃它有两个理由：

- **只记得住最后一次。** 一条记录可以回滚 → 重新应用 → 再回滚，第一次回滚的时间和理由就被覆盖了。审计系统丢历史，比字段多严重得多。
- **每加一种审批动作就要加三列。** 加「恢复」那次就加了 `requeued_*` 并压了一次迁移基线；事件表下只是多一个 `kind` 取值。

**不记「提交」事件。** `base_audits` 那一行本身就是提交，`created_*` 已经写着谁在什么时候提的。因此**前台自助改一次数据只有主表一行、事件表零行**——它压根没走过审批，不必用一条事件去假装。

**表 `base_audit_approvals`、路径 `audit/approvals`、页面「审批记录」——三层同一个词。**

这张表曾经叫 `base_audit_transitions`，页面叫「迁移记录」。换掉有两个理由：中文的「迁移」在这个库里已经是数据库 migration 的固定译法——建库脚本、迁移基线、`test:database-migrations` 说的都是那个，`sql.mts` 里甚至有一张真的「迁移记录表」；而 transition 这个词只活在代码里，与菜单、页面上的说法从来对不上，读的人得在两套词之间来回换算。

随之改变的是定位：这里记的是**审批过程**，不是状态机事件。六种动作都是这套审批系统提供的处理手段，撤销、回滚、重新应用也在其中——它们发生在批准之后，但仍属同一套流程，与「批准」「驳回」并列在同一张表上才看得出一条记录的完整经过。

**`kind` 里的 `approve` 只是六种动作之一**（中文「批准」），与表名说的「审批」不是一回事。中文这两个词分得开，英文 approve / approvals 同源，看 `kind` 的取值时不要按词形去推断范围。

审批页列表上那一列叫「最近审批」，点开就是「审批记录」，两处对得上。

它有两个入口：审计记录页行上的一个弹窗（带 `audit_id`，只看这一条记录的经过），以及「审计管理」分组下单独的一页 `/panel/admin/base/audit/approvals`（按操作者或按动作筛全站——查「上周谁批了什么」「谁回滚过东西」在这里比在主表里翻方便）。这一页**只读**：事件只追加不修改，改一条已经发生的审批记录等于篡改证据。因此它不声明 `tableCrud`——那个声明会让公共层自动挂上回收站、还原/彻底删除和整套审批按钮，摆出来只会让人以为审批记录是可以改的。

**`review_status` / `data_status` 保留，当物化缓存。** 筛选「待审批」是这一页最常用的查询，走索引等值最便宜；由事件推导要按记录分组取最后一条，那正是本文一直在避开的形状。真相仍然是事件序列，因此写入顺序是**先追加事件、再更新这两列**：无事务环境下断在中间的表现是「事件在、状态没跟上」，读的时候以事件为准就能自愈；反过来则是「状态改了但没人知道是谁改的」。

回滚与重新应用是同一段代码，只有方向相反：

| | 写回 | 校验当前值等于 |
| --- | --- | --- |
| 回滚 | `before` | `after` |
| 重新应用 | `after` | `before` |

翻转的 UPDATE 带上原状态做条件（`WHERE id = ? AND review_status = ? AND data_status = ?`），并发下只有一个请求能翻成功。

**界面上是两个互斥的按钮，不是一个开关。** 已生效的行只显示「回滚」，已回滚的行只显示「重新应用」——一个按钮两种含义会让人点之前先去看状态列。这需要表格协议支持按行判断动作可见性（`TableAction.visibleWhen`），是一个通用能力，不只审计用得上。状态列本身用带颜色的标签，绿色表示这条变更此刻是生效的。

请求里带上**期望状态**：列表过期时点到的那一条会被拒绝并说明原因，而不是被翻成与按钮字面相反的方向。

### 7.4 多选回滚按倒序逐条执行

界面可以多选回滚，但它只是逐条执行的批量入口，**不是原子的级联回滚**——无事务环境下做不到，也不应假装做得到。

**拆解按倒序（新到旧），装回按正序（旧到新）。** 回滚、驳回、撤销是拆解，批准、重新应用、恢复是装回。这由 §7.2 的值校验直接决定：同一列经历 A → B → C 两次变更后，当前值是 C，只有先撤 B→C（`SET col=B WHERE col=C`）才能接着撤 A→B；装回时当前值是 A，方向正好反过来。建号那三行同理：先有账号才有凭证，拆的时候反着来。多选时按状态分成两组，各自排序后执行。

不涉及同一列的条目彼此独立，顺序对它们无影响；倒序只对同一列的链式变更是必需的。

**逐条独立判定，互不影响。** 某一条因值校验失败被拒绝时，其余条目照常执行，最后返回每一条的结果。不回滚已成功的部分——既无法回滚，也没有必要：每一条回滚本身都是一次可再回滚的变更（§7.3）。

顺序错了的后果只是撤不动，不会写坏数据。这是值校验相对 `updated_at` 校验的又一处好处：它让错误的顺序失败，而不是让它覆盖别人的修改。

## 8. 列表顺序与索引

**执行回滚时必须在实现里按 `created_at` 降序重新排序，不能沿用列表的显示顺序。** §7.4 的倒序是正确性要求，而显示顺序是用户可改的：按表名或操作者排一次序再多选回滚，链式变更就会全部撤不动。值校验保证了这不会写坏数据，但行为会变得莫名其妙——同样几条，按时间排能撤，按别的列排就撤不了。执行顺序必须与显示解耦。

**变更内容一列一行。** 一次操作常常同时改好几列，挤在一行要靠眼睛去找箭头；列表用 `multiline` 显示模式（`pre-wrap` 加三行折叠），改得多也不会撑爆表格。

存储是**两个 JSON 列**：`changes_before` 与 `changes_after`，形如 `{列名: 值}`。

合成一列（`{列名: {before, after}}`）的写法被放弃了，因为它对**读库的人**很不友好：每个列名要写两遍，`"before"` 与 `"after"` 这两个词占掉大半篇幅，而新建记录里 before 全是 null——直接翻表时满屏都是 `{"nickname":{"before":null,"after":"admin1"},"qq":{"before":null,"after":"11"}}`，想看「这次要新增什么」得先在噪音里把 after 挑出来。分开之后一眼就是一份值。

拆开的那个老顾虑是**键集合可能不齐**：按其中一边遍历的回滚代码会静默漏还原一列，而漏掉的那列压根不进 WHERE，值校验也拦不住。解法是拼回内存形状时取**两边键的并集**（`parseAuditChanges`），任何只出现在一侧的列照样成对出现，缺的那一侧是 `undefined`。写入侧也保证对齐：`serializeAuditChanges` 给每一列都写 after，before 只有真是 `undefined` 时才省略——而修改那一支的前值来自行上，最坏也是 `null`，照写不误。

唯一 before 为空的是**新建**：`changes_before` 是 `{}`，空对象本身就说清了「这一行之前不存在」。而新建的批准/驳回根本不读 changes（`applyInsertTransition` 自己处理），漏不着。

比对、显示、写回这几段代码看到的仍是成对的 `{before, after}`，转换只发生在读写库的那一处。

**三个筛选都不预设默认值。** 「待审批」当过默认值（理由是进这一页最常做的事是处理积压的申请），但它把这一页从「变更记录」悄悄变成了「待办列表」：刚提交完想确认记下来没有，翻半天以为没记。真要处理积压，选一下筛选也只是一步。页面因此叫「审计审批」——审批是它的主要用途，查历史是次要的。

「全部」用显式哨兵值 `all`，不用空串：空串在 antd 的 `Select` 里等于「没有选中」，选完下拉框会显示成空白；顺带让 URL 自解释——`review_status=all` 比 `review_status=` 一眼看得懂。

默认值仍然要**由服务端认**（现在三个筛选的默认值都是 `all`）：客户端首次请求发出时还没带上查询默认值——它拿到 schema 之后才填进查询状态，而那一步刻意跳过了重新请求（避免首屏两次请求）。只在字段上声明 `defaultValue` 的话，下拉框显示「待审批」而列表是全部。另外可按数据表、记录 ID 与操作原因关键字筛选——原因是人写的自由文本，走模糊匹配，`%` 与 `_` 直接当通配符用（转义要 `ESCAPE` 子句，三种方言的默认转义字符不一致，为一个搜索框引入那套规则不划算）。关键字匹配的是提交时填的「操作原因」，审批意见与回滚理由各有自己的列。

列表**默认按 `created_at` 降序**，与项目现有 CRUD 一致（例如 `server/routes/base/api/panel/admin/base/users.mts` 的 `orderBy: id DESC`）。审计列表最常看的是"刚刚发生了什么"；升序分页还会因为新记录不断插入头部而让每页内容错位。用户可以自由改排序、筛选和分页，不影响回滚的正确性。

索引：审计查询几乎总是"某个范围内按时间倒序"，因此除了归属列本身，还需要 `(owner_tid, created_at)`、`(owner_bid, created_at)`、`(owner_uid, created_at)` 这类复合索引；只有 `(owner_tid, deleted_at)` 的话排序还要再排一次。

## 9. 可见性

审计记录带有完整的归属字段，因此直接适用前置需求 §4.2 的规则，不需要额外设计：

| 角色 | 能看到的审计范围 |
| --- | --- |
| `platform_admin` | 全部 |
| `tenant_admin` | 本租户 |
| `branch_admin` | 本分站 |
| `user` | 以自己为作用账号产生的记录 |

普通用户能看到自己的变更历史，是这个设计的自然结果，也是有用的。

**回滚权限单独收窄**：仅 `platform_admin`、`tenant_admin`、`branch_admin` 可以回滚，且只能回滚自己可见范围内的记录。普通用户只能查看。

实现上，审计接口挂在 `panel/admin` 下，那一层的角色门（`server/routes/base/api/panel/admin.mts`）已经把非管理员挡在外面，回滚因此天然受限；管理员之间的范围差异由公共层的归属判定收敛，接口里不再叠加条件。**面向普通用户的「我的变更记录」页面尚未提供**，见 §14。

## 10. 保留期

审计表只增不减，必须有保留期，规则与 `sms_messages` 一致：

- 由站点设置里的「审计保留天数」控制（`site-settings.auditRetentionDays`），按租户独立，默认 **365 天**，设为 `0` 表示不自动清理，上限十年。
- 到期记录**物理删除**，分批进行且可重入，以系统上下文运行（`purgeAuditRetention`）。
- 触发方式：本项目没有调度器，因此 Node 进程启动时跑一次、之后每 6 小时跑一次。漏跑一轮只是记录多留一会儿。Workers 部署没有常驻进程，要改用 cron 触发器调用同一个函数。
- 保留期只能由 `platform_admin` 修改——租户管理员能缩短自己的审计保留期，等于给了销毁证据的手段。

## 11. 操作原因与审批（已实施）

### 11.1 每次人工修改都要说明理由

审计现在记下了"谁在什么时候把价格从 100 改成 50"，但**没记为什么**。取证时前者的价值远低于"……因为客诉退款，工单 #1234"。`reason` 是让审计从日志变成证据的那一列。

因此提交修改时弹出**操作原因**输入框，内容写进审计记录。

**不能全量强制。** 改个昵称也要写原因，人会填"1"、"。"——**垃圾原因比没有原因更糟，它给了假的可信度**。只对敏感操作要求，清单复用 `AUDITED_COLUMNS` 的结构再标一个 `requiresReason`。

原因跟着**一次操作**走，不跟着单条语句走：一次更新命中多行会产生多条记录，它们共享同一个 `operation_id` 与同一条原因。

**原因走请求头 `X-Change-Reason`，不走请求体。** 删除接口的请求体是一个 id 数组，塞不进字段；用请求头对所有请求形状都统一，业务路由也完全看不见它——不用改签名，也不会误把它当成业务字段。头部只能放 ASCII，因此客户端 `encodeURIComponent` 后再发。

前端**每一条会写库的提交路径**都要带上，一处漏掉那次操作就没有理由：

| 路径 | 怎么收集 |
| --- | --- |
| 编辑抽屉（PUT） | 表单末尾追加 `changeControlColumn()`，提交时摘出去改走请求头 |
| 行动作表单、工具栏动作表单 | 同上 |
| 删除（单条 / 批量） | 确认框里带输入（`modalConfirmWithReason`） |
| 多选动作（回滚/恢复、回收站还原） | 同上 |
| 行简单动作、工具栏简单动作 | 同上 |
| 配置表单（`FormPage`）的保存与动作 | 注入 `changeControlField()`，同样摘出去走请求头 |

**控件只出现在 `/api/panel/admin/`**，与审批的适用范围同一条线（§11.2）。由服务端按请求路径注入标志，前端据此决定问不问原因——不是前端自己判断路径。审批页自己的动作（撤销、批准、驳回、回滚）走 `runSystemSql`，压根不经过审批门，但操作原因仍要收：它会写进审批意见、回滚理由或恢复理由。

- 登录与注册页压根不产生审计记录（新增不留痕，§3.2），要一条变更理由没有意义；
- 个人中心与账户中心是用户处置自己的数据，改个昵称还要写「变更理由」是荒谬的。这些操作**照常留痕**，只是不问理由。

**操作原因只在确认框里问，不占表单一格。**「立即生效」废除之后它没有同伴了，而它本来也不是被编辑对象的字段——放进表单会跟着「还原默认」一起被重置，也会让「改了什么」的比对多出一项噪音。见下文「变更说明在确认框里问，不占表单」。

**故意不带的四处**，因为它们都不产生审计记录：新增（§3.2 新增不留痕）、连通性测试（只读）、下载签名（只读）、上传签名（新增）。

目前**不强制**：留空也能提交。哪些操作强制填由服务端另行判定，清单尚未确定。

### 11.2 适用范围：只有 `/panel/admin`

审批**只适用于管理后台**（`/api/panel/admin/**`）。个人中心与账户中心（`/api/panel/user/base/me`、`/api/panel/accounts/**`）的自助操作——改昵称、绑邮箱、换主邮箱——**不走审批**：它们是用户对自己数据的处置，最不敏感，也最需要立即生效。这些操作仍然照常留痕，只是不排队。

范围边界正好落在既有的角色门上：`server/routes/base/api/panel/admin.mts` 就是 `/panel/admin` 的入口守卫，审批范围与它同一条线，不需要另建一套路径规则。

### 11.3 后台的修改一律进队列

一度有一个「立即生效」勾选框，管理员勾上就跳过审批直接写库；它已经删掉，见下文
「『立即生效』已废除」。有权限的角色（`platform_admin`、`tenant_admin`、`branch_admin`，
与 §9 的回滚权限一致）改为在待审批提示里点「批准并生效」。

### 11.4 审批与审计**用同一张表**

设计过程中一度判断这两者必须分表，理由是"审计不可修改、审批必须可改，一张表满足不了"。**这个判断随着 §7.3 的翻转模型作废了**，两条反对理由都不再成立：

| 当时的反对 | 现在为什么不成立 |
| --- | --- |
| 审计不可改，审批要能改 | 状态本来就要来回翻（applied ↔ reverted），各组时间/操作者列已经在记"谁什么时候因为什么改了状态" |
| 审计按行记，审批按操作走 | `operation_id` 解决了：一次操作的多条写入共享它，批准就是把这一组一起应用 |

第二行顺带解掉了那个卡住审批的问题——**多条语句构成的业务操作现在能整体审批**，不必把审批范围限死在单语句操作上。

### 状态拆成两列：审批状态 + 数据状态

一列装不下这两件事。**「没人批过」和「批过了」都让数据生效了，但不是同一个事实**：前台自助与路由显式声明的机器写入根本没进过队列，把它们记成「已批准」，等于告诉看的人有个不存在的审批人点过头。

| `review_status` | 含义 |
| --- | --- |
| `none` | 无需审批：用户自助（§11.2），或路由显式声明的机器写入（建号收尾、回收站恢复） |
| `pending` | 已提交，等审批 |
| `approved` | 审批人放行 |
| `rejected` | 审批人否掉 |
| `withdrawn` | 申请人自己收回 |

| `data_status` | 含义 |
| --- | --- |
| `unwritten` | 从未写入：待审批、被驳回、被撤销的申请都停在这里 |
| `applied` | 已生效 |
| `reverted` | 生效过又被回滚，数据已改回去 |

```
提交 ──┬─ 无需审批 → review=none    + data=applied
       └─ 进队列   → review=pending + data=unwritten
                        ├─ 批准 → review=approved  + data=applied ──回滚──▶ data=reverted
                        ├─ 驳回 → review=rejected  ──恢复──┐        ◀──还原──
                        └─ 撤销 → review=withdrawn ──恢复──┘
                                                          └──▶ 回到 review=pending
```

**两列正交，这正是它们必须分开的原因。** 回滚与重新应用只动 `data_status`，「是谁放行的」原样留着；恢复只动 `review_status`，数据一个字不写。合成一列时做不到：重新应用只能挑一个目标状态，而那个状态里混着审批信息——一条自助操作被回滚再重新应用，就会凭空变成「已批准」，记录被自己的状态机洗白。

动作因此也按轴分：批准 / 驳回 / 撤销 / 恢复看 `review_status`，回滚 / 重新应用看 `data_status`。一条「无需审批」的自助操作照样能回滚，而它压根没有可批准的申请。

**「恢复」只对被否掉的新增开放。** 修改、删除、还原被驳回了，重新提交一次就是了——两条路做同一件事，而多一条路就多一处状态要想。新建不一样：重来要把整张表单再填一遍，而那一行还带着内容躺在回收站里，捞回来比重填便宜得多；何况建号写三行，从回收站一张表一张表地捞会漏掉凭证，账号看着正常却登不进去。

**恢复一条被否掉的新增，要把行也放回待审批的样子**：从回收站捞出来（`deleted_at = 0`），`queued_at` 重新写上**此刻**——它记的是「什么时候进的队列」，而这条申请正是现在才回到队列里的；当初提交的时刻另有去处，记在这条记录的 `created_at` 上。没有这条路的话，驳回错了只能去每张表的回收站里一行一行捞，而建号写三行：捞回账号那一行却漏掉凭证，账号看着正常、人却登不进去。审批页按 `operation_id` 分组，天然一起处理。

**审批与回滚各用一组字段，不能合并。** 一条记录可能先被批准、之后又被回滚；合用一组的话，回滚信息会把"谁批准的"覆盖掉，而审批人恰恰是事后最想查的东西之一。

三组字段的分工见 §7.3 的表。要点是：**每一种审批动作写自己那一组**，谁都不会被别的动作覆盖。

两条配套规则：

- **`pending` 可改，终态不可改。** 申请人改了重交就是改这一行。这不违反"审计不可修改"——尚未发生的事没有历史可言，`pending` 记的是意图不是事实。一旦离开 `pending`，两份值与 `created_*` 就冻结，只剩两列状态与各自的时间/操作者还能动。
- **保留期只清理终态。** `pending` 永不自动删除，否则一条挂着的申请会因为超期而凭空消失（§10）。

### 11.5 实现落点

`runOperation` 判定要走审批时，把记录写成 `pending`、**一条数据都不动**，然后抛 `PendingApprovalError`。抛异常的好处是不用改任何路由——异常一抛，后面那句 `return apiMessage(c, 200, '已保存')` 根本不会执行。

**但响应不能只靠异常收口。** Hono 的 `compose` 在**每一层** `dispatch` 里就地 catch 并交给 `onError`，异常在深处就被转成 500 了，根本传不到外层中间件的 `await next()`；业务路由自己的 `try/catch` 也可能把它吞掉。因此真正的判据是请求上下文里的标记：

```ts
if (c.get('pendingApproval') && c.res.status !== 202) {
  c.res = await apiMessage(c, 202, '修改已提交审批，通过后才会生效', …);
}
```

两处细节都是踩出来的：必须**直接改写 `c.res`**（响应已被下游 finalize，`return` 出去的新响应会被 compose 丢弃），并且**不能看当前状态码**（此时往往已经是 500）。只要记成了待审批，数据就一定没动，任何别的响应都是错的。

受管表写入被 `try/catch` 包住的那几处也逐个改成重新抛出 `PendingApprovalError`，让提示准确；但**正确性不依赖这一点**——上面那道兜底才是保证。

**同一个人对同一条记录再次提交时，覆盖他自己那条待审批记录**，不管新提交是继续排队还是勾了「立即生效」。

- 继续排队：否则队列里堆着同一个人对同一行的多份申请，审批人只能逐条批过去，而先批的那几条会因为值校验（§7.2）全部失败——它们的 `before` 是更早的值。
- 立即生效：他已经自己把这一行改掉了，原先那条申请随之作废，留着就是一条谁也批不动的孤儿记录。

两种情况都是同一件事的最新版本。按操作者过滤：两个人各自对同一行提出的修改是两件事，各排各的队。被覆盖成 `applied` 时不写 `reviewed_*`——立即生效不是审批，不该伪造审批记录。

批准（`pending → applied`）与恢复（`reverted → applied`）走同一条代码路径：两种情况下行上都还是 `before`，都要写成 `after`。驳回不碰数据，只落状态。因为 `operation_id` 把一次操作的多条写入归到一组，**多语句操作可以整体审批**，不必把范围限死在单语句上。

## 13. 验收标准

- 白名单内的表发生业务字段变更时产生一条记录；只改动排除列（`last_seen_at`、`expires_at` 等）时不产生记录，且不发生额外读取。
- 每一张表都出现在 `AUDITED_TABLES` 或 `UNAUDITED_TABLES` 之一；新增表未登记时测试失败。
- 白名单外的表任何写入都不产生记录。
- 软删除与恢复各产生一条记录，`action` 分别为 `soft_delete` 与 `restore`。
- 新增与物理删除不产生记录。
- `update` 记录里只包含实际变化的列；提交未改动的字段不产生噪音，全部未变化时不产生记录。
- 凭证列的值不出现在审计列表与详情的接口响应里，只显示"已变更"；回滚这些列仍然有效。
- 代用户操作产生的记录中，`created_duid` 是客服的 device-user，`owner_uid` 是被代查的账号。
- 新增记录不产生审计条目。
- 回滚 `update` 后字段恢复原值；回滚 `soft_delete` 后记录回到未删除状态；回滚 `restore` 后 `deleted_at` 写回**原时间戳**而不是当前时间。
- 要还原的列在变更之后又被改过时，回滚被拒绝且数据不变。
- 同一行上与本次变更无关的列被改过，不影响回滚。
- 心跳列（`last_seen_at` 等）的更新不影响回滚。
- 回滚不产生新记录，原记录 `data_status` 变为 `reverted`；再次回滚同一条被拒绝。
- 同一列的两次连续变更，多选后按倒序回滚全部成功，数据回到最初值。
- 同样两条按正序回滚时第一条即被拒绝，数据保持不变。
- 多选中某一条被拒绝时，其余条目照常回滚，结果逐条返回。
- 审计记录不能被修改或删除，接口层没有对应入口。
- 列表默认按时间降序；改用其他列排序后执行多选回滚，仍按时间降序执行并全部成功。
- `tenant_admin` 只能看到并回滚本租户的记录；`branch_admin` 限本分站；普通用户只能查看自己的。
- 超过保留期的记录被物理删除，未到期的不受影响。
- 审计写入失败时，业务写入一并失败。

## 列的顺序

管理后台列的先后与 `prisma/base.prisma` 里 `base_audits` 的字段顺序**一致**：两处对照着看时不用来回找。不是每个字段都显示（`operation_id` 就不显示），因此比的是**相对次序**而不是完整相等；计算列排在它所依据的那一列的位置上（`summary` 之于 `changes_before` / `changes_after`）。审批的经过不占列：列表上只显示**最近审批**一行（最后一条事件），完整时间线在详情页——横着摆十几列时，一条记录最多经历两三种审批动作，其余格子永远空着。

由 `test:change-audit` 守着——加了新列忘了对齐会直接报错。

## 用词：撤销 / 回滚

「撤销」和「回滚」两个词太近，读的人分不清哪个会动到数据。因此按**对象**命名，并且回滚就叫回滚：

| 状态 | 标签 | 谁做的 | 数据 |
| --- | --- | --- | --- |
| `pending` | 待审批 | 申请人提交 | 没动 |
| `applied` | 已生效 | 批准或直写 | 已改 |
| `rejected` | 已驳回 | **审批人**否掉 | 从未动过 |
| `withdrawn` | 已撤销申请 | **申请人**自己收回 | 从未动过 |
| `reverted` | 已回滚 | 把已生效的改回去 | 已改回 |

`rejected` 与 `withdrawn` 落在同一侧但不是同一件事，因此分开记——追查时「是被否掉的还是自己撤的」是两个不同的结论。

**每一次审批追加一条 `base_audit_approvals`**，不往列里塞：同一条记录会被反复翻面，压进列里只记得住最后一次（§7.3）。

`withdraw` 那一条**没有理由**：撤销是申请人把自己提的东西收回去，不需要向谁交代，界面上也不问——留一格永远是空的，比不留更容易让人以为漏填了。

撤销和审批都从 `pending` 出发，但一个是审批人的决定、一个是申请人自己收回，`kind` 分开记，读的时候一眼分得清那一条是谁做的。

## 「立即生效」已废除

原先表单里有一个「立即生效（跳过审批）」勾选框。现在管理后台的修改**一律进审批队列**，有权限的人在待审批提示里点「批准并生效」。两条路做同一件事，留一条就够，而勾选框那条还得在每个表单里占一格。

`options.immediate` 仍然保留，但只给**路由内部显式声明**的写入用，不再由请求头驱动——请求头能被伪造，而这个开关只应由代码说了算。目前只有一处：建号收尾把 `owner_uid` 指回账号自己——那是创建的一部分，不是人做的修改。

```
删除（软删除）   → 进队列，行留在列表上并标「待审批」 → 批准 → 进回收站
回收站 → 恢复     → 进队列，记录留在回收站里 → 批准 → 回到列表
回收站 → 彻底删除 → 立即执行，且不留痕（§3.0：物理 delete 不审计），且只给超级用户
```

### 恢复为什么也要审批

这里曾经是立即生效的，理由是「回收站得是后悔药，删错一条不该等审批人有空才救得回来」。

那个理由站不住：**删除本身就要审批人签过字**，所以删的时候已经等过一次了，「删错了」不是一个随手就能造成的状态。而恢复是把一条**被批准删掉的**记录重新对所有人可见——那是在推翻一个已经做过的决定，正是审批要管的事。真要救急，超级用户可以自己批自己（§13.5），一步就走完。

多条一起选时共用一个操作号并 `defer`：第一条就抛异常的话，后面几条根本不会进队列，用户看到「已提交审批」却只提交了一条。

## 变更说明在确认框里问，不占表单

变更说明不是被编辑对象的字段，混在表单里既容易被当成要填的内容，也会跟着「还原默认」一起被重置，还会让「改了什么」的比对多出一项噪音。改到提交前的确认框里问，和「将保存以下修改」列在同一个框内。

- **必填**：一条写着空原因的记录和没有记录差不多。填之前确认按钮一直禁用，而不是点了再弹一个「请填写原因」——后者要人多点一次才知道。
- **没改动就不问**：一次什么都没变的提交没有「原因」可言，摆个必填框只会逼人瞎写。这时只确认「当前未修改，仍要提交吗？」。
- **撤销自己的申请不问**：那是把自己提的东西收回去，不需要向谁交代。批准与驳回要问——那是给申请人的答复，记进审批意见。

## 待审批的修改要看得见、也动得了

提交后进了审批队列，界面上却什么都看不出来——显示的仍是旧值，用户以为没保存成功，于是再改一次，队列里堆出第二条。因此：

**设置页**：表单顶部列出这一行还没落地的修改（逐条写清「改了什么 → 变成什么」），并给两个动作。

**所有 TableCRUD 表格**：有修改在等审批的行标一个「待审批」，行上多出同样两个动作。标记列排在最前——一行有没有在等审批，是看这一行时最先要知道的事；没有任何待审批的行时这一列不出现。

两个动作的权限不同：

- **批准 / 驳回**只对有审批权的人出现（`APPROVAL_SKIP_ROLES`）。看不到按钮只是不引诱人去点，服务端另有一道校验。
- **撤销申请**只在「这条是我自己提的」时出现，不设权限门槛：撤销的意思是把自己的申请收回去，替别人撤等于替别人做决定，那是驳回该干的事。

这两个动作由 `handleTableCrudAction` 统一处理，和回收站的恢复/彻底删除同一条路径。注意它**不能只在回收站范围里调用**——回滚与立即批准发生在正常列表上，只在 `deleted` 范围里调的话它们永远走不到，表现是「API route did not return a response」。

**批准配置类修改后必须让配置缓存失效。** 批准是直接把值写回表的，绕过了 `configStore` 那条会顺手清缓存的路；不清的话批准完页面还显示旧值，看起来像批准没生效。失效用代次号而不是按对象身份删——数据库句柄常被 `withDatabaseActors` 包一层，包出来是新对象，按身份删根本命中不到。

## JSON 列只记差异

JSON 列的变更**只记变了的那几个键**，不抄整块值。改一个页脚而把整个站点配置抄进审计，「改了什么」等于没答，记录也会随配置一起膨胀。

回滚时按键**合并**回去而不是整块覆盖：先读当前值，确认这条记录提到的每个键都还停在这次审批前那一侧（别的键随便别人怎么改），再把这几个键写回去，并用**读到的整值**作为并发条件——读改写之间被人插一手，条件就匹配不上，写入落空。

这换来一个原先做不到的能力：中途被别人改过的其他键不会被回滚一起抹掉。旧的整块覆盖要么把它抹掉，要么因为整列对不上而根本撤不了。

合并时按当前值的键序重建，只替换提到的键：JSON 的键序本无语义，但保持稳定能让存储和后续 diff 都可读。

### 脱敏在展开之前

**整列隐藏的列绝不逐键展开。** `password` 也是 JSON 列，展开就等于把 `password.hash` 明明白白写在页面上——隐藏与否先在最外层定死。

`base_configs.value` 因此从「整列隐藏」名单里移出：原先它被整列藏掉的理由是「整块 JSON 里混着 OIDC 客户端密钥，无法逐列区分」，逐键之后这个理由不成立了，密钥那几个键单独藏，页脚、联系邮箱这些照常可见。

JSON 里的键名列不全（各处配置自己定），所以除了同名列的名单，再加一条按名字判断的兜底：驼峰先折成下划线，名字里带 secret / password / token / credential / private 的一律当敏感处理。宁可多藏也不少藏——藏错了只是看不到一个无关紧要的值，漏藏就是把密钥写进了可见页面。

## 记录操作来源

每条审计记录都带上 `request_hostname` 与 `request_path`：这次操作是从哪个域名、哪个接口发起的。

多站点共用一套代码，同一张表在不同域名下都可能被改；只记「改了什么」而不记「在哪改的」，事后追查时分不清是哪个站点的管理员动的手。

**两者都由服务端自己看到，不听客户端的。** 路径记的是**去掉后缀的接口路径**（`/api/panel/user/base/me` 而不是 `/api/panel/user/base/me.php`）——`.php` 是站点可配的接口后缀，记原样会让同一件事在审计里长出好几种写法，按路径筛选也就筛不干净。记接口路径而不是页面路径：页面路径要靠 `referer` 推断，那是客户端说什么就是什么，写进审计等于给伪造留了口子。

解析不出地址时记空串，不让它把整次写入带塌——留痕是为了留下证据，为了一个「从哪来」的字段而使操作失败是本末倒置。

## 13.5 超级用户与四眼原则

**只有超级用户能自己批自己。** 其余有审批权的人（`platform_admin`、`tenant_admin`、
`branch_admin`）只能批**别人**提交的申请，自己提的要另一个人来看一眼。

在这之前审批不是关卡：进得来后台的三个角色都能批，提交人自己点一下批准就过了——
留痕仍然完整，但拦不住任何人。加上这道判定之后它才第一次成为关卡。

名单在 `.env` 的 `SUPER_USER_IDS`（`base_users.id`，逗号分隔）：

- **未设置 = `1`**，也就是每个站点的初始管理员。不给默认值的话，新装的站点没有任何人
  是超级用户，主人提交的第一个修改就没人能批，系统当场卡死。
- **显式设成空串 = 没有超级用户**，任何人都要双人复核。那是主人主动做的选择。
- 它是**每个站点各自的 1 号用户**：`.env` 每台机器一份，而每个站点有自己的库。

放 `.env` 而不是数据库：**拿到数据库的人不该能把自己写进这份名单**。这与救援工具箱同构
——高危能力一律要求带外授权。用 `id` 而不是 `key`：key 是雪花，每次重建库都要有人去查
一串 19 位数字粘进 `.env`，大概率没人会配，于是四眼永远没启用。

**比对必须落到人，不是设备。** 审批记录里存的是 `created_duid`（设备用户）；直接拿它和
当前请求的 duid 比，同一个人换台设备就成了「两个人」，四眼原则当场失效。因此要多查一层
`base_device_users` 落到 `user_id`。

**撤销不受这道判定管**：那是把自己提的东西收回去，不是替谁做决定。回滚也不受管——
它动的是已经生效的数据，另有自己的权限门。

**彻底删除只给超级用户。** 它是全站唯一不可逆、也不留痕的操作（物理 `delete` 不审计，
§3.0），因此同样要求带外授权。

## 13.6 一行上同时只允许一种动作的申请

同一行上，队列里最多只有一种动作在排队。同一个动作**重新提交**是「重说一遍」，照旧覆盖上一条；换一个动作就是叠加，一律 409（`PendingLockError`）。

### 别人提的申请把这一行整个锁住

上面那条挡的是「叠加」，不看是谁提的。**再狠一层：只要队列里挂着一条别人提的申请，这一行
什么动作都不给做**——连「同一个动作的重新提交」也不行。

理由是署名：重新提交会**覆盖**原来那条记录，而记录上的 `created_duid` 还是原来那个人的。
换成别人来重说，审批人看到的就是一条署着甲的名、写着乙的字的申请。改一份还没生效的新建
（下面那条例外）同理——那份草稿是别人的。

自己提的照旧放行：撤了就能接着改，那是同一个人对同一件事改主意。

**比到人，不比到设备。** 记录里存的是 `created_duid`（设备用户），直接拿它比的话，同一个人
换台设备就成了「两个人」，自己反倒被自己锁住。与四眼原则（§13.5）用同一把尺子。

**认不出「我是谁」就不判这一层**，退回按动作判。没有登录身份的只有内部路径——迁移、种子、
模块级调用；把它们一律当成「别人」的话，一条待审批记录会把这一行对系统自己也锁死。人际锁
管的是人与人，没有人的地方它无话可说。真实的后台请求必然有 `currentUser`。

### 一个业务对象横跨几张表时，锁要认得出「这一套」

行锁按 `(表名, 行号)` 判，可一个用户是三行：`base_users` + `base_user_credentials` +
`base_user_profiles`。管理页上编辑「一个用户」，只改昵称时压根不生成 `base_users` 的语句，
于是别人挂在账号那一行上的申请拦不住这次修改——从页面上看是同一条记录，锁却只锁住了其中
一张表。

由路由声明身份行（`OperationOptions.lockRows`），框架不猜：「哪几行算同一套」是业务知识。
`users.mts` 声明 `[{ table: 'base_users', rowId }]`，于是改资料、改凭证、删除都要先过账号
那一行的锁。靠 `operation_id` 反查也能连起来，但那连的是「曾经在同一次操作里被一起写过」，
批量操作会把毫不相干的行也串上。

### 界面：按钮不藏，点进去说清是谁

被别人锁住的行**照常显示编辑按钮**，点进去抽屉顶部一条警告：「乙管理员提交的「修改」申请
正在等待审批，这条记录暂时不能动——要先由审批人批准或驳回。」藏按钮省事，但看的人只知道
「不能改」，不知道该去找谁。那句话由服务端算好整句发下来（`_pending_lock`），与真去保存时
`PendingLockError` 给的是同一句——提前说和事后说必须一致，否则读起来像两条不同的规则。

**唯一的例外：改一份还没生效的新建。** 那一行带着 `queued_at`，谁也看不见，改它没有任何对外后果——因此**直接写进去，不另开一条申请**，并把那条新建记录的 `changes_after` 刷新成最新内容（审批人看到的必须是他将要批准的那一份）。再排一次队只会让他面对两条记录，还得自己在脑子里合并出「批准之后是什么样」。「谁改过草稿」不单独留痕，落在那一行的 `updated_duid` / `updated_at` 上。

界面上跟着收按钮：编辑在三种情况下出现——这一行干净、挂着的正好也是修改、以及挂着一条还没生效的新建；删除与还原发的是别的动作，只在这一行干干净净时出现。

**为什么这么严。** 表面理由是审批人要做心算——一行同时挂着「要不要有它」和「把它改成什么样」，得合并几条记录才知道批准之后是什么样，而「驳回新增 + 批准修改」这类组合根本没人想要（那条修改作用在一行已经进了回收站的记录上）。

更硬的理由是**请求本身说不清动的是哪一件**：行上的动作发出去是 `?action=withdraw-pending`，只带行号，不带动作。一行同时挂着「修改」和「删除」时，界面只显示得出一对按钮（标签取最要紧的那一种），点「撤销删除」却会把那条修改一起撤了。要么把动作也编进每一个请求里、每一种动作各给一对按钮，要么根本不让这种局面出现——后者简单得多，代价只是「先撤销再改」。

**代价。** 想把一条已经在排队的申请换成另一种动作，要先撤销。改自己刚提的修改、改一份还没生效的新建，都不受影响。

```
干净的行       → 编辑 / 删除
挂着修改       → 编辑 / 撤销修改 / 批准修改      （删除收起来）
挂着新增       → 编辑 / 撤销新增 / 批准新增      （改草稿立即生效，删除收起来）
挂着删除·还原  → 撤销X / 批准X                   （编辑与删除都收起来）
```

## 13.7 新增怎么走审批

新增没有前值可比，因此走另一套：**行照写进库，但先不让人看见**。

| 步骤 | 做了什么 |
| --- | --- |
| 提交 | 先记一条 `action=insert`，再把行写进去，`queued_at` 记下进队列的时刻 |
| 待审批 | 行在库里，但 `queued_at != 0`，所有正常查询都看不到它（见 column-naming.md） |
| 批准 | `activate()` 把 `queued_at` 归零，这一行才开始存在 |
| 驳回 / 撤销 / 回滚 | **软删除**，并把 `queued_at` 一并归零 |

**upsert 的 INSERT 分支也算新建。** 设置页写配置、用户管理里给一个还没有资料行的账号填昵称，走的都是 `INSERT ... ON CONFLICT DO UPDATE`：行不存在时它是一次新建。审计那一层按修改的形状记——读不到前值就当作「什么都没改」，于是语句被直接执行掉。这曾经是一处真的漏洞：**每一项配置、每个账号的第一份资料，第一次保存既不进队列也不留痕，从第二次起才正常。** 现在由操作层查一次冲突条件来定走的是哪一支（它本来就要读那一行的前值，不多一次查询），INSERT 那一支照常记成待审批的新建。

页面那一侧跟着放开一处：`configRowId` 用 `queued: 'all'` 查行号——第一次保存写下的那一行带着 `queued_at`，普通查询看不见它，不放开的话「有 N 项修改正在等待审批」这条提示会整个消失，保存完看到的是默认值，而且没有任何地方告诉你它在排队。

**批准之前核一遍内容：你批的必须就是你看到的。** 批准修改早就有这道校验（每一列的当前值必须还等于记录里的前值，§7.2），批准新增原先没有——`activate()` 只把 `queued_at` 归零，不看内容。于是待审批期间那一行被别处改过的话，审批人看着「newguy / 普通用户」点了批准，生效的却是「hijacked / 平台管理员」，而记录上仍然写着他看过的那一份。

只核记录里写下的那几列：归属与时间戳本来就不进 `changes`，它们在等待期间被公共层动过是正常的。核不上就拒绝并说明原因，那一行留在待审批里。

**比较必须先归一，四处都要。** BIGINT 各驱动返回的类型不一（number / string / bigint），一律按字符串比；数组与对象按 JSON 比（`String(['a','b'])` 得到 `a,b`，两个不同的数组会撞上）；而 JSON 值**必须先按键名排序**——行上读回来的是文本，JSON 列在 PostgreSQL 上落成 `JSONB`，它按自己的规则重排键，回读到的字符串与写进去时的不是同一串。不排的话，凡是带 JSON 列的新建（`password` 就是一个）在 PostgreSQL 上每次批准都会被判成「内容与申请不一致」，而在 SQLite 上一切正常，只有上线才发作。别的动作不核——驳回与撤销是把它拿掉，回滚与重做动的是已经生效过的东西。

**布尔要单独拉平，而且只在申请那一侧是布尔时才拉。** 核对用的查询一律 `CAST(… AS TEXT)`，而布尔在各方言里读回来长得不一样：SQLite、MySQL、D1 存 0/1，转文本得 `'0'`；PostgreSQL 存 true/false，转文本得 `'false'`；申请里则是 JSON 的 `false`。不拉平的话 `String(0)` 是 `'0'`、`String(false)` 是 `'false'`，**凡是带布尔列的新建一律批不动**——批准报「内容与申请不一致」，指向一个根本不存在的篡改；驳回与撤销倒是照常，于是那条申请成了死结，数据永远生效不了。`global_cloud_object_storage_buckets.path_style` 上真的发作过。

拉平只按**申请那一侧的类型**来：申请里是布尔，才把行上读回的 `'0'` / `'false'` 当布尔解读。不能无条件把 `'true'` 归一成 `'1'`——那样一个存文本 `'true'` 的列与一个存 `'1'` 的列会被判成相等，而它们本来是两个不同的值。申请里的类型是可信的，它来自 JSON。

**新建记录的 `changes_after` 写的是「批准之后这一行会是什么样」**（`changes_before` 是 `{}`）：待审批的行带着 `queued_at`，在任何正常列表里都看不见，让审批人「自己去看那一行」根本行不通，等于闭着眼睛点批准。

**明文密钥**（`client_secret`、`dsn` 那几个）一个都不写进来——这比在显示时脱敏更彻底，库里根本没有，不会在一张保留期一年的表里躺着。归属列、时间戳与 `key` 也不写：前两样每一行都有，`key` 已经是「记录标识」那一列。

`password` 是例外，**照抄**：它存的本来就是摘要，抄进记录里抄的也是摘要，不是口令。换到两件事——批准前核得出「这一行的凭证还是不是提交时那一份」（不抄的话，待审批期间有人把哈希换掉，批准时发现不了），以及审批人看得到**密码规律**：`password（规律）：空 → ULLDDDDD`。「这个新账号的密码是 8 位纯数字」是一条能据此驳回的理由，而规律既不是口令也推不出口令，就是用户管理页上那一列「密码特征」。整块 blob 仍然不露，salt 与 hash 一个字都不显示。

`queued_at` 曾经写在这里，理由是「批准落到数据上就是这一列」。当时 `changes` 是一列、前值是提交时刻，读起来是 `queued_at: 1788636234201 → 0`，确实说明了一件事。后来三条支撑一条不剩：前后值分开存之后新建的 `before` 是 `{}`，它显示成「queued_at：空 → 0」，什么也没说；「恢复」改用此刻的时间戳，不再回读它；批准前的内容校验又必须把它排除——它正是那一步要改的那一列。所以现在不写了。

**为什么驳回是软删除而不是物理删除。** 原先是物理删除，理由是「它从未生效过，留着只是
一份没人认领的草稿」。软删除的理由更强：软删除本来就有保留期，被驳回的新建因此在回收站
里待着，看得见、找得回——审批人手一抖驳回了别人半天的录入，那份录入不该就此不存在。

`queued_at` 一起归零，是为了让它成为一条**普通的已删除记录**。留着非零的话，从回收站
恢复出来的行仍然对业务查询不可见，却又出现在管理列表里（那里看得见待审批的行），
成了一个谁也说不清状态的幽灵。

**这一条记录不能交给通用的写回路径。** 内容列的前值记的是 `null`，而行上早就是真实值，
通用路径拿前值当并发条件，第一步就会判成「已被后续修改覆盖」。因此 `applyInsertTransition`
只处理 `queued_at` 那一列。

**定位靠 `row_key` 而不是 `row_id`。** 新建时行还没写进去，自增主键要插进去才知道；
而 key 由 SQL 构造器在建语句时就生成好了，因此「先记录、后写行」这条顺序对新建也成立
（§6.2）。顺带不依赖 `lastInsertRowid`——PostgreSQL 拿它要给每条 INSERT 追加 `RETURNING`。

**是不是人做的新增，由调用方选 `runOperationSql` 还是 `runSql` 声明**，与 update 那边
同一条线。会话、登录挑战、OIDC 码、设备注册、验证码这些机器写入继续走 `runSql`——
把它们一并记下来会把审计表冲爆。代价是漏用 `runOperationSql` 的人工新增会静悄悄不留痕，
守卫拦不住（它分不清人和机器）。

## 13.8 一次操作，一起批准

**审批的对象是一次操作，不是一条记录。** 同一个 `operation_id` 的记录批准、驳回、撤销、
回滚时一起处理——那一列此前全库没有一处在读，这是它的第一个真实用途。

建号是最直接的例子：它写三行——账号（`base_users`）、凭证（`base_user_credentials`）、
资料（`base_user_profiles`，只有填了才写）。只批账号那一行，得到的是「能登录但没有密码」；
只驳回账号那一行，凭证和资料就成了指向不存在账号的垃圾。

两处实现要点：

- **后两行的 `user_id` 要等账号行插进去才知道**，一次 `runOperation` 传不完。因此
  `OperationOptions` 加了 `operationId`（几次调用共用一个操作号）和 `defer`（进了队列
  也不抛异常，让调用方走完三步再收尾）。
- **建号里的凭证与资料写的是纯 `insert` 而不是 `upsert`**：新账号必定还没有这两行，而
  upsert 冲突时走的是 UPDATE，操作层不会把它记成新建——那样三行里就有两行不进队列。

审批页因此显示了「操作号」这一列：同号的记录是一件事。

**一次操作里的几行有先后。** 建号先有账号，才谈得上它的密码和资料；驳回与撤销对新建
而言是物理删行，那是「拆」，必须反着来——先删账号再删它的凭证，中间那一刻凭证指向的
账号已经不存在了。因此「建起来」的动作（批准、恢复）从最早的一条开始，「拆掉」的
（回滚、驳回、撤销）从最新的一条往回走。库里眼下一个外键约束都没有，所以顺序错了也不
报错，但错了就是错了。

## 13.9 自助写入也只作用在已经生效的那一行上

前台自助不排队、立即生效，也不该被后台的待审批申请挡住（那是 §13.6 管的事）。但**目标行
还没生效**是另一回事：`queued_at` 非 0 说明它是一条还没批准的新建，对写的人根本不可见。

不拦的话三件事同时发生：

1. 他看不到结果——那一行仍然不可见，于是**反复改**；
2. 每改一次留下一条 `data_status` 写着「已生效」的审计记录，而外面一个字都看不到——**审计表
   在说假话**；
3. 那条待审批的新建被他改掉了内容，审批人再去批准就撞上「内容与申请里的不一致」（§13.10），
   那条申请成了死结。

因此 `scope === 'self'` 的写入撞上未生效的行一律 409（`QueuedRowError`）。**不挡
`options.immediate` 那种路由内部的机器写入**：建号收尾正是要往自己刚插进去、还没生效的行上
补 `user_id`，挡了它建号就断在半路。

**只拦不说等于把问题换个样子。** 个人中心因此改了两处：待审批的资料行用 `queued: 'all'` 读
出来照常显示（表单里就是等着生效的那一份），页顶一条警告说明它在等审批、这段时间不能改。
藏着不显示的话，用户看到的是「什么都没设」，而库里明明有一行写着管理员填的昵称。

右上角显示的身份不走这条路（`currentUser`），因此还没生效的昵称不会漏到对外显示的地方。

## 13.10 每一次翻面都要求内容还是记录上那一份

§7.2 说的是**修改**：回滚时每一列都要求当前值仍等于记录里的 `after`。新建那一路走的是
另一段代码（`activate()` 只动 `queued_at`，`restore()` 只动 `deleted_at`，都不看内容），
因此要单独说清楚哪几步核、哪几步不核。

**规则：这一行还要继续存在的每一次翻面，都要求它的内容还是记录上 `changes_after` 那一份。**

| 动作 | 核不核 | 为什么 |
| --- | --- | --- |
| 批准 approve | **核** | 第一次让它露面。审批人照着记录上的内容点的头，生效的必须就是那一份 |
| 回滚 revert | **核** | 看着 A 却把 B 下线了；别人对这一行的合法修改会被一起埋掉 |
| 重新应用 redo | **核** | 又一次让它露面。回收站里的行照样收得下修改申请，改一笔再重新应用，放出去的就不是记录上那一份 |
| 驳回 reject | 不核 | 见下 |
| 撤销 withdraw | 不核 | 见下 |
| 恢复 requeue | 不核 | 行放回队列后仍然不可见，后面还要再走一次批准，那一次会核 |

**驳回与撤销不核，是有意留的退路。** 它们把这一行彻底作废——申请结束、行删掉，不留下
任何还要继续用的东西。这两步也跟着核的话，一条内容被动过手脚的待审批新增就成了死结：
批不了（内容不符），也否不掉（同样内容不符），队列里卡着一条谁也收不了场的申请，只能
去数据管理硬删。作废一份被动过手脚的东西，不该被那手脚挡住。

**行已经不在了，对这两步也算成功。** 同一条退路还要再宽一格：撤销与驳回的做法是把那一行
软删掉，影响 0 行时原先报「原记录已不存在」——于是行被别处删掉的申请三条路一起堵死：
批准核不过内容（行不在，核对必然失败），撤销与驳回又找不到行。这两个动作的意思本来就是
「这一行不要生效」，行都没了，结果正是要的那个。不这么算的话，那条申请永远卡在待审批
列表里，还占着 `(table_name, row_key, 0)` 那个位置，**连带这一行以后都不能再提新申请**。

这条路真的走到过：对象存储的 `bindings.mts` 编辑用途时先裸删旧行再插新行，把上一轮还在
排队的那一行物理删掉了，连编三次只剩最后一条能批，前两条谁也处理不掉。那个裸删已经改成
按差异写（只动变化的那几行），但**孤儿申请不能只靠上游不出错来避免**——数据管理页、
回收站的彻底删除、外部脚本都能删到那一行。

批准那一支不放宽：行不在就批不了，否则等于批准了一个空气。

只核记录里写下的那几列（`insertChanges`）：归属、时间戳、`queued_at` 本来就不进
`changes_after`，它们在等待期间被公共层动过是正常的——`queued_at` 更是批准这一步要改的
那一列，核它等于自己跟自己过不去。

**修改与删除另有一道前置条件：目标行的 `queued_at` 必须是 0。** 把一份变更盖在还没生效、
外面根本看不见的行上是说不通的。眼下走不到这一步——改一份还没生效的新建不会另开申请，
而是直接写进去、顺手刷新那条新建记录的 `changes_after`（§13.7），于是「有一条修改申请，
它指着的行却还在队列里」这个组合造不出来。写这道条件是因为那一段的每一行 SQL 都默认了
「目标行已经生效」，而那件事此前只由 §13.7 的一条例外顺带保证着。

## 13.11 一行同时只能有一条申请在队列里，由数据库说了算

§13.6 那两条规则（只允许一种动作、别人提的整个锁住）都是应用层「先查再写」——挡不住两个
请求同时进来，也认不出没有登录身份的模块级调用是谁。硬约束在数据库上：

```
base_audits
  settled_at BigInt @default(0)
  @@unique([table_name, row_key, settled_at])
```

`settled_at` 是**了结时刻**：排队中记 `0`，批准、驳回、撤销都写上当时的毫秒；恢复
（requeue）把它放回队列，因此归零。回滚与重新应用**不动它**——那两个改的是数据状态，申请
本身早就了结了；归零会让它重新占住队列里那个位置，把别人挡在门外。从未进过队列的自助
记录一诞生就是了结的（`review_status = none`），因此也带一个时刻。

于是 `0` 成了哨兵：同一行的第二条 pending 撞上前一条，而已了结的那些各带不同的时刻，
历史要多少条有多少条。

**为什么用 `settled_at` 这个名字。** 批准、驳回、撤销三种都是「了结」——`decided_at` 盖不住
撤销（那不是审批人的决定，是申请人收回），`closed_at` 与工单语境里的「已解决」混。它与
`deleted_at` / `queued_at` 是同一个模式：0 表示还没发生，非 0 是发生的时刻。

**为什么值是毫秒而不是雪花号。** 雪花号天然唯一，同毫秒也不会撞，试过——但它超出 JS 的
安全整数范围，任何 `includeAll` 的读取会当场抛
`Value is too large to be represented as a JavaScript number`，每个读它的地方都得记着 cast
成文本。为一个几乎不可达的并发场景换来全局的读取负担，不划算。那个场景是「同一行的两条
记录在同一毫秒了结」：队列里最多一条，所以撞不上；剩下自助记录那一路，要撞得有两次内容
不同的自助修改落在同一毫秒。真撞上了表现是那次写入报唯一索引冲突，可见、可重试。

**裸的 UNIQUE 错误要翻译。** 约束触发时应用层的判定已经放行了，拿不到队列里那条的任何
信息，因此给的是笼统那句「这一行已经有一条申请在等待审批，一行上同时只能有一条」——与
行锁的说法一致，读起来是同一条规则而不是两条。

## 13.12 为什么这张表叫 `base_audits` 而不是 `base_approvals`

它装的**不只是审批**。前台自助的每一次修改都在这里留一条 `review_status = none` 的记录，
那种记录从来没进过审批队列：

```
4 条   scope=self   review_status=none      ← 建号之后用户自己改了四次昵称
2 条   scope=admin  review_status=approved
```

用户越多、前台越活跃，`none` 的占比只会越高。叫 approvals 的话，表名说的是那 1/3。

两处旁证都是这套代码自己写下的：`review_status` 的注释说「没进过队列的写入是 none，不是
approved」；§14 说不分表的理由是「分表会把『这一行被谁改过』的时间线劈成两半，而**那正是
审计最常回答的问题**」。

**审批是这张表上的一个状态子集，不是它的全部。** 因此两个词各有地盘：`audit` 是这张表和
它的页面（所有变更），`approval` 留给走审批那条路的部分——`review_status`、
`pending-approval.mts`、`PendingApprovalError`、四眼原则那一套，一个都没改。

事件表跟着叫 `base_audit_approvals` 而不是 `base_audit_events`：这套机制的核心动词一直是
**transition**（`TRANSITIONS` 规则表、`transitionOne`、`transitionAuditEntries`、
`applyInsertTransition`，四十来处），而 `event` 只活在那张表自己的名字里。叫 events 只是把
错位从 approval/audit 挪到 event/transition。

**一个 `kind` 只有一个中文名。** 曾经有两套文案：按钮上叫「批准」「重新应用」，记录里叫
「管理批准」「执行重做」——前缀按「谁做的、动的是什么」编，读起来舒服，可同一个 `redo`
落成了两个词，那正是命名歧义本身。现在中文只有 `TRANSITIONS[x].label` 一处，谁做的由旁边
的操作者列回答，不必编进类型名里。

## 14. 已知限制

- **前台自助的记录也堆在同一张表里。** 靠 `scope` 分开（§4.1），不分表——分表会把「这一行被谁改过」的时间线劈成两半，而那正是审计最常回答的问题。审批页默认只看待审批，翻历史时用「来源」筛选。
- **审批的范围限定在 `/panel/admin`（§11.2）。** 非管理员发起的后台操作要等 `agent` 与分站运营角色落地后才会自然进入队列。
- **回收站的「彻底删除」不留痕。** 它是物理 `delete`（§3.0 不审计），只能对已经在回收站里的行执行——而记录进回收站必须先经过一次审批，这条路径因此仍有一道门；但「谁在什么时候把它彻底删了」目前查不到。
- **不覆盖物理删除。** 见 §3.0。
- **一次操作里有一条核不上时，其余几条照样翻过去。** §13.8 让同号的记录一起处理，但内容
  校验（§13.10）是逐条判的：建号那三行里只有账号行带业务字段，它核不上而凭证行核得上时，
  回执是「成功 1 条，失败 1 条」，这一组就停在了半翻的状态。要不要改成「一条核不上整组
  都不动」还没定——那需要先把整组读齐再决定，与眼下逐条执行的写法不是一回事。
- **创建流程的收尾动作不留痕。** 新建账号后把 `owner_uid` 指回账号自己，是创建的一部分而不是人做的修改，走 `runSystemSql`。三处后台的物理删除在改用软删除之前是审计盲区。
- **只覆盖经过公共层的写入。** 裸 SQL 与迁移脚本不产生记录，这是有意的（数据搬迁不是业务变更）。
- **凭证的历史值会在审计表里多留一段时间。** 存储形态与活表一致（§5），但保留期更长——已经轮换掉的密钥要等保留期到了才清除。
- **多选回滚不是原子回滚。** 逐条独立执行，见 §7.4。
- **每一种审批动作只留最后一次。** 反复回滚又恢复的过程不保留：`reverted_*` 是最后一次回滚，`restored_*` 是最后一次恢复（§7.3）。数据当前停在哪一边始终准确，丢的是翻转次数与更早那几次的时间点。
- **业务变更每次多一次读。** 这是记录变更前值的代价；心跳写入按 §3.3 短路，不承担该成本。
- **审计表本身不被审计。** 否则会无限递归；它靠不可修改与保留期保证完整性。
- **没有面向普通用户的查看页面。** 归属字段已经让「只看自己的记录」免费成立（§9），但目前只有 `panel/admin` 下的管理员页面，普通用户没有入口。
- **回滚被拒绝时不产生噪音记录。** 回滚语句的 WHERE 里带着值校验条件，审计的 SELECT 用的是同一组条件，因此校验不通过时读不到行、也就不会记下一条没真正发生的变更。
- **受管表目前都没有心跳列。** §3.2 的字段排除清单因此暂时只在构建层生效（`updated_at`、`updated_duid` 本就写不进业务值），等 `sms_shortcut_tokens` 这类表建起来才会真正挡量。
