# 代理用户与管理视图需求开发文档

状态：设计已确认，未实施（2026-09-04 主人确认）。

前置需求：[数据可见性与代用户操作](data-visibility-and-delegated-access.md)。本文在其租户模型之上增加**用户之间的代理关系**。

## 1. 背景

租户解决了"数据归哪个客户群"，但租户内部所有用户是平的。分销场景需要一层：代理发展自己的下级用户，需要看到名下用户的开通情况、用量与账单，并按人数或用量结算。

**代理不是租户，代理是用户。** 代理与普通用户属于同一个租户、处在同一级别，区别只是它名下挂着一批下级用户。因此代理关系记在 `base_users` 上，不动 `base_tenants`。

## 2. 两条轴

系统里有两类主体，各自的可见范围沿不同的轴展开，不要混为一谈：

| 轴 | 角色 | 可见范围 |
| --- | --- | --- |
| **后台人员** | `super` | 全部租户的全部数据 |
| **后台人员** | `admin` | 本租户的全部业务数据 |
| **后台人员** | `support` | 自己的数据，加上代查**本租户内**指定账号 |
| **外部主体** | `user` | 自己的数据 |
| **外部主体** | `agent` | 自己的数据，加上名下下级用户的**管理视图** |

`super`、`admin`、`support` 是运营这套系统的人；`user`、`agent` 是使用这套系统的人。代理属于后者——它是一个普通用户，只是多了一个管理名下用户的视图。

### 2.1 代理只能看管理视图

**代理看得到名下用户的账号、套餐、用量、账单，看不到他们的业务数据。**

分销商需要知道有多少下级、用了多少、该收多少钱，不需要读下级的短信正文或端口映射配置。把可见性限制在管理视图，既符合最小权限，也让行级判定完全不用改动——热路径仍然是 `owner_uid = ?` 一个索引等值。

### 2.2 代理不能代查下级用户

代查是 `support` 的能力，`agent` 不具备，且 `agent` 不扩大 `support` 的代查范围。

这是 §2.1 的必然推论：若代理能代查下级账号，一次代查就看到了下级的全部业务数据，"只看管理视图"当场失效。代查是精确访问机制，不是绕过代理边界的通道。

代理无法直接帮下级排查业务问题，正确路径是本租户的 `support` 或 `admin` 处理。这是有意的取舍，不是遗漏。

## 3. 数据结构变更

### 3.1 `base_users.agent_uid`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `agent_uid` | `BigInt?` | 发展该账号的代理，指向同库 `base_users.id`；`NULL` 表示租户直属，无代理 |

字段名取 `agent_uid` 而非 `parent_uid`：它命名的是关系本身（"我的代理是谁"），比泛化的父子更准确。本期**固定两层**——代理的 `agent_uid` 恒为 `NULL`，下级用户的 `agent_uid` 指向代理。二级代理属于后续需求，届时改用物化路径。

`agent_uid` 是业务字段，不是归属字段，不进 `SYSTEM_FIELD_NAMES`：它由代理的开通动作显式写入，不由公共层自动填充。

**代理关系不跨分站。** 代理与下级必须属于同一分站，即两者的 `owner_tid` 与 `owner_bid` 都相等——分站管理的正是自己所属的用户与代理。写入与变更时都要校验。

### 3.2 不新增的东西

- 不新增代理实体表：代理就是 `base_users` 中被别人 `agent_uid` 指向的那些行。
- 不动 `base_tenants`：代理是用户级关系，与租户层级无关。
- 不新增行级字段：业务表不记录"归哪个代理"，代理归属通过 `owner_uid → base_users.agent_uid` 推导。下级更换代理时只改 `base_users` 一行，不需要回写业务表——与前置需求 §4.1 拒绝把租户信息冗余到行上是同一个理由。
- 不改动行级可见性判定：`agent` 不参与前置需求 §5.2 的规则。

## 4. 角色

`shared/types/role.mts` 增加 `agent`：

| 角色 | 可分配 | 作用域 |
| --- | --- | --- |
| `agent` | 是 | 本账号的数据，加上 `agent_uid` 指向本账号的全部下级用户的管理视图 |

- 由本租户的 `admin`（或 `super`）授予。代理不能自行发展代理——二级代理属于后续需求。
- `agent` 不隐含 `support`，也不与 `admin` 叠加使用：`admin` 已能看到本租户全部业务数据，再叠加代理视图没有意义。

## 5. 管理视图

管理视图是一组**独立的授权接口**，与行级判定无关。以系统上下文查询，显式按 `agent_uid` 限定范围，自带角色校验。

### 5.1 下级用户列表

返回 `agent_uid = <当前账号>` 的用户，每行包含用户名、状态、创建时间、套餐。**不返回下级的业务数据。**

### 5.2 用量与账单

按下级账号聚合的计数与用量，口径由各业务站点定义（SMS 站点为手机数与短信条数）。

聚合查询必须显式追加 `owner_uid IN (<下级账号集合>)`，**不得**通过放宽前置需求 §5.2 的可见性规则实现。集合来自一次 `WHERE agent_uid = ?` 查询，规模等于该代理的下级数。

### 5.3 开通与停用

代理可以创建下级账号、停用下级账号。创建时 `agent_uid` 自动写为代理自己，`owner_tid` 自动写为代理所属租户，代理都不能指定其他值。

代理**不能**删除下级账号，也**不能**修改下级的 `agent_uid`——转移下级归属只能由 `admin` 或 `super` 执行，因为它会改变计费归集。

### 5.4 下级的注册入口

代理可以拥有自己的注册链接或域名。域名方案沿用前置需求 §3.3：域名登记到 `base_hosts`，同时指向代理所属的租户与分站，注册时再按链接携带的代理标识写入 `agent_uid`。

**主机名只决定租户与分站，不决定代理**——`base_hosts` 里没有代理信息，代理归属由注册链接的参数决定，且必须校验该代理属于同一分站。

## 6. 计费归集

按 `agent_uid` 向上汇总：下级账号的用量归集到其代理。

- 下级更换代理由 `admin` 或 `super` 修改 `base_users.agent_uid` 完成，**不回溯历史账单**：变更之后产生的用量归新代理，之前的归原代理。
- 因此账单必须按周期快照存储，不能每次按当前 `agent_uid` 重算——否则一次归属变更会改写全部历史账单。快照表的设计属于后续的计费需求。

## 7. 实施步骤

1. `base_users` 增加 `agent_uid`，补四个迁移组 × 四种方言的迁移文件。
2. `shared/types/role.mts` 增加 `agent`。
3. 代理视图页面（下级用户列表、用量、开通停用），`agent` 与本租户 `admin` 可见。
4. 下级用户列表、用量聚合、开通停用三组授权接口，全部带同租户校验。
5. 冒烟用例覆盖 §8 全部条目，重点是"代理读不到下级用户业务数据"。

## 8. 验收标准

- `agent` 能看到 `agent_uid` 指向自己的全部下级用户及其套餐与用量。
- `agent` 看不到其他代理名下的用户。
- **`agent` 查询下级用户的业务表返回 0 行**，即使该账号是它开通的。
- `agent` 创建下级时 `agent_uid` 自动为自己、`owner_tid` 自动为本租户，提交其他值不生效。
- `agent` 不能删除下级，也不能修改下级的 `agent_uid`。
- 具备 `support` 的账号代查下级用户时，仍只受"同租户"约束，`agent` 关系不扩大也不缩小其范围。
- 跨分站建立代理关系被拒绝（跨租户自然也被拒绝）。
- 本租户 `admin` 能看到代理与其下级的全部业务数据（代理关系不影响 `admin`）。
- 用量聚合的结果等于逐个下级账号查询之和。

## 9. 已知限制

- **只有两层。** 代理不能发展代理，二级代理需要物化路径，属于后续需求。
- **代理无法帮下级排查业务问题。** 这是 §2.2 边界的直接代价，需要时由本租户的 `support` 或 `admin` 处理。
- **归属变更不回溯账单。** 依赖周期快照，见 §6。
- **代理关系不跨分站。** 同一个人若在两个分站或两个租户各有账号，那是两个独立账号，代理关系各自独立。
