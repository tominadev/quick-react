# 代理用户与管理视图需求开发文档

状态：设计已确认，未实施（2026-09-04 主人确认）。

前置需求：[数据可见性与代用户操作](data-visibility-and-delegated-access.md)。本文在其租户与分站模型之上增加**用户之间的代理关系**。

## 1. 背景

分站解决了"数据算哪个网点的"，但网点内部所有用户仍然是平的。分销场景需要一层：代理发展自己的下级用户，需要看到名下用户的开通情况、用量与账单，并按人数或用量结算。

**代理不是租户，也不是分站，代理是用户。** 代理与普通用户属于同一个租户、同一个分站、同一级别，区别只是它名下挂着一批下级用户。因此代理关系记在 `base_users` 上，不动 `base_tenants` 或 `base_branches`。

用电信打比方：租户是省公司，分站是地市分公司与营业网点，代理是网点下面的代办点，用户是终端客户。

## 2. 两条轴

系统里有两类主体，可见范围沿不同的轴展开：

| 轴 | 角色 | 可见范围 |
| --- | --- | --- |
| **后台人员** | `platform_admin` | 全部租户的全部数据 |
| **后台人员** | `platform_support` | 自己的数据，加上代查任意租户内任意账号 |
| **后台人员** | `tenant_admin` | 本租户的全部业务数据 |
| **后台人员** | `tenant_support` | 自己的数据，加上代查本租户内任意账号 |
| **后台人员** | `branch_admin` | 本分站的全部业务数据 |
| **后台人员** | `branch_support` | 自己的数据，加上代查本分站内任意账号 |
| **外部主体** | `agent` | 自己的数据、名下下级的管理视图，加上代查名下下级 |
| **外部主体** | `user` | 自己的数据 |

前五个是运营这套系统的人，后两个是使用这套系统的人。代理属于后者——它是一个普通用户，只是多了名下用户的管理视图和一个受限的代查范围。

## 3. 代理能看到什么

分两层，机制完全不同：

### 3.1 管理视图：名下下级的账号与用量（接口层）

代理**始终**能看到名下下级的账号信息与用量汇总，通过独立的授权接口提供，与行级判定无关：

- **下级列表**：`WHERE agent_uid = <自己>`，返回用户名、状态、创建时间、套餐。**不返回业务数据。**
- **用量与账单**：`WHERE owner_aid = <自己>`，按周期聚合，见 §6。
- **开通与停用下级**：创建时 `agent_uid`、`owner_tid`、`owner_bid` 全部自动填充，代理不能指定其他值。

这些查询以系统上下文执行并显式追加范围条件，**不得**通过放宽前置需求 §4.2 的可见性规则实现。

### 3.2 业务数据：只能通过代查，一次一个账号

代理**默认看不到任何下级的业务数据**。需要查看时，走与客服相同的代查机制，只是范围校验不同：

| 角色 | 代查范围 |
| --- | --- |
| `platform_support` | 不限 |
| `tenant_support` | 目标的 `owner_tid` = 请求者的 `owner_tid` |
| `branch_support` | 目标的 `owner_bid` = 请求者的 `owner_bid` |
| `agent` | 目标的 `agent_uid` = 请求者自己 |

同一套作用账号传递、同一张 `base_delegation_events` 审计表、同一条提权防线（目标不得具备任何管理员角色）。**只有范围那一条不同**，因此不需要三套实现。

#### 为什么走代查而不是在谓词里加一支

在谓词里表达"代理能看下级的数据"只有两条路，都不划算：

| 方案 | 代价 |
| --- | --- |
| 子查询 `owner_uid IN (SELECT id FROM base_users WHERE agent_uid = ?)` | 回到 `OR` 加子查询的形状，业务表索引失效，正是放弃等级模型时避开的东西 |
| 把 `owner_aid` 铺满全表，谓词写 `owner_aid = ?` | 第四个通用列，而且**下级更换代理要跨全部业务表回写**；D1 没有事务，部分表归属陈旧直接体现为账单算错 |

代查两者都不需要：代理归属仍然只存在 `base_users.agent_uid` 一行，换代理改一行即可；谓词一个字都不用改。

安全形态也更好：代理不是"天然泡在整片下级数据里"，而是每次显式指定一个账号并留下审计记录，出事时能查到是谁、什么时候、看了谁。

## 4. 数据结构变更

### 4.1 `base_users.agent_uid`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `agent_uid` | `BigInt?` | 发展该账号的代理，指向同库 `base_users.id`；`NULL` 表示分站直属，无代理 |

字段名取 `agent_uid` 而非 `parent_uid`：它命名的是关系本身（"我的代理是谁"），比泛化的父子更准确。

`agent_uid` 是业务字段，不是归属字段，不进 `SYSTEM_FIELD_NAMES`：它由代理的开通动作显式写入，不由公共层自动填充。

**本期固定两层**：代理的 `agent_uid` 恒为 `NULL`，下级用户的 `agent_uid` 指向代理。二级代理属于后续需求，届时改用物化路径。

**代理关系不跨分站。** 代理与下级的 `owner_tid` 与 `owner_bid` 都必须相等——分站管理的正是所属的用户与代理。写入与变更时都要校验。

### 4.2 计量记录的 `owner_aid`

**只有计量与账单记录带代理列，业务表不带。**

业务表不记录"归哪个代理"，代理归属通过 `owner_uid → base_users.agent_uid` 推导，下级更换代理只改 `base_users` 一行。

但账单不能这样算：按当前 `agent_uid` 实时聚合的话，下级换一次代理，**全部历史账单会被改写**，本该归原代理的钱变成新代理的。因此计量记录在产生时把代理钉死：

```
<站点>_usage_records / base_billing_entries 之类
  owner_tid, owner_bid, owner_uid   -- 通用归属，创建时定死
  owner_aid                          -- 产生这笔用量时的代理，写入后不变
  period, quantity, ...
```

聚合是 `WHERE owner_aid = ? AND period = ?` 一个索引等值，历史天然不回溯，代理转移只影响之后新产生的记录。

### 4.3 不新增的东西

- 不新增代理实体表：代理就是 `base_users` 中被别人 `agent_uid` 指向的那些行。
- 不动 `base_tenants` 与 `base_branches`：代理是用户级关系。
- 不改动行级可见性判定：`agent` 不参与前置需求 §4.2 的规则，它的谓词与普通用户一样是 `owner_uid = ?`。

## 5. 角色与授予

`shared/types/role.mts` 中的 `agent`：

- 由本分站的 `branch_admin` 或本租户的 `tenant_admin` 授予。**代理不能自行发展代理**——二级代理属于后续需求。
- `agent` 不与管理员角色叠加：`branch_admin` 已能看到本分站全部数据，再叠加代理视图没有意义。
- 代理**不能修改下级的 `agent_uid`**——转移下级归属只能由 `tenant_admin` 或 `platform_admin` 执行，因为它改变计费归集。
- 代理**不能删除下级账号**，只能停用。

## 6. 下级的注册入口

**域名决定租户与分站，链接参数决定代理。**

```
host          → base_hosts → (tenant_id, branch_id)   决定归属
?agent=<key>  → 校验该代理与当前分站一致              决定 agent_uid
```

`base_hosts` 里**没有代理信息**。理由：代理换域名会牵动分站解析，而同一个网点下多个代理共用网点域名是常态。注册时必须校验链接携带的代理属于当前分站，否则拒绝。

## 7. 计费归集

定价在**租户**（价格由租户分配给分站），分站与代理是分销通道与结算维度：

```
租户定价 → 分站（网点）→ 代理 → 用户
             owner_bid    owner_aid
```

两个维度都在计量记录上，各自能独立汇总：按分站结算网点，按代理结算代办点。

下级更换代理由 `tenant_admin` 或 `platform_admin` 修改 `base_users.agent_uid` 完成，**不回溯历史账单**——历史记录里的 `owner_aid` 已经定死。

## 8. 实施步骤

1. `base_users` 增加 `agent_uid`，补四个迁移组 × 四种方言的迁移文件。
2. 代查能力增加 `agent` 范围（目标的 `agent_uid` = 请求者），与 `tenant_support`、`branch_support` 共用同一套机制。
3. 下级列表、用量聚合、开通停用三组授权接口，全部带同分站校验。
4. 注册入口解析链接携带的代理标识并校验分站一致。
5. 计量记录表增加 `owner_aid`（随各业务站点的计量需求一起做）。
6. 冒烟用例覆盖 §9 全部条目，重点是"代理不指定账号时读不到下级业务数据"。

## 9. 验收标准

- `agent` 能看到 `agent_uid` 指向自己的全部下级用户及其套餐与用量。
- `agent` 看不到其他代理名下的用户。
- **`agent` 不指定作用账号时，查询下级用户的业务表返回 0 行**，即使该账号是它开通的。
- `agent` 指定名下下级为作用账号后，能查到并改动该账号的业务数据，且留下一条 `base_delegation_events`。
- `agent` 指定非自己下级的账号时被拒绝；指定任何管理员账号时被拒绝。
- `agent` 创建下级时 `agent_uid` 自动为自己、`owner_tid` 与 `owner_bid` 自动为本租户本分站，提交其他值不生效。
- `agent` 不能删除下级，也不能修改下级的 `agent_uid`。
- 跨分站建立代理关系被拒绝（跨租户自然也被拒绝）。
- `branch_admin` 能看到本分站内代理与其下级的全部业务数据，代理关系不影响它。
- 用量聚合的结果等于逐个下级账号查询之和。
- 下级更换代理后，历史计量记录的 `owner_aid` 不变，之后新产生的记录归新代理。

## 10. 已知限制

- **只有两层。** 代理不能发展代理，二级代理需要物化路径，属于后续需求。
- **代理排查问题要逐个账号。** 代查一次只能指定一个下级，看不到整片下级数据的横截面。这是 §3.2 边界的直接代价。
- **代理关系不跨分站。** 同一个人若在两个分站或两个租户各有账号，那是两个独立账号，代理关系各自独立。
- **业务表不带代理列。** 任何"按代理筛选业务数据"的需求都要经由 `base_users` 推导，或落到计量记录上。
