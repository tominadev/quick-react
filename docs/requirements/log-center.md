# 日志中心需求

## 背景

2026-09-12 起在日志中心服务器上部署了 Alloy（采集）、Loki（存储与查询）、Grafana（大屏）。
2026-09-17 卸载 Nginx，网关改由本项目的 `loki` 代码站点承担：推送接口校验凭据后转发给 Loki，
Loki 其余接口一律 403，其余路径转发给 Grafana。除这一层网关外，日志链路上没有自研代码。

截至 2026-09-17，Loki 中只有日志中心自身的日志（13MB、15 个流），源站一台都还没接入。

## 目标

- **不自研日志存储与查询引擎**，继续使用 Loki。
- 日志的查看与管理做进本项目：查询页、源站管理、推送凭据、保留策略、告警。
- Grafana 降级为管理员的临时探索工具，不作为日常入口，**也不作为权限边界**。

## 边界

| 层 | 归属 | 理由 |
| --- | --- | --- |
| 采集 | Grafana Alloy | 源站侧标准件，不自研 |
| 存储与查询引擎 | Loki | 压缩分块、时间分片、保留清理、写入限流、乱序容忍都已具备，自研收益为负 |
| 推送鉴权、查询页、源站管理、告警 | 本项目 `loki` 站点 | 需要租户隔离、角色权限，并与站点已有的通知模块打通 |
| 临时探索、复杂图表 | Grafana | 保留能力，但只对管理员开放 |

**运行日志与业务审计日志分属两个系统，不得混用**：谁改了哪条数据属于业务审计，走关系库、
带事务与归属字段（见 [change-audit-and-revert](change-audit-and-revert.md)）；Nginx、journal、
应用输出属于运行日志，走 Loki。两者的保留期、查询方式和权限判定都不同。

## 多租户

Loki 启用 `auth_enabled: true`，租户 ID 取本项目的 `owner_tid`（`base_tenants.id`），
不新增第二套租户概念。

- **写入**：网关按推送凭据定位到源站记录，用该记录的 `owner_tid` 作为 `X-Scope-OrgID` 转发给 Loki。
  租户由服务端从凭据推出，**不接受采集端自报**——自报等于任何一台源站都能写进别的租户。
- **查询**：由服务端按当前会话的租户注入 `X-Scope-OrgID`。前端不发送 LogQL，也不能指定租户。
- **跨租户查询**：仅超级管理员可用，必须显式选择目标租户，并按代用户操作留痕
  （见 [data-visibility-and-delegated-access](data-visibility-and-delegated-access.md)）。

**这一项必须在接入源站之前完成。** 切换 `auth_enabled` 会改变 Loki 的存储路径布局，
并要求所有源站的 Alloy 配置改动；接入几十台源站之后再切，要迁移数据并逐台改配置。
单租户模式下已写入的数据落在 Loki 内部的 `fake` 租户下，不迁移，按保留期自然过期。

## 采集端注册与克隆识别

凭据不再由人工建记录、手工填进源站配置——那样克隆一台机器就复制了一份凭据，
两台机器在日志中心看是同一台，日志和指标混在一起且不会报错。

改为自注册：注册令牌按租户/批次发放（`loki_enroll_tokens`），同一条安装命令可以在很多台机器上执行；
Agent 拿它换取这台机器专属的推送凭据，源站记录随之自动建出来。令牌只能注册新机器，改不了已有机器的凭据。

**克隆判定不使用机器指纹。** 实测：LXC 容器读不到 DMI `product_uuid`，云厂商 instance-id 在容器里
取到的是宿主虚拟机的 ID（同一宿主上的容器全都一样），machine-id 和磁盘内容会被克隆原样复制。
靠这些判身份必然误伤或漏判，因此指纹只存下来供后台展示佐证，不参与判定。

判定走令牌轮换：服务端对每个身份只认一个当前令牌，每次心跳校验通过立即换发新的。
克隆机带着同一份配置出生，等原机轮换过一轮之后它再来报到，用的就是作废令牌——
**同一个身份被两个进程持有**，这件事本身就是证据。判定为克隆时自动拆成新身份，
记录 `cloned_from_id` 并置 `clone_pending`，后台可复核。

唯一要区分的是「心跳响应丢了」：Agent 手里还是旧令牌，但它自己知道没收到响应，
会带 `retry` 标记；克隆机以为一切正常，不会带。这一个标记就把两者分开，因此重试不限次数——
连续丢包是网络问题，不是克隆的证据。

## 推送凭据

一源站一份凭据，由注册流程下发：

- 每条源站记录持有自己的推送用户名和密码；密码只存哈希，创建后不再明文展示。
- 停用某台源站只影响那一台，不影响其他源站写入。
- 网关校验失败返回 401，不区分「用户名不存在」和「密码错误」，避免探测账号是否存在。
- 凭据校验必须是常数时间比较。

## 数据结构变更

新增站点 schema `prisma/loki.prisma`，表名前缀 `loki_`。

`loki_enroll_tokens`（注册令牌）：`title`、`token_hash`、`status`、`expires_at`、`max_uses`、`used_count`、`last_used_at`。

`loki_sources`（源站 / 采集端）：前六个系统字段与三个归属字段按项目约定排列，随后：

- `title`：源站显示名
- `host`：采集端上报的 `host` 标签值，租户内唯一
- `push_user`：推送用户名，全局唯一（网关在认证时按它定位记录，此时还不知道租户）
- `push_secret_hash`：推送密码哈希
- `status`：启用 / 停用
- `last_seen_at`：最后一次成功推送时间
- `agent_token_hash` / `previous_token_hash` / `previous_retry_used` / `token_rotated_at`：身份令牌轮换状态
- `cloned_from_id` / `clone_pending`：克隆拆分的来源与待复核标记
- `fingerprint`：最近一次上报的机器指纹，只作展示佐证

后续阶段按需增加 `loki_alert_rules`（告警规则）。写入量、错误数等统计一律从 Loki 查询，
不在关系库里冗余存储。

## 阶段

1. **接入源站前**：Loki 多租户、`loki_sources` 表与源站管理页、网关改为按凭据鉴权并注入租户。
   2026-09-17 已完成除源站管理页之外的部分：表、迁移、网关鉴权与租户注入、Loki `auth_enabled` 已打开；
   新增源站目前只能直接写库，管理页仍待做。
2. 日志查询页：条件由后端下发，服务端翻译成 LogQL；按租户过滤；支持时间范围、标签、级别和全文过滤。
3. 告警规则接入站点已有的通知模块；保留策略与磁盘容量看板。

未完成的条目不得视为已实现。

## 验收标准

- 没有启用中的源站记录时，任何推送都返回 401，不会出现无鉴权的写入路径。
- 两台分属不同租户的源站推送后，任一租户的会话只能查到自己那台的日志。
- 停用一条源站记录后该源站推送返回 401，其余源站不受影响。
- 采集端自报的租户标识被忽略：伪造 `X-Scope-OrgID` 的推送仍落在凭据对应的租户下。
- 普通角色无法查询其他租户的日志，超级管理员跨租户查询留下审计记录。
- Grafana 仅管理员可访问，且不作为任何权限判定依据。
