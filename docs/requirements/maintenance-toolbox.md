# 维护工具箱与救援操作需求

本文档定义统一的命令行维护工具箱。它是脱离所有网页和正常登录链的救援工具，用于处理登录配置错误、运行状态检查和可控修复，目标是让系统在普通后台登录失效时仍能恢复。本文档只定义需求，未完成的条目不得视为已实现。

## 1. 背景与目标

当前 `Accounts OIDC 登录` 配置错误时，管理员可能无法进入正常后台，只能直接修改数据库配置。这个过程容易误改字段、泄露密钥，也无法留下统一的操作记录。

维护工具箱需要提供：

- 服务器或本机 Shell 中执行的独立救援命令；
- 不依赖普通站点、Base 本地登录、Passport 或 OIDC 的救援超级管理员上下文；
- 配置查看、修改、恢复默认和状态检查；
- 明确的确认提示、幂等操作和审计记录；
- Node SQLite、MySQL、PostgreSQL 与 Worker D1 的统一数据库操作逻辑，不提供 HTTP 管理入口。

这里的“关闭 Passport 功能”必须拆成明确的能力名称：

- `Accounts OIDC 登录`：业务站点通过 Passport 登录的开关；关闭后回到本站用户名密码登录；
- `Passport 外部身份源`：Google、微信等上游登录源的启用状态；
- `Passport 站点`：账号中心本身的站点能力，不因关闭 Accounts OIDC 登录而被删除或停用。

命令输出和确认提示禁止只写“关闭 Passport”，必须显示完整能力名称和作用范围。

## 2. 命令入口与执行边界

### 2.1 CLI 入口

工具箱只能通过命令行启动，不注册页面、导航、HTTP API、Cookie、浏览器会话或 CDN 资源。建议统一入口为：

```text
交互命令：maintenance
开发/未安装命令：npm run maintenance
非交互命令：maintenance <group> <action> [options]
实现：scripts/maintenance.mjs
公共逻辑：server/modules/base/maintenance/
动作协议入口：server/modules/base/maintenance/index.mts
终端调用模块：scripts/maintenance-toolbox.cjs
```

命令行工具必须复用现有数据库适配器、SQL 助手、密码策略和配置解析逻辑，不得为 SQLite、MySQL、PostgreSQL 或 D1 复制业务实现。

直接执行 `maintenance`（TTY 环境）时进入编号式维护菜单，交互形式类似宝塔终端工具：

```text
1) 基础管理员恢复
2) 登录配置救援
3) 站点设置恢复
4) 会话与设备处理
5) 服务管理（PM2）
6) 数据库结构检查与修复
7) 站点和运行诊断
0) 退出
请选择：
```

菜单由公共维护模块提供，操作完成后先显示结果并等待主人按键返回菜单，不启动 Web 服务。每个高风险选项都必须先显示目标、影响范围和是否立即生效，再等待明确确认。非 TTY、自动化部署和脚本场景使用稳定的非交互 action；支持 `--json` 输出机器可读结果，但不能绕过确认或救援身份校验。

### 2.2 与开发启动器的边界

维护工具箱是独立终端模块，不把菜单、确认、日志闸门或救援业务实现直接写进 `esbuild.cjs`。`npm run dev` 可以通过调用模块提供入口，但开发启动器只负责装配调用，不复制工具箱逻辑；后续增加 `npm run maintenance` 时复用同一模块，即使 dev 构建或服务损坏，工具箱也必须可以独立启动。

终端调用适配器：`scripts/maintenance-toolbox.cjs`；维护动作注册：`scripts/maintenance-actions.cjs`；PM2 服务适配器：`scripts/maintenance-service-pm2.cjs`。这些都属于独立模块，`esbuild.cjs` 不提供 dev 子进程的停止、重启或日志控制，只负责在开发环境中装配调用。

开发启动器仍支持与工具箱无关的低级启动参数，并将参数作为环境能力传给 Node 服务：

```text
npm run dev -- --no-listen
npm run dev -- --no-checks
```

其中 `--no-listen` 禁止服务监听端口，`--no-checks` 跳过启动时的 migration、代码站点初始化等检查，适合单独进行构建和诊断。参数只影响当前 dev 进程，不写入数据库，也不改变正常站点配置。

启动器会自动识别 PM2：如果当前 `npm run dev` 由 PM2 托管，或 PM2 中已有同一项目目录的在线服务，就自动启用 `--no-listen` 的等效行为，避免重复监听端口。PM2 未安装或状态无法读取时只给出诊断提示，不把服务控制降级为直接操作 Node 进程；需要明确覆盖时才允许使用 `DEV_FORCE_LISTEN=1`。

工具箱打开期间，开发调用方将 dev 子进程输出和当前进程日志交给独立模块的输出闸门暂存，避免日志覆盖菜单；返回调用方后恢复正常输出。子进程不读取终端输入，终端输入始终由工具箱模块管理。

### 2.3 救援身份

命令执行时建立一次性的 `rescue_superadmin` 救援上下文。它不经过普通站点登录、Passport 登录或 OIDC 登录：

工具箱只有命令行入口，服务器操作权限和命令入口本身就是授权边界，不再额外要求维护口令。命令仍必须校验目标数据库来源和运行环境，避免误操作生产库。

重设管理员密码时，交互菜单直接提示输入新密码并以星号回显；少于 8 个字符时直接要求重新输入，校验通过后才确认执行。非交互场景可通过 `MAINTENANCE_ADMIN_PASSWORD` 环境 Secret 提供。用户名可通过 `MAINTENANCE_ADMIN_USERNAME` 提供或在菜单中输入；密码不得出现在命令行参数、确认提示或日志中。

工具箱不创建网页会话或长期 Cookie；管理员密码、OIDC 客户端密钥等敏感值只按动作需要读取，禁止写入日志或回显。

救援会话建立后标记为 `rescue_superadmin`，不等同于任何站点的普通管理员会话，但对工具箱已经登记的救援操作拥有完整权限，不再进行普通角色、站点角色或目标对象权限限制。救援上下文的能力边界只由工具箱动作登记决定，不得再叠加普通对象权限拦截。救援会话仍不得回显用户密码、云 Secret、OIDC Client Secret，也不提供任意 SQL、任意命令或任意服务器文件访问；这些是工具能力边界和保密要求，不是对救援超级管理员的对象权限限制。

## 3. 终端维护菜单

工具箱采用公共 CLI 菜单协议。维护模块负责下发分组、编号、说明、确认文案和动作 key；终端只渲染通用菜单，不按站点名称、数据库方言或错误文本自行判断。交互菜单和非交互 action 必须调用同一份动作实现，不能维护两套救援逻辑。

初始分组：

### 3.1 登录与身份恢复

- 基础管理员 `base_users.id = 1` 的角色恢复；
- 基础管理员 `base_users.id = 1` 的用户名设置；
- 基础管理员 `base_users.id = 1` 的密码重设；
- 当前 Accounts OIDC 登录状态、Issuer、客户端 ID；绝不返回客户端密钥；
- 关闭 Accounts OIDC 登录；
- 启用 Accounts OIDC 登录；
- 恢复 Accounts OIDC 默认配置；
- 查看 Google、微信身份源启用状态；
- 单独停用 Google 或微信身份源。

每个动作必须显示作用范围。例如：

```text
关闭 Accounts OIDC 登录
作用：当前数据库中继承 Base 的站点回到用户名密码登录，不删除 Passport 账号和外部身份。
```

`base_users.id = 1` 是当前数据库保留的基础超级管理员记录，不是通过工具箱新建的绕过权限账号。当前角色模型只有 `admin` 管理员角色时，`id = 1` 的 `admin` 记录即作为超级管理员使用。恢复操作必须按主键执行确定性的修复或重建，而不是把现有记录当成冲突：按包含已删除记录的范围查询 `id = 1`，找到记录就直接修复 `deleted_at = 0`、`status = enabled` 和 `roles`（确保包含 `admin`）；找不到记录就显式重建 `id = 1`。不得出现“`id = 1` 已存在所以拒绝恢复”的分支；如果实现把本应修复的记录报告为主键冲突，属于代码错误。

超级管理员会话不受普通对象级权限限制，可以执行工具箱列出的全部管理和破坏性操作；后端只要求明确的二次确认、作用范围提示和完整审计，不得以“系统记录”“不可删除”等理由拒绝超级管理员。救援上下文虽然不等同于站点管理员会话，但对已登记的救援动作同样不做对象级权限拦截；它只用于工具箱协议，不会伪装成站点登录会话。

设置 `id = 1` 的用户名和密码必须分别确认，复用 Base 的用户名校验、密码策略和存储哈希实现。密码重设默认撤销该管理员的 Base 会话，不主动撤销 Passport/Accounts 会话。用户名等业务唯一字段必须在公共校验层完成确定性检查；恢复流程不得用数据库主键异常代替修复逻辑，也不得静默覆盖其他业务记录。

### 3.2 站点设置恢复

- 恢复站点设置默认值；
- 恢复系统配置默认值；
- 恢复技术栈伪装默认值；
- 显示“恢复后需要保存”或“已立即生效”的准确状态。

恢复默认的语义必须由后端声明。未明确声明立即保存时，只重置当前表单，用户仍需点击“保存配置”。

### 3.3 运行诊断

- 当前运行时：Node 或 Worker；
- 数据库方言和连接状态；
- 当前站点、继承链和数据库绑定；
- migration/schema 检查结果；
- API、页面和静态资源路径后缀；
- 当前维护会话及最近维护事件。

诊断默认只读，不显示 DSN 密码、云 Secret、Cookie、维护口令或完整用户数据。

### 3.4 服务管理（PM2）

服务启动、停止、重启和日志查看必须操作部署管理器 PM2，不操作调用工具箱的 Node、esbuild 或 watch 子进程。目标服务由当前项目真实目录和 `PM2_APP_NAME`（可选）确定，禁止交互式输入任意应用名，也禁止通过 Shell 拼接任意命令。

- 查看 PM2 服务状态；
- 通过 PM2 Cluster 注册并启动当前项目服务（默认 `max` 实例）；
- 交互式调整当前项目的 Cluster 实例数并保存 PM2 配置；
- 通过 PM2 重启当前项目服务的全部 Cluster 实例；
- 通过 PM2 停止当前项目服务的全部 Cluster 实例；
- 查看当前项目全部实例最近日志，并可由开发启动器接管持续日志输出。

启动服务前必须先停止工具箱调用方正在监听的本地 Node 服务，确认端口已交给 PM2 Cluster 后再注册服务；如果注册失败，不得偷偷操作其他项目。PM2 目标按服务名和真实工作目录分组，同一服务的全部实例作为一个操作目标；发现其他目录存在同名服务时，重启、停止和日志操作必须拒绝并给出确定性错误。

若系统未安装 PM2，必须返回明确的不可用原因，不回退为直接发送进程信号。开发启动器检测到同一项目已有 PM2 服务时不再监听端口，并将 PM2 Cluster 的日志转发到开发终端；开发 watch 的重建流程仍不直接发送进程信号。

### 3.5 会话与临时状态

后续阶段可加入：

- 清理已过期的 OIDC 授权状态；
- 清理已过期的外部扫码状态；
- 撤销指定维护会话；
- 标记卡住的 webhook 事件为可重试。

这些动作必须按状态和过期时间限定范围，禁止提供“清空整张表”按钮。

## 4. 动作与输出协议

交互命令启动后一次读取工具箱结构和当前状态：

```json
{
  "toolbox": {
    "groups": [],
    "actions": []
  },
  "context": {}
}
```

动作使用稳定 key，例如：

```text
set-accounts-oidc
restore-accounts-oidc-defaults
restore-site-settings
schema-check
```

非交互命令统一使用 `maintenance <group> <action> [options]`。CLI 必须再次校验目标数据库、操作参数和数据完整性；交互菜单隐藏某个选项不能替代执行层校验。

所有结果使用统一文本和 JSON 输出协议：

- 成功：明确说明是否立即生效；
- 失败：说明确定的原因和下一步；
- 退出码：成功为 `0`，参数错误、授权失败、数据冲突和执行失败使用不同的非零类别；
- 不允许脚本根据错误文本推断后续行为，应使用稳定 action 和退出码。

## 5. 安全和确认规则

- 救援入口只允许通过命令行启动，不能通过普通请求参数临时打开；
- 所有写操作必须进入公共动作执行器并经过确认，不提供通过 HTTP GET 修改配置的旁路；
- 关闭、启用、恢复默认、撤销会话和修复 schema 均必须确认；
- 救援超级管理员执行工具箱内任何已登记操作不做对象级权限拦截；删除、覆盖、停用和结构修复等高风险动作只增加明确确认、影响范围提示和审计，不以权限不足为由拒绝；
- 确认文案必须指出能力名称、作用范围和是否立即生效，不使用“该配置”“该身份”等模糊代词；
- 操作必须幂等：重复关闭、重复停用、重复恢复默认不能产生重复记录或错误副作用；
- 所有数据库写入继续通过统一 SQL 助手和数据库上下文，不允许工具箱拼接 SQL；
- 工具箱不提供任意 SQL、任意文件写入、任意命令执行或直接修改密钥内容的能力；
- 返回数据、日志和审计详情必须脱敏；
- 失败尝试需要限流，且不返回可用于枚举数据库、站点或配置的细节；
- 正常维护会话和救援维护会话都必须支持“退出当前维护会话”。

## 6. 配置和数据结构

### 6.1 配置

维护工具箱本身的非敏感配置可使用 `base_configs`：

```text
maintenance-toolbox
```

救援根密钥和来源白名单只能来自运行环境 Secret/配置，不写入数据库，不进入 Prisma migration，不在后台页面回显。

### 6.2 维护会话

如需持久化救援会话，新增 `base_maintenance_sessions`。遵循所有数据表统一字段顺序：

```text
id, created_at, updated_at, deleted_at, created_duid, updated_duid,
owner_uid, token_hash, scope, source_ip, user_agent_hash,
expires_at, last_seen_at, revoked_at, status
```

`token_hash` 使用唯一约束；维护会话没有普通设备来源时，审计设备字段为 `NULL`，不得伪造 `0`。

### 6.3 操作审计

新增 `base_maintenance_events` 保存每次维护动作：

```text
id, created_at, updated_at, deleted_at, created_duid, updated_duid,
owner_uid, session_id, action, target, status, request_id,
source_ip, details, completed_at
```

`details` 只保存脱敏后的原始诊断信息。`request_id` 用于幂等和排查；重复请求不能重复执行不可逆动作。审计记录默认不可由工具箱删除，只能按统一删除规则进入回收站。

## 7. 数据一致性

以下操作必须使用批处理或事务，不能留下不可恢复的半状态：

- 建立救援上下文并写入对应审计结果；
- 撤销维护会话并写入对应审计结果；
- 消费 OIDC/扫码一次性状态并创建必要的凭证或会话；
- schema/migration 操作及其版本记录。

单纯读取、重复可执行的设备清理、过期状态清理和诊断操作可以不使用事务，但必须限制范围并支持重试。

关闭 Accounts OIDC 登录只修改统一配置项 `accounts-oidc-client.enabled`，不得删除账号、身份、会话或客户端密钥。共享数据库时 Global、Passport 和业务站点按照现有共享配置规则同时生效；数据库分离时只影响当前目标数据库。

## 8. 多运行时要求

- Node：支持默认 SQLite、配置好的 MySQL/PostgreSQL DSN；维护工具不得扫描未知文件或自动发现数据库；
- Worker：只使用 `DEFAULT_DB` 或构建期声明的 D1 Binding；Worker 不提供 CLI 救援操作；
- Node 与 Worker 共用 `shared/types`、动作 key 和反馈协议；
- Worker 不执行 Node 专属的进程重启、文件备份或任意 schema 改写；这些能力必须显示为不可用或由 CLI 完成；
- 所有 API 必须经过公共响应层，页面和 API 路径保持对应。

## 9. 明确不做

- 不通过工具箱任意创建新的超级管理员账号；只允许恢复或重建约定的 `base_users.id = 1` 保留管理员记录；
- 不把管理员密码、云 Secret 或 OIDC Client Secret 写入页面、数据库明文、Cookie 或日志；
- 不让救援会话伪装成普通管理员、Accounts 或 Passport 会话；救援会话只在工具箱协议内使用 `rescue_superadmin` 身份；
- 不让工具箱根据站点名复制 Passport、Global 或业务站点逻辑；
- 不提供任意 SQL、任意命令、任意文件浏览和任意密钥导出；
- 不把维护工具做成 CDN 可缓存的公共管理页面。

## 10. 验收标准

- OIDC 配置错误导致普通后台无法登录时，允许在来源白名单内通过独立救援入口进入 `rescue_superadmin` 工具箱；
- 关闭 Accounts OIDC 后，业务站点可按现有统一开关回到用户名密码登录；
- 关闭操作不删除 Passport 用户、外部身份、OIDC 客户端或会话数据；
- 恢复默认、停用外部身份源和撤销维护会话均有明确确认；
- 重复执行同一动作不会产生重复数据或错误副作用；
- 目标数据库、操作参数或运行环境校验失败时不得执行写操作；
- CLI 只显示脱敏配置和诊断结果；
- 审计记录包含动作、目标、结果、时间、请求 ID 和来源信息；
- Node SQLite、MySQL、PostgreSQL 以及 Worker D1 的类型检查、Worker 构建和相关协议测试通过；
- 正常站点后台、Passport、Global 与业务站点继续使用同一套 Base 工具箱协议。

## 回归测试

`npm run test:maintenance-rescue` 覆盖全部救援动作，重点是**救援设的密码必须真的能登录**。

这个测试的由来：凭证从 `base_users.password` 拆到 `base_user_credentials` 之后，`readAdmin` 仍在查那一列，于是**整个工具箱**（不只是密码重设）一律报 `no such column: password`——而它失效的时候，恰恰是 Accounts 登不进来、只剩救援这一条路的时候。

救援入口跑在没有请求上下文的 CLI 里，绕过了所有 HTTP 层测试，任何一处引用了已删除的列都不会被别的测试发现，只能由它自己盯着。
