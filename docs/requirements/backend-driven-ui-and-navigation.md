本文档记录当前项目在“后端重、前端轻”方向上的后续改造范围。后端负责业务结构、权限和文案，前端负责通用协议渲染与少量已打包的专用组件。

- [x] TableCRUD 的表结构与表数据按统一 `include` 参数分离：请求必须显式携带资源，首次请求追加 `include=schema,data` 返回 `option`、`columns` 和数据，结构已加载后改用 `include=data`，公共响应层只返回数据字段；`include=schema` 只返回结构，不带 `include` 不返回表资源。回收站使用 `include=deleted,schema,data` 首次加载、`include=deleted,data` 后续加载，也支持 `exclude=deleted` 明确排除删除记录，切换表或首次加载时重新取得完整结构。

API 页面启动模式只缓存不含用户状态的 HTML 页面壳；会话、角色、页面状态和业务数据仍通过不可缓存的后端接口获取。关闭开关时继续使用服务端按会话生成的 HTML，不得将受保护页面作为公共 CDN 内容缓存。

## 2. 后端驱动按钮

### 2.1 目标与最小数据原则

列表、表单和页面操作按钮由后端输出，后端决定：

- 是否显示；
- 显示文案；
- 按钮顺序；
- 是否禁用；
- 是否需要确认；
- 动作 key。

前端不再硬编码具体业务按钮名称、业务按钮权限或业务按钮顺序。

同一约束也适用于操作完成后的行为：刷新当前页、跳转、打开或关闭弹窗、关闭窗口以及目标路径都由后端通过统一响应协议声明。前端业务组件不得因为“这是登录接口”“当前是 Passport 站点”或“响应里出现某个字段”而自行决定下一步；前端只允许在统一协议执行器中把稳定 action 映射为通用浏览器行为。例如普通操作可以返回 `next: { action: 'reload' }`，需要在应用内切换认证状态时由后端返回 `next: { action: 'navigate', path: '/目标路径', refreshAuth: true }`，响应层会自动附带认证上下文。通用执行器使用响应里的上下文，再用浏览器路由切换路径，不重新加载应用脚本；只有 `refreshAuth` 未开启的普通 `navigate` 才执行完整页面导航。需要保留反馈时 `reload` 可带秒级 `delay`（延迟单位为秒），组件只把完整响应交给执行器。

站点继承同样按能力收敛：Passport、Global 和普通业务站点共用的登录、系统设置与 `/panel` 鉴权必须由 Base 实现，不得为某个站点复制一份再删减字段。Accounts 首页、OIDC Provider、账户中心、Global 控制面和云资源页属于真实独立能力，可以保留各自模块；判断身份中心时使用其是否提供 OIDC 授权端点等能力信息，不比较固定站点名称。

后端输出遵循最小数据原则：只输出前端无法根据已有上下文推导出的信息。默认行为不需要显式描述：

- 能通过 `key`、当前页面资源和后缀生成的 URL，不返回 `url` 或 `href`；
- 正常显示的按钮不返回 `visible`；
- 默认可用的按钮不返回 `disabled: false`；
- 能由动作 `key` 推导的请求方法、路径、资源 ID 和刷新行为，不重复返回；
- 页面和 API 的公共前缀、路径后缀不放进每个按钮配置。

只有改变默认行为时才返回对应字段，例如 `disabled: true` 或确认配置。不使用 `visible` 表达静态显示状态：不适用的动作直接省略。

### 2.1.1 开关语义：关闭不增熵，打开才增加能力

所有**可选能力开关**必须采用单向增量语义：关闭时执行最低复杂度的基线行为，打开时只启用已经实现并登记的附加能力。这里的“不增熵”指关闭状态不得引入额外的页面元素、路由、请求、数据库写入、会话状态、事件或前端专用分支；关闭开关不应再维护一套为了模拟关闭效果的重复代码。打开开关则复用同一份已存在的实现，不复制另一套开启逻辑。

- 可选功能默认优先使用关闭值；确实属于系统基线的功能可以默认开启，但必须在配置说明中明确其基线身份，默认值不是开关语义本身。
- 开关名称和文案描述“增加什么能力”，例如“启用 Accounts 登录”“启用 API 页面启动”；不要把同一开关同时当作“隐藏按钮”“拒绝接口”和“停用资源”的多重含义。
- 禁止使用 `disableXxx`、`禁止Xxx` 这类负向功能开关：它们会变成“打开开关后才增加拦截或禁止分支”，违背关闭不增熵。应改为 `xxxEnabled` 等正向能力开关，例如 `loginEnabled = false` 表示保持无登录的基线，`loginEnabled = true` 才启用已有登录实现。
- “关闭登录按钮”只表示不增加该入口，页面回到原有登录基线；如果需求是禁止整个登录能力，应使用单独、明确的安全策略开关，不得借用按钮开关表达。
- 严格校验、要求 PKCE 等安全强化项也应按“启用额外策略”命名：关闭表示沿用基础协议，打开才增加额外拦截或校验；安全基线仍由后端接口鉴权保证。
- `enabled/disabled` 等资源状态不是可选能力开关，表示记录是否可用，不能因为名称相同而套用“关闭后回退到基线”的解释。
- 后端统一提供开关的稳定值、默认值、文案、权限和生效范围；前端只按通用协议渲染，不根据站点名、接口路径或开关名称自行推导关闭行为。

新增或修改开关时，先回答三个问题并记录在需求或架构文档中：关闭后的最低基线是什么、打开增加了哪些可观察行为、关闭是否完全不产生额外副作用。若一个开关无法清楚回答这三点，应先拆分能力或重新命名，不得继续叠加特例。

### 2.2 标准 CRUD 动作

标准 CRUD 动作不由后端重复提供路径或方法。前端根据当前页面的 `resourcePath`、行主键和动作 `key` 生成 API 请求：

```text
create -> POST   /api/<resourcePath><apiSuffix>
edit   -> PUT    /api/<resourcePath>/<id><apiSuffix>
delete -> DELETE /api/<resourcePath>/<id><apiSuffix>
refresh -> 重新加载当前资源
```

后端只需提供类似以下语义配置：

```ts
{
	key: 'delete',
	label: '删除',
	confirm: '确认删除吗？'
}
```

`key` 同时用于选择已注册的前端交互和默认请求规则，例如 `create`、`edit`、`delete`、`refresh`、`test` 或 `download`。当前协议不再重复提供含义相同的 `action`、`type` 或 `method`。如果未来某个动作无法由 key 推导，应先确认它能否注册成新的稳定 key，再决定是否扩展协议。

API 路径相对于 `/api`，业务配置不重复写 `/api`，也不重复写 `.php` 等后缀。路径前缀和后缀仍由前端通用协议助手处理，这属于基础设施逻辑，不属于业务硬编码。

### 2.3 非标准动作

同步云资源、执行迁移、导出数据等无法从 CRUD 规则推导的操作，使用受限的动作标识：

```ts
{
	key: 'migrate',
	label: '执行迁移',
}
```

前端只执行预先注册的通用动作，不执行后端下发的 JavaScript。后端 API 仍必须独立完成权限校验，按钮隐藏不能替代接口鉴权。

非标准动作也遵循最小数据原则：如果前端注册的动作可以根据当前页面、当前行和参数生成目标，就不返回路径；只有无法推导时，才允许返回相对于 `/api` 的逻辑路径。

### 2.4 默认 CRUD 权限等级

标准 CRUD 默认采用由低到高的权限等级：

| HTTP 方法 | 默认能力 | 默认等级 | 典型操作 |
|---|---|---:|---|
| `GET` | `read` | 1 | 查看列表、查看详情、刷新 |
| `POST` | `create` / `request` | 2 | 新增记录、提交申请 |
| `PUT` | `update` / `review` | 3 | 修改记录、审核记录 |
| `DELETE` | `delete` | 4 | 删除记录、不可逆操作 |

默认规则下，拥有 `GET` 能力的用户可以读取数据，但不能自动获得 `POST`、`PUT` 或 `DELETE` 能力。后端根据当前用户能力生成动作列表：没有能力的动作不返回，API 本身也必须拒绝对应请求。

标准 CRUD 的 `DELETE` 统一表示软删除：记录的 `deleted_at` 由 SQL 公共层写入当前时间，正常列表自动隐藏该记录，删除成功反馈必须说明可以恢复或彻底删除。所有带 TableCRUD 表格协议的响应都由 Base 公共层追加“回收站”工具栏动作；前端在当前批量操作区右侧打开嵌套的同一资源 TableCRUD，并向原接口传递 `include=deleted` 查询参数查看已删除记录，由后端动作配置提供恢复和“彻底删除”操作。回收站不注册独立 API 或导航菜单，彻底删除才允许使用物理 `DELETE`。

HTTP 方法只是标准 CRUD 的默认映射，不是最终权限模型。业务动作可以覆盖默认映射，例如：

```text
POST /sync       -> cloud.sync
POST /apply      -> order.apply
PUT  /review     -> order.review
```

因此权限判断应优先使用业务能力名，例如 `users.read`、`users.create`、`orders.review`、`users.delete`，而不是在所有场景直接比较 HTTP 方法。方法到能力的映射仅作为标准 CRUD 的默认策略。

权限等级不是安全边界的唯一依据。敏感的读取接口仍可以要求高于普通 `GET` 的能力，删除、审核和批量操作也必须在后端逐接口校验。

## 表格的排序与地址栏状态

**排序在服务端做。** 数据是分页的，只排当前页等于排了个寂寞。请求参数是 `?sort=<列>:<asc|desc>`，多列用逗号分隔、靠前的优先：`?sort=status:asc,user_name:desc`。列名用表格列的 `dataIndex`；映射到数据库列由查询自己完成，因此请求里出现的任何名字都只是查表的键，拼不进 SQL。认不出的字段直接丢掉。

**多列的优先级按点击顺序，不用 antd 的 `sorter.multiple`。** 那个是列上写死的固定优先级，用户点的先后不影响结果，而"先按状态再按时间"和"先按时间再按状态"是两回事。已经在排的列保持原有先后，新点的列排到末尾——"再按某列细分"是往后加一层，而不是把之前的次序打乱。

**列上的 `sortOrder` 必须在渲染时注入，不能写进列定义。** 列定义只在拿到 schema 时构造一次，写死在里面的话它永远停在首次的值；而 antd 的"下一档排序"是依据当前 `sortOrder` 算的，于是点几次都只有升序——倒序根本点不出来。

**能排序的列就是这条列表查询选出来的列。** `tableSort(c)` 在查询执行时把选出的列名回调给请求上下文，响应层据此在列定义上标注 `sortable`，前端只按这个标注渲染排序箭头，不自行推断。这样不需要另维护一份白名单，加列减列也不会走偏；路由只需在列表查询上加一个 `sort: tableSort(c)`。

请求的排序排在原有排序前面，原有的留作兜底：按状态这类重复值很多的列排时，同值行之间还要有稳定次序，否则翻页会看到同一行出现两次、另一行一次都不出现。请求了不存在的列就整个回落到默认排序——那多半是换了页面结构后浏览器还留着旧地址。

**搜索、翻页、排序都记在地址栏里**，刷新回到原处，链接也能直接分享：

```
?page=3&size=50&sort=user_name:desc&q.user_name=adm&q.status=enabled
```

**分页要显示总数。** antd 默认只画页码，`showTotal` 得自己给。游标分页（数据来自云厂商接口那类）拿不到总数，`total` 是按当前页估出来的，那种情况只报「第 x-y 条」不报总数——写一个会变的「共 N 条」比不写更糟。

**`totalRecords` 是符合条件的真实总数，不是这次取回了几条。** 列表通常有条数上限（审计是 200），拿返回行数充数会在超过上限时谎报：库里 250 条却显示「共 200 条」。有上限的列表要单独计一次数，并且用与列表**同一组筛选条件**。

**首屏那一个启动请求也必须带上地址栏的参数。** API 启动模式下，页面数据是 App 用 `include=auth,schema,data` 一次取回来的，表格组件直接拿去用、不再自己请求一次；启动请求不带参数的话，带着 `?q.status=all` 进来首屏拿到的却是服务端默认那一份，界面和地址对不上。地址栏名字（`page`/`size`/`q.<字段>`）与接口名字（`pageNum`/`pageSize`/`<字段>`）的换算只在 `tableRequestParams` 一处，且**只带地址栏里真有的东西**——地址上什么都没写就一个参数都不加，接口照常用它自己的默认值。

**地址栏是唯一事实来源。** 进页面时就把**生效的**筛选写进地址栏（包括后端下发的默认值），看到的地址就是当前查询——刷新、收藏、分享出去都是同一份结果。否则会出现「界面上显示待审批、地址栏里什么都没有」，刷新后走哪一套全看实现细节。

查询条件有三个来源，后面的压过前面的：字段自带的 `defaultValue` → 页面传入的初始值 → **地址栏**。带着 `?q.status=…` 进来的地址是用户明确选定的，必须赢过默认值；审计页默认「待审批」，用户改成「全部」再刷新，挑的不能白挑。空串也算明确选择，不回落到默认值。

- 搜索字段带 `q.` 前缀：它们是各表自定义的，不加前缀就会和 `page`、`sort` 这些通用参数撞名。
- 只有非默认值才写进地址，默认状态下地址栏保持干净。
- 页面自身的其它查询参数（例如表单页的 `?tab=`）不会被表格状态顺手清掉。
- 用 `replaceState` 而不是 `pushState`：翻了五页再按后退应该离开列表，而不是一页页倒着退回去。
- 排序变化时回到第一页——停在第 5 页却换了次序，看到的是一段没有来由的数据。

读写这套状态的是纯函数（`table_crud/url-state.ts`），由 `test:table-url-state` 单独盯着，不依赖 React 与 antd。

## 设置页保存前的两道确认

- `confirmOnUnchangedSubmit`：什么都没改也点了保存，多半是误触，问一句。
- `confirmChangedSubmit`：改了东西时，把**改了哪几项、从什么变成什么**逐条列出来再问一句。

设置页一屏十几个开关，改完隔一会儿再回来点保存，多半已经记不清动过哪些；而这些改动往往立刻影响整个站点的行为——关掉本站登录、切换页面启动模式、改掉 OIDC 客户端。列出来的是**字段标题**和**人能读的值**：开关说「开/关」，下拉说选项文案而不是它的值，空值说「空」。

四个设置页都必须两样都配，由 `npm run test:column-order` 一并守着（它扫 settings 目录下的每个文件）。

## 表格配置随响应整体替换（2026-08-27 补充）

通用 CRUD 组件收到 `table.option` 时必须**整体替换**当前配置，不能与上一次的配置合并：数据管理这类"同一个页面切换数据源"的场景下，合并会让上一张表的行操作、工具栏和查询动作残留到新表上。

**列可以分组，编辑抽屉按分组渲染成可切换的 Tab**（`TableColumn.group`）。任一列带上 `group` 就分组，没带的列归到第一个分组；只影响表单，不影响列表。

分组的 Tab 必须 `forceRender`：Tab 默认懒渲染，**没渲染过的 `Form.Item` 不会注册到表单，提交时那一组字段会整个丢掉**——而用户根本察觉不到自己漏填了什么。

查询输入框里**按回车等同于点搜索**。查询区是裸的输入框，不在 `form` 里，没有默认提交行为可拦，因此要显式接 antd 的 `onPressEnter`——而不是为此套一层 `form`，那还得处理默认提交与冒泡。没有搜索动作或正在加载时回车不生效。

查询条件变化（例如切换数据表）时还必须清空**已选中的行**和**列筛选**：选中行残留会让批量删除按着旧表的主键去删新表的数据，列筛选残留会让新表的数据被莫名其妙地过滤掉。

覆盖测试：`npm run test:table-switch-browser`。
