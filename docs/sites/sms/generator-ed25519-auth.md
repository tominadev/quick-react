# Mac 生成器改用 Ed25519 签名认证

本文档只定义需求，**未完成的条目不得视为已实现**。落地之前，生成器仍在用平台预配凭证
（见 [SMS Mac Shortcut 生成器需求开发文档](shortcut-generator.md) §3）。

## 1. 为什么换

生成器调 `/api/platform/*` 现在用 `Authorization: Bearer <SMS_PROVISIONING_KEY>`——一把
**长期有效的明文口令**，躺在那台 Mac 的 `.env` 里，服务端只存 `sha256` 摘要。三个问题：

- **泄露之后一直有效**，直到有人想起来换。没有任何自动失效的机制。
- **口令由服务端生成再交给对方**，传输路上多一次暴露；而签名方案里私钥从不离开那台机器。
- **没有新鲜度，一次抓包可以无限重放。** 本站另外两条链路（绑定票据、推送）都已经靠
  `ts` 把重放窗口压到 60 秒，只有这一条还没有。

换完之后三条链路（接入方绑定、平台推送、生成器调用）是**同一个信封、同一套心智**，
读一处文档就够，不必为第三种认证方式单独记一套规则。

## 2. 请求格式

与绑定、推送完全相同的信封：

```http
POST /api/platform/shortcut-tokens.php?action=config
Content-Type: application/json

{"publicKey":"…","signature":"ed25519=…","payload":"{\"ts\":1789700000,\"…业务字段\"}"}
```

| 字段 | 要求 |
| --- | --- |
| `publicKey` | 这台机器的 Ed25519 公钥，原始字节的 Base64URL，43 个字符 |
| `signature` | `ed25519=` 前缀加签名的 Base64URL。**签的是 `payload` 那段字符串本身的 UTF-8 字节** |
| `payload` | **一段 JSON 字符串**，不是嵌套对象。原来请求体里的业务字段，加上 `ts` |
| `payload.ts` | Unix 秒。与服务器时间相差超过 60 秒即拒绝，与绑定票据同一个数 |

**`payload` 必须是字符串。** 传成嵌套对象就得重新序列化才能验签，而两边的序列化不可能保证
一致——键序、空格、Unicode 转义差一点签名就对不上，而报出来的是「签名无效」，看的人会去查
私钥，查不到真正的原因。服务端要**当场按名字点破**这个错，不要让它退化成签名失败。

**没有 nonce。** 绑定票据需要一次性 nonce，因为重放一次就多绑一个手机；生成器这边的操作
带幂等键（`idempotency_token`，见生成器文档 §5.5），60 秒窗口内重放不会产生第二份效果。
将来若出现不幂等的生成器接口，再补 nonce 表。

## 3. 身份解析

**拿公钥反查是哪台机器，机器自称的标识不作数。** 与现在的凭证解析同一条规则——对象键里的
目录名靠机器身份决定，自称可以伪造，伪造就意味着一台机器能把文件写进另一台的目录。

公钥查不到、机器已停用，一律回同一句话：不该让拿到公钥的人多得到一个「这台机器是不是被停了」
的答案。

验证顺序与绑定票据一致：拆信封 → 查格式 → 按公钥查机器 → **验签** → 验完签才解析 `payload`。
`ts` 的检查排在验签之后——它在 `payload` 里，提前读就等于信了还没验过的内容。

## 4. 数据结构

`sms_generator_machines`：

| 动作 | 列 | 说明 |
| --- | --- | --- |
| 新增 | `public_key` | Base64URL 的 43 个字符，**非空**，唯一。一把公钥不能同时属于两台机器，否则「这次调用是哪台机器发的」就说不清 |
| 删除 | `secret_hash` | |
| 删除 | `secret_prefix` | |

**`secret_hash` 与 `secret_prefix` 必须一起删掉。** 留着就等于留了一条「把公钥清空就退回口令」
的暗路，而那把长期有效的明文口令正是这次要废掉的东西。

后台「生成器机器」页随之变化：新增表单从「服务端生成口令、一次性显示 `.env`」改成**填公钥**；
一次性口令弹窗、`secretNotice`、`issueSecret` 一并删除。私钥不经过本站，因此本站没有任何
只显示一次的东西要给运维保存。

## 5. 不做兼容

**代码里任何时刻只有一套算法。** 不保留 Bearer 分支，也不做「填了公钥就用签名、没填就用口令」
那种按数据条件自动退场的自适应——它同样是两条路径，要双份维护、双份测试，出问题时还要先判断
走的是哪一条；而留下来的那条往往正是更弱的那条。

过渡的风险由**部署顺序**消化，不由代码消化：

1. **加列**（`public_key` 可空），不动认证逻辑。上线后行为完全不变。
2. **登记公钥**：Mac 侧生成密钥对，公钥填进后台。此时公钥已登记但无人使用，生成器仍走口令，
   照常工作。
3. **切换**：Mac 侧改成签名调用，同时本站上线「只认签名」版本——删口令路径、删两列、
   `public_key` 改非空。这一步与 Mac 侧**约时间一起做**。

第 3 步前后几分钟内生成器可能取不到令牌。影响可控：生成器不是实时链路，它的作用是往池子里
补令牌，池子有余量就不影响绑定；真空了才会报「令牌池空了」。**切换前先确认池子有余量。**

## 6. 生成器侧要做什么

一句话给维护那台 Mac 的人：

> 调平台接口不再用 `Authorization: Bearer`，改成：自己生成一对 Ed25519 密钥（私钥留在本机，
> 公钥发来登记），请求体发
> `{"publicKey":"<公钥,base64url,43字符>","signature":"ed25519=<对 payload 字符串原始字节的签名,base64url>","payload":"<把原来的请求体 JSON 加上 \"ts\":当前Unix秒，整个 JSON.stringify 成一个字符串>"}`，
> **signature 签的就是 payload 这个字符串本身，签完别再重新序列化**，Content-Type 用
> `application/json`。

`.env` 里的 `SMS_PROVISIONING_KEY` 换成私钥文件路径；私钥**不上传、不进版本库、不写日志**。

## 7. 回归测试

`npm run test:sms-generator-pool` 的认证方式整体换成签名，并覆盖三条坏路径，每条都要回
确定性错误而不是内部异常：

- 拿别的私钥签 → 签名无效；
- `ts` 落在 60 秒窗口之外 → 已过期；
- `payload` 传成嵌套对象 → 按名字点破，不能退化成「签名无效」。

## 8. 明确不改的东西

**手机上的快捷指令不动。** 它调 `/api/shortcut/message-receive` 用的是静态原始令牌，而
快捷指令跑在用户自己的手机上、由 Shortcuts 执行，改不了也不该改——那条链路的凭证一次一份、
绑定到一部手机，泄露面本来就限定在那一部手机上。
