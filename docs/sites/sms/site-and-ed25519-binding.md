## 0. 词汇约定

两个方向都涉及短信的传输，用词固定，不得混用：

| 方向 | 用词 | 对应 |
| --- | --- | --- |
| 手机 → SMS | **接收** | 接收接口 `/api/shortcut/message-receive`，字段 `received_at`、`message_id` |
| SMS → 用户服务端 | **推送** | `sms_push_endpoints` |

其余称谓遵循 [AGENTS.md](../../../AGENTS.md)：本文中的"用户"一律指网站终端用户。

## 1. 背景

SMS 站点集中查看多部手机收到的短信，不负责发送。手机侧由 iOS Shortcut 收到短信后调用 SMS 接收 API，认证方式是每台设备独有的 Bearer 令牌。

除了在页面上手工绑定，用户还需要从自己的服务端自动为账号绑定手机。用户服务端不直接调用浏览器接口，而是用 Ed25519 私钥签发一次性票据，把票据放进静态绑定页面 URL 的 `#` 片段；页面读取片段后通过 AJAX 提交给 SMS 后端完成绑定。私钥始终留在用户服务端，SMS 只保存公钥。

## 2. 目标与边界

### 目标

- 提供 `sms` 业务站点，展示已绑定手机的短信。
- 一名账号可绑定多部手机；每部手机同时只有一个有效的 Shortcut 令牌。
- 用户服务端用 Ed25519 签名票据完成跨页面绑定，不暴露私钥。
- 票据具备受众、有效期、随机数和一次性消费状态，防止跨站重放。
- 为未来 SMS 独立数据库保留清晰的本地身份边界，不跨库读取其他站点的用户表。

### 不在本期范围

- 不发送短信，不实现短信验证码能力。
- 不把 iOS Shortcut 改造成 Ed25519 客户端；Shortcut 是受限客户端，用高熵令牌经 HTTPS 认证。
- 不在浏览器保存或生成用户服务端的私钥。
- 不允许通过修改 URL 中的用户编号、手机号或其他明文参数绕过签名校验。

## 3. 身份与命名

- `sms` 是站点名称，代码、页面和 API 遵循现有站点路径约定。
- 归属主体只使用当前 SMS 数据库中的 `base_users.id`。跨表引用命名为 `base_user_id`，行归属字段为 `owner_uid`。
- `base_users` 由 Base 层声明。共享数据库的继承站点共用同一张 `base_users`；独立数据库时每个库各有一份。SMS 不创建 `sms_users`，不读取其他站点的用户表。
- 本地密码登录和外部登录都由 Base 认证边界转换为 SMS 本地会话。SMS 业务模块只读取会话得到的 `base_user_id`，不关心认证来源。
- 票据**不携带账号编号**：归属账号由票据里的公钥反查（公钥 → 接入方 → `owner_uid`）。调用方给不出账号，也就填不错、越不了权。
- 后端不根据请求方自称或当前 URL 推断身份，只认已登记接入方签发的票据。
- **绑定有两条路径，身份来源不同**：有本站会话时取会话的 `base_users.id`；无本站会话时由票据里的公钥反查。两条路径都不接受调用方提交的用户编号。流程分别见 §6.1 与 §6.2。
- 反查出的账号必须存在于 SMS 当前数据库且处于启用状态，不能把其他站点的用户 ID 当成本地用户 ID。

## 4. 数据模型

所有表遵循项目统一的**十一个系统字段**，顺序固定、由公共层维护、业务 API 一律不提交（见
[列命名约定](../../conventions/column-naming.md)）：

```
id  key  created_at  updated_at  deleted_at  queued_at  created_duid  updated_duid
owner_tid  owner_bid  owner_uid
```

其中 `key` 是机器写的稳定标识（雪花号或 UUID），跟 `id` 一样只用来指向这一行，**不装人给的值**；
`queued_at` 非 0 表示这一行还在审批队列里等着生效，对正常查询不可见；`owner_*` 是行归属字段，
不是审计字段。

**唯一约束里只有这张表的名字列参与时才带 `deleted_at`。** 名字是人取的，软删一行之后同一个
名字该能再用；哈希、令牌摘要、nonce、对象键这些要么是机器生成、要么是外部给定，永不重复，
带上 `deleted_at` 纯属多余——更要紧的是**不带反而更安全**：一个已消费的 nonce 即便记录被删掉
也不该能重放，一个撤销过的令牌哈希不该能借尸还魂。

名字列默认叫 `name`；个别表里 `name` 读不出它装的是什么，可以换一个更具体的词，但必须登记
在 `shared/system-fields.mts` 的 `NAME_COLUMNS` 里——本文的 `sms_phones` 就登记成了 `number`。

名字列的唯一索引形态固定为 `@@unique([owner_tid, <名字列>, deleted_at])`。

**外键列一律建索引**（`@@index([<列>])`）：没有索引的外键意味着查询全表扫，而这套设计里
`phone_id`、`token_id`、`integration_client_id`、`message_id`、`push_endpoint_id`、
`generator_machine_id`、`owner_uid` 都在高频路径上。

### 4.1 `sms_integration_clients`

**接入方是用户自己注册的一个项目**，不是平台代为登记的。一个人可以注册好几个——博客、商城、内部系统各一个，每个有自己的公钥与推送地址，互不影响。平台不该关心某个用户有几个项目；把一件能自助的事变成工单，只会让人绕过它去共用一套密钥。页面因此在用户面（`/panel/user/sms/integration-clients`）。


登记可以代表用户签发绑定票据的服务端接入方。

| 字段 | 说明 |
| --- | --- |
| `name` | 接入方标识，`(owner_tid, name, deleted_at)` 唯一。**不进协议**——票据靠公钥反查接入方 |
| `title` | 管理端显示名称 |
| `binding_scope` | 允许的绑定能力，本期固定包含 `phone:bind` |
| `status` | `enabled` / `disabled` |
| `last_used_at` | 最近成功验证时间，可为空 |

公钥不在本表：轮换期间需要新旧公钥并存，一行放一个公钥做不到，因此拆到 §4.2。

### 4.2 `sms_integration_client_keys`

一个接入方可以有多个公钥，按 `kid` 定位。

| 字段 | 说明 |
| --- | --- |
| `integration_client_id` | 指向 `sms_integration_clients.id` |
| `kid` | 这把钥匙的名字，给人看的；`(integration_client_id, kid)` 唯一。**不进协议** |
| `public_key` | Ed25519 公钥的 Base64URL。**全库唯一，它就是身份**——票据据此反查接入方与归属账号 |
| `public_key` | Ed25519 公钥，原始字节的 Base64URL 表示 |
| `status` | `active` / `retired` |
| `retired_at` | 停用时间，可为空 |

**协议只认 `kid`，不存在 `key_version` 这个协议字段。** 轮换流程：先登记新 `kid` 并置为 `active`，接入方切换后把旧 `kid` 置为 `retired`；`retired` 的公钥立即拒绝新票据。**私钥永远不写入 SMS 的数据库、日志或 API 响应。**

登记页上有「在这台电脑上生成密钥对」：密钥对用 WebCrypto 在**浏览器里**生成，公钥自动填进表单，私钥以 PKCS#8 的 PEM 显示在那一个页面上供复制、**不上传**。这不违背上面那条——私钥根本没有经过 SMS 的服务端，本站从头到尾只收到公钥；由服务端生成再发下来才是违背的，那样私钥就走过了本站的代码路径，而「只有接入方持有私钥」正是这套签名的全部价值。

私钥只显示一次，页面刷新即失；弄丢了就重新生成一把、换一个 `kid` 登记（`kid` 不重复使用）。浏览器不支持 Ed25519 时按钮会说明情况，回到 openssl 那条路。

### 4.3 `sms_phones`

| 字段 | 说明 |
| --- | --- |
| `key` | **这张表允许接入方通过票据自己指定值**（见下），不传就照常自动生成雪花号。本项目里除 `global_sites` 外唯一偏离"key 只装机器写的雪花号"这条通用约定的表 |
| `owner_uid` | 归属账号，指向当前数据库的 `base_users.id` |
| `number` | 规范化后的 E.164 手机号，**没有唯一索引，允许重复**。票据中的协议字段名为 `phone` |
| `title` | 用户可修改的设备名称 |
| `status` | `enabled` / `disabled` / `revoked` |
| `bound_at`、`revoked_at` | 绑定与撤销时间，后者可为空 |
| `integration_client_id` | 属于哪个接入方项目，`0` 表示不属于任何项目（用户在控制台自己绑的那一部） |
| `client_ref` | 接入方自己的引用串（票据里的可选字段，见 §7.1），默认空字符串，**不参与任何唯一性判断**。推送短信时原样带回给接入方（§4.9.2）——接入方不一定按手机号存自己的客户 |

**`number` 不再是这张表的名字列**（已从 `shared/system-fields.mts` 的 `NAME_COLUMNS` 除名，
`test:naming` 不再要求它带唯一索引）。早先版本里它是名字列，唯一索引下探到"账号 + 项目"
这一层；现在改成**允许同一个号码在同一个接入方名下绑出好几行**，`number` 因此不再满足
"租户内唯一"这条名字列的定义——重复是设计如此，不是遗漏。

**去重换了落点：不再靠 `number`，靠 `key`。** 两条路径分叉：

- **票据路径传了 `key`**：只认这个值，完全不看号码。同一个 `key` 再提交一次——**幂等**，
  直接给回原来那份快捷指令的下载地址，那一行的 `number`/`title` 顺带同步成这次提交的值；
  同一个 `key` 被**别的**接入方占用——拒绝（409），不透露占用者的任何信息。不同的 `key`
  各开一行、各领一个令牌，即使号码完全相同——这正是"同一个号码可以在同一个接入方名下
  绑出好几行"的机制：手机往往不是接入方自己的，是他客户的，同一部手机先后服务过好几个
  客户/订单时，各传各的 `key`。
- **没传 `key`**（票据路径不传，或控制台会话路径——它压根没有 key 的概念）：退回按
  `(owner_tid, owner_uid, integration_client_id, number)` 去重，这段行为与「允许重复」
  这次改动之前完全一样：同一账号 + 项目下同一个号码只保留一行，重复绑定是幂等的。
  **这段查重没有数据库唯一索引兜底了**（`number` 上的索引已经删除），靠应用层先查后插；
  这是刻意的取舍——人在控制台点两下"绑定"不该绑出两部一样的手机，但接入方要的"同号
  可重复绑定"与这条查重并不冲突：两条路径的默认行为本来就不同。

**`key` 的唯一索引是全表级别的，不分租户、不分接入方**（`@@unique([key])`，与本项目所有
表的 `key` 列同一形态——`test:naming` 强制要求它单独一条唯一索引、不与任何列组合，包括
`owner_tid`）。因此"同一个 key 是不是我自己的"这道判断必须在应用层做：查到已存在的行，
比对它的 `owner_uid` 与 `integration_client_id` 是否与当前调用方一致，一致才算命中，不
一致就是别的接入方占用了这个值。**`key` 的唯一索引不带 `deleted_at`**（与其余非名字列的
唯一键一致），软删过的行依然占着这个值，因此查找与竞态兜底都要用能看见已删除行的范围。

`status` 三值语义：`enabled` 正常接收；`disabled` 用户临时停收，关系保留，可自行恢复；
`revoked` 已解绑，关系终止，不可自行恢复。

**解绑不是删除，命中已存在行时复用它**：无论是靠 `key` 命中还是靠号码命中，行为一致——
若命中的行状态是 `revoked`，改回 `enabled`，先把它名下仍为 `bound` 的旧令牌改成 `revoked`
（否则手机一恢复，旧快捷指令跟着复活），再领一个新令牌；若不是 `revoked`，看它现在有没有
活着的令牌，没有（被删或被撤销，例如管理员清空过令牌池）就**就地换发**一个——幂等说的是
"保证有一份能用的快捷指令"，不是"记录在就算完"。

**本表不保存当前令牌的引用。** 令牌与手机的关系只由 `sms_shortcut_tokens.phone_id` 单向
维护——双向外键在无事务环境下必然出现单边不一致，见 §11。查询手机的当前令牌用 `phone_id`
反查。

手机号本身不是认证凭证。解绑或撤销后原令牌立即失效，不能继续写入短信。

**这不构成越权。** 绑定只是登记意图，短信是从**某一个令牌**进来的、归属那个令牌的主人；
要真的收到短信，得有人把那份快捷指令装到那部手机上——那是物理接触，不是这里插一行就能
得到的。绑一个不属于自己的号码，得到的是一部永远收不到短信的手机。

**票据路径（§6.2）的 `key`、`client_ref` 都是票据里的可选字段（§7.1），不由服务端验证
是不是"真的"属于哪个客户**——它们是接入方自己的标签，`client_ref` 原样存、原样推回去，
不解析、不用于任何权限判定；`key` 只用于去重与归属比对，同样不解析其内容。

### 4.4 `sms_shortcut_tokens`

记录 Shortcut 令牌的服务端摘要。原始令牌只存在于 Shortcut 文件与用户手机。

| 字段 | 说明 |
| --- | --- |
| `token_sha256` | 原始令牌的 SHA-256，小写十六进制 64 字符，`(token_sha256)` 唯一 |
| `owner_uid` | 令牌归属账号；公共池阶段为空，领取时写入 |
| `phone_id` | 绑定的手机；`pending` 与 `available` 状态下均为空 |
| `status` | `pending` / `available` / `bound` / `revoked` |
| `idempotency_token` | 生成任务的幂等键，`(idempotency_token)` 唯一 |
| `last_used_at` | 最近一次成功提交短信的时间，可为空 |

`status` 四值语义：`pending` 入库过程中的中间态，不可领取；`available` 在公共池中待领取；`bound` 已绑定手机；`revoked` 已作废。

入库与领取的具体步骤见 §5，无事务前提下的原子性处理见 §11。

原始令牌与 `token_sha256` 敏感级别相同，任一泄露都必须立即撤销该令牌。

### 4.5 `sms_shortcut_artifacts`

Shortcut 文件本身存放在私有对象存储，数据库只保存元数据。

| 字段 | 说明 |
| --- | --- |
| `token_id` | 指向 `sms_shortcut_tokens.id` |
| `object_key` | 私有对象键，`(object_key)` 唯一 |
| `file_sha256` | 文件摘要，小写十六进制 64 字符，用于上传完成校验 |
| `size_bytes` | 文件大小 |
| `content_type` | 由服务端固定写入，生成器不提交 |
| `version` | 同一令牌的文件版本号 |
| `generator_machine_id` | 指向 `sms_generator_machines.id`，由服务端从凭证解析后写入 |
| `status` | `ready` / `revoked` |

唯一约束 `(token_id, version)`。换发新文件时递增 `version` 并把旧版本置为 `revoked`。

`object_key` 形状为 `shortcuts/<机器 name>/<yyyymmdd>/<毫秒时间戳>-<随机后缀>.shortcut`，目录名取 `sms_generator_machines.name`。**随机后缀不可省略**：仅由时间戳构成时，并发的 `prepare-upload` 可能落在同一毫秒并生成相同键，后一次 PUT 会覆盖前一个对象，导致令牌记录指向装着另一个令牌的文件，领取者会拿到他人的令牌并读到他人短信。随机后缀至少 8 字节，取自密码学安全随机源。对象键不得包含手机号或 `token_sha256`。

只有 `status = 'ready'` 且对应令牌 `status = 'available'` 的记录才允许被领取。用户下载时由后端返回短期预签名 GET 地址，Bucket 禁止公共读。

### 4.6 `sms_messages`

| 字段 | 说明 |
| --- | --- |
| `owner_uid` | 短信归属账号，等于所属手机的 `owner_uid` |
| `phone_id` | 来源手机 |
| `content` | 短信正文 |
| `recipients` | 收件人 |
| `sender` | 发送人 |
| `received_at` | 接收时间，**不参与去重哈希**（见下） |
| `payload_hash` | 去重哈希，`(phone_id, payload_hash)` 唯一 |

去重靠唯一约束加 `ignoreInsert` 完成，**不使用"先查后插"**——无事务环境下先查后插存在竞态，且违反 AGENTS.md 对业务唯一字段的约束。

**`payload_hash` 的输入是 `phone_id + message_id + 正文 + 发送人 + 收件人`，不含接收时间。**

本文早先的版本要求把 `received_at` 纳入哈希，那是错的，实测会让重复提交进两行：服务端时间
每次都不同，Shortcut 重发时自然算出两个哈希，去重完全失效——而重试正是这条接口最常见的
并发来源，网络不稳就会重发。

也不能只按正文与发送人算：这条唯一索引不带 `deleted_at`（§4 的规则），软删掉的短信仍然占着
它那个哈希，用户删掉一条之后同样内容的下一条会被当成重复丢弃，而那明明是一条新短信。

所以稳定标识必须**来自手机侧、且重试时不变**，也就是 `message_id`——与推送那边的
`delivery_id` 是同一个模式（§4.9.3「稳定标识，重试沿用同一值」）。手机没给 `message_id` 时
退回按内容算：老版本 Shortcut 仍然能用，只是失去「删掉之后再收到同样内容」这一种区分。

短信由 Shortcut 用 Bearer 令牌写入，那一刻没有登录会话，公共层的归属上下文为空。**因此写入前必须显式绑定归属**，否则 `owner_uid` 会被填成 `NULL`，而 `NULL` 归属的行对普通账号一律不可见——**短信的主人自己也看不到自己的短信**：

```ts
const owned = withDatabaseActors(database, { baseUserId: phone.owner_uid });
await runSql(owned, sql({ database: owned }).ignoreInsert('sms_messages', ['phone_id', 'payload_hash'], { ... }));
```

同一模式适用于 §6.2 的票据绑定路径。相关的通用问题见 [数据行归属需求](../base/row-level-data-ownership.md) §9。

列表默认只返回未删除记录。用户主动删除采用软删除，进入回收站。

#### 保留期与清理

`sms_messages` 是本站唯一会持续膨胀的表，必须有保留期，否则只增不减。

- 保留期由站点配置项 `sms.message_retention_days` 控制，默认 **90 天**，设为 `0` 表示不自动清理。租户级覆盖属于后续需求：`base_tenants` 是 Base 层的表，不应写入 SMS 专有字段。
- **到期记录物理删除，不是软删除。** 软删除只是标记，表体积照涨，起不到控制增长的作用。清理走公共层的 `delete`，按 `received_at` 判定。
- 回收站中的软删除记录同样受保留期约束，不因已软删除而豁免。
- 清理由定时任务执行，**分批进行且可重入**：每批限量（建议 1000 行），按 `received_at` 升序，删完一批即提交。无事务环境下不做长事务，任务中断后下次运行继续。
- 清理任务以系统上下文运行（未绑定主体），因此不受行级判定约束。
- 删除前不做导出。用户若需长期留存，应通过 §4.9 的推送把短信投递到自己的服务端。

### 4.7 `sms_ticket_nonces`

票据的一次性消费记录。

| 字段 | 说明 |
| --- | --- |
| `integration_client_id` | 签发该票据的接入方 |
| `nonce` | 票据中的随机数；`(integration_client_id, nonce)` 唯一 |
| `expires_at` | 取票据的 `exp`，用于过期清理 |

**消费方式是插入而不是更新**：用 `ignoreInsert` 写入，影响行数为 0 即表示该 nonce 已被使用，绑定失败。唯一约束在数据库层保证一次性，无需事务，见 §11。已过期的记录由清理任务按 `expires_at` 删除。

### 4.8 `sms_access_keys`

用户服务端调用管理 API 的 Bearer Access Key。只保存哈希、前缀、归属账号、权限范围、状态和过期/撤销时间，原始 Key 只展示一次。

### 4.9 短信推送

把收到的短信投递到用户自己的服务端。方向与 §0 的"接收"相反，术语固定为**推送**。

#### 4.9.1 `sms_push_endpoints`

| 字段 | 说明 |
| --- | --- |
| `url` | 推送目标，必须 HTTPS（本地开发可显式配置例外） |
| `status` | `enabled` / `disabled` |
| `integration_client_id` | 属于哪个项目；`0` 表示不挂在任何项目下 |
| `phone_id` | 限定只推送该手机的短信；为空表示该账号全部手机 |
| `last_success_at`、`last_error` | 最近一次成功时间与最近错误摘要 |

**这张表不存任何密钥。** 推送用 Ed25519 签名，私钥是平台自己的，存在 `sms_platform_keys` 上、由管理后台维护；接收方用 SMS 公布的公钥验签。因此没有对称密钥要分发、要加密存储、要逐个端点轮换。

> 早先的方案是把密钥放环境变量。改成入库有两个理由：同一个系统里 `global_cloud_credentials.access_key_secret` 已经明文存着（那把凭证泄露能删整个 Bucket，比推送签名私钥危险得多），两种密钥两套存法，维护的人得记住哪个在哪；而轮换要改配置、要重启，没法在后台点两下完成。私钥与 access key 同一待遇——能盗库就能拿到密钥，再加一层可解密的加密只是把钥匙和锁放进同一个抽屉。私钥不出服务端：不进任何接口响应，管理页面上也不显示。

这与绑定票据是**同一套签名方案，只是方向相反**：接入方用自己的私钥签票据、SMS 用登记的公钥验；推送时 SMS 用自己的私钥签、接收方用 SMS 的公钥验。全系统一套编码规则、一套跨语言测试向量。

**同一个号码可以被不同的人、不同的项目、同一接入方名下不同的 `key` 各登记一次**（§4.3）——`number` 上没有唯一索引，去重换成靠应用层的 `key`（传了）或 `(账号, 项目, number)`（没传）。

因为**手机往往不是本站用户自己的，而是他客户的**：甲、乙两家服务商可能服务同一位客户，各自给那部手机装自己的快捷指令。号码在租户内唯一的话，先绑的那家把号占死，后来的一家连登记都做不到——而他们本来就该互不相干。

**登记不等于拿到短信。** 登记之后他确实有了自己的一行手机、自己的令牌、自己那份 `.shortcut` 文件；但那份文件**有没有被装进那部手机是物理动作**——装得上说明手机的主人同意了，那本来就是授权；装不上，他手里只是一部永远收不到短信的记录。短信从哪个令牌进来就归属谁，推送再按 `owner_uid` 分发，因此越权拿不到任何东西。

**推送按项目配对**：手机登记在哪个项目下，就只推给那个项目的推送地址。客户把手机交给项目 X 用，不等于同意项目 Y 也读他的验证码——同一个人名下的另一个项目配一条限定这部手机的地址就能收到的话，那是越权。`0` 是一个有效的分组（用户自己的手机），配对到同样没挂项目的那些地址。

因此同一个人的多个项目要共用一部手机时，**各绑一次、各装一份快捷指令**：这不是绕路，而是那部手机对每个项目本来就是独立授权的。

**票据路径（§6.2）绑定时关联是强制的**：`integration_client_id` 由票据里的公钥反查出来，不由调用方指定——自称可以伪造，而这一列决定了短信将来推给谁。会话路径（用户在控制台自己绑）才是可选的：他在下拉里挑一个自己的项目，或者不挑，那就是自己的手机。

**URL 必须做出站目标校验（SSRF 防护）。** 地址由用户任意填写，若不加限制，推送就成了从服务端发起的任意内网请求。解析后的目标 IP 落在以下范围时一律拒绝保存并拒绝投递：回环（`127.0.0.0/8`、`::1`）、私有网段（`10/8`、`172.16/12`、`192.168/16`、`fc00::/7`）、链路本地（`169.254/16`，含云元数据地址 `169.254.169.254`）、以及 `0.0.0.0/8`。校验必须在**每次投递前**重做，不能只在保存时做一次——DNS 记录可以在保存之后被改指到内网地址。

本地开发的例外由环境变量 `SMS_PUSH_ALLOW_LOCAL_TARGETS=1` 显式打开：接收方跑在本机时地址必然是 `http://127.0.0.1:xxxx`，否则整条链路在开发机上走不通、也就没法验证。**开着它等于关掉 SSRF 防护，生产环境绝不能开**；默认关闭。

解析出多个地址时，**任意一个**落在禁止范围就拒绝——只看第一个的话，轮询 DNS 可以让内网那条在下一次投递时才轮到。

#### 4.9.2 推送请求格式

```http
POST <url>
Content-Type: application/json
X-Sms-Timestamp: 1788432000
X-Sms-Delivery-Id: <本次投递的稳定标识>
X-Sms-Signature: ed25519=<base64url>
```

签名为 Ed25519，输入是 `timestamp + "." + 原始请求体字节`，输出 Base64URL（去 `=`），与绑定票据的编码规则一致。接收方从 SMS 的公钥端点取公钥验签，应校验时间戳在合理窗口内（建议 5 分钟）以防重放，并按 `X-Sms-Delivery-Id` 去重。

**接收方应当缓存公钥，按 `kid` 索引，而不是每收一条推送就拉一次。** 推送头里的 `X-Sms-Key-Id` 就是为此存在：缓存里有这个 `kid` 就直接验签、一个请求都不发；没有才拉一次公钥端点并更新缓存。轮换之后只有第一条推送会触发那一次拉取。这与 OIDC 的 JWKS 是同一个模式。

端点是**便利，不是强制**：接收方也可以把公钥写死在自己的配置里，代价是轮换时要人工改一遍——而有了端点，轮换才谈得上在后台点两下完成。

> 为什么一定要签名：HTTPS 只保证「我连的是对的服务器」，不保证「这条 POST 是谁发的」。任何知道 webhook 地址的人都能往那里发一条「您的验证码是 123456」，没有签名就无从分辨。而不用对称密钥（HMAC）的理由见 §4.9.1：那要逐个端点分发、存储、轮换，一百个推送地址就是一百把钥匙。

公钥端点是 `GET /api/push-key`，**公开、不需要任何凭证**——公开是它的用途：公钥本来就要发给所有接收方，把它藏在认证后面，接收方反而要先有一份凭证才能验签，而验签这一步存在的理由正是「不必先信任传输通道」。

```json
{
  "algorithm": "Ed25519",
  "keys": [
    { "public_key": "<32 字节公钥的 Base64URL>", "status": "active" },
    { "public_key": "<下一把，已公布未启用>", "status": "publishing" },
    { "public_key": "<上一把，仅退役观察期出现>", "status": "retiring" }
  ],
  "max_age_seconds": 300,
  "encoding": { "public_key": "base64url", "signature": "base64url", "signed_input": "信封里 payload 那段字符串的 UTF-8 字节" }
}
```

**`keys` 是数组，接收方问的是「信封里这把公钥在不在名单里」**，不要假设只有一把、也不要假设第一把就是签名用的那把。**名单里不发 `kid`**：判定来源的从头到尾就是公钥本身，推送信封里带的也是公钥（§4.9.2 已不再发 `keyId`）。多给一个标识只会诱使接收方拿它当缓存的键，而它不过是由公钥算出来的一个标签。`kid` 仍然存在于数据库和管理页面上——那是给人念的，不进协议。

**`max_age_seconds` 是这份名单的保质期**，同时写进响应体和 `Cache-Control: max-age`（读得到响应头的客户端不必解析正文，而 `file_get_contents` 这类写法根本看不到响应头）。这个数就是轮换的节拍，见下。

**过期时间挂在名单上，不挂在单把密钥上。** 给每把密钥标一个 `expires_at` 会是一句平台守不住的承诺：退役是管理员在后台点出来的，不是到点自动发生的；而密钥一旦泄露必须能立刻换掉，任何事先公布的到期时刻在那一刻都作废。接收方要是信了那个时刻，早退役会让他把真推送当成伪造丢掉，晚退役会让他继续信一把已经不该信的公钥——两个方向都错。接收方真正需要知道的只有「我这份缓存还能信多久」。

#### 4.9.2.1 平台密钥轮换

**只公布一把公钥的话，换密钥那一刻就断了**：接收方缓存着旧公钥，而新签的请求用的是新私钥，验不过；反过来，已经发出去、正在重试的旧请求也会在接收方换到新公钥之后验不过。两边都不是攻击，表现却和攻击一模一样，运维只能靠停机来回避。

因此轮换期间**多把并存**，在管理后台的「推送密钥」页操作。**关键是先公布、后启用**，不能一步到位：

1. 点「生成新密钥」——新的一把落地即 `publishing`，**立刻出现在 `/api/push-key`，但还不用于签名**；
2. 等至少一个 `max_age_seconds`（当前是 5 分钟）。这段时间是留给接收方的缓存过期的，页面上那句「等 N 分钟」与端点公布的数出自同一个常量；
3. 在那一行点「启用签名」——它转 `active`，原来的 `active` 自动转 `retiring`，两把公钥继续同时公布；
4. 等过一个完整的投递重试窗口——**观察时间必须盖过重试窗口**，否则最后几次重试仍会验不过；
5. 在 `retiring` 那一行上点「退役」，它不再公布。

**第 1、3 步分开是结构性的，不是流程建议**：签名只认 `active`（见 `loadSigningKey`），而新密钥落地是 `publishing`，因此**一把没被公布过的密钥不可能被用来签名**。合成一步的话，那一刻发出去的推送在接收方眼里就是一把没见过的公钥签的，直接被当成伪造丢掉，而本站这边只看到一堆投递失败，看不出原因。

第 3 步里**先启新的、再把旧的转 `retiring`**，两条语句一次提交。反过来的话中间会有一瞬间一把 `active` 都没有，那时候来的短信签不了名、投递直接失败；而这个顺序的中间态是两把 `active`，签名取最新那把，不影响任何一次投递。

当前签名那把**不能直接退役**：退了就没有密钥可签名，等于把推送整个关掉，而页面上没有任何提示会说明这一点。要换就先生成新的。

这与接入方那一侧的轮换是同一套做法（§4.2 的 `active`/`retired`），方向相反而已。

> 推送本身（`sms_push_endpoints`、`sms_push_deliveries` 与投递逻辑）尚未实现，公钥端点先把公钥公布出去。

请求体包含短信正文、来源手机的**完整**号码、绑定时接入方传的 `client_ref`（原样带回，未传为
`null`）与接收时间；不包含原始令牌、`token_sha256` 或其他账号的信息。

**号码不再打码。** 早先方案是只给后四位，理由是接收方不需要完整号码；实际用下来，接入方
若不按手机号存自己的客户（隐私敏感的平台常这样），单靠后四位没办法把短信对回自己的记录，
`client_ref` 解决的是「接入方自己认得出」，但没有它的旧绑定、以及接入方就是想按号码对账
的场景，仍然需要完整号码。这条链路本来就要求 HTTPS、Ed25519 验签，接收方对这条数据的
处置与短信正文一样，负同等的安全责任。

#### 4.9.3 `sms_push_deliveries`

投递状态必须落库，否则进程重启后重试队列丢失。

| 字段 | 说明 |
| --- | --- |
| `message_id` | 来源短信 |
| `push_endpoint_id` | 目标推送地址 |
| `delivery_id` | 稳定标识，`(delivery_id)` 唯一；重试沿用同一值 |
| `status` | `pending` / `sending` / `succeeded` / `failed` |
| `attempts` | 已尝试次数 |
| `next_attempt_at` | 下次尝试时间 |
| `last_error` | 最近错误摘要，不含密钥与短信正文 |

唯一约束 `(message_id, push_endpoint_id)`：同一条短信对同一目标只产生一条投递记录，避免重复排队。

#### 4.9.4 投递与重试

- 只有 HTTP 2xx 视为成功，其余（含超时）计为失败。请求超时建议 10 秒。
- 重试采用指数退避，建议 1 分钟起、上限 6 次，用尽后置为 `failed` 并停止。
- 抢占待投递记录用**单条条件更新**，不用事务：

```sql
UPDATE sms_push_deliveries SET status = 'sending', attempts = attempts + 1
WHERE id = ? AND status = 'pending' AND next_attempt_at <= ?
```

影响行数为 0 表示已被其他工作进程取走，跳过即可。这与 §11 的无事务原则一致。

- 投递任务以系统上下文运行，不受行级判定约束。
- `failed` 记录保留供用户查看，随所属短信一并按 §4.6 的保留期清理。
- 用户可在管理页手动重投单条 `failed` 记录：重置为 `pending` 并沿用原 `delivery_id`，使接收方的去重仍然有效。


### 4.10 `sms_generator_machines`

登记允许运行 Shortcut 生成器的 Mac，一台一行，凭证是它的字段而非独立实体。

| 字段 | 说明 |
| --- | --- |
| `name` | 机器标识，`(owner_tid, name, deleted_at)` 唯一，同时作为对象键中的目录名 |
| `title` | 管理端显示名称 |
| `secret_hash` | 平台预配凭证的哈希，与 `sms_access_keys` 同规则，不保存明文 |
| `secret_prefix` | 凭证前缀，仅用于在管理端辨认，不足以还原凭证 |
| `status` | `enabled` / `disabled` |
| `last_used_at` | 最近一次成功调用生成接口的时间，可为空 |

`name` 使用运维分配的短标识（如 `mac-studio-01`），**不使用主机名或硬件 UUID**：主机名常含人名且可变，硬件 UUID 属于设备指纹，两者都不适合出现在对象键里。

管理操作：**新增机器**（服务端生成高熵凭证，存哈希，明文只在创建响应中展示一次）、**重置凭证**（生成新凭证，旧凭证立即失效）、**停用机器**（`status` 置 `disabled` 后凭证立即被拒，不影响其他机器与已生成的令牌文件）。

创建和重置的响应**直接生成一份完整的 `.env`**，供运维整体复制到对应的 Mac。生成器的全部配置来自这一份文件，不再需要额外的配置接口：

```dotenv
# machine: mac-studio-01
SMS_API_ENDPOINT=https://sms.example.com/api/platform/shortcut-tokens.php
SMS_PROVISIONING_KEY=<明文凭证，只展示一次>
```

- 机器标识以注释形式写入，仅供运维辨认。它**不是有效变量**，生成器不读取也不提交——机器身份由服务端从凭证解析，见上文。
- `.env` 只包含平台预配凭证。**不得写入用户 Access Key 或 Ed25519 私钥**：生成器不调用用户级 API，也不签发绑定票据，放进去只会扩大泄露面。
- 该文件同时含地址与凭证，泄露即是一套完整可用的凭据。要求权限 `600`，不进版本库，并排除出 Time Machine 等备份范围。生成用的 Mac 是专用运维机器，接受明文落盘；补救手段是后台重置凭证，旧 `.env` 立即失效。
- **给的是完整端点，不是基址。** 站点的 API 后缀可配（`siteConfig.apiSuffix`），基址加路径要生成器自己拼，拼错就是一台永远调不通的机器。**里面也没有短信接收地址。** 接收地址会被烤进 Shortcut 文件并分发到用户手机，一旦做成快照就会静默过期，因此由生成器在每次运行时通过 `action=config` 拉取当前值，见 §5。基址过期则是安全的：生成器第一次调用就失败，重新下发 `.env` 即可。

管理页面挂在 `/panel/admin/sms` 下，API 为 `/api/panel/admin/sms/...`，代码位于 `server/routes/sms/api/panel/admin/sms/`，与表前缀 `sms_` 对应。

本表属于平台运维数据，`owner_uid` 为 `NULL`，因此行级判定已经使它对普通账号不可见（可见性文档 §5.2 第 4 条）。管理页面仍按 `admin` 角色限制访问，两层各自独立生效。

### 4.11 各类凭证的区分

| 凭证 | 持有者 | 能做什么 | 服务端如何保存 |
| --- | --- | --- | --- |
| Shortcut 原始令牌 | 用户手机 | 只能提交短信 | 只存 SHA-256 |
| 用户 Access Key | 用户服务端 | 调用用户级管理 API | 只存哈希 |
| 平台预配凭证 | 生成用的 Mac | 只能登记令牌、上传和确认 Shortcut 文件 | 只存哈希 |
| Ed25519 公钥 | SMS（私钥在接入方） | 验证绑定票据 | 明文公钥 |
| 推送签名私钥 | SMS 平台 | 为推送请求签名 | **不入库**，放平台密钥存储 |

五者不能互相替代。数据库里没有任何可解密的密钥：校验类只存哈希，签名类要么只存公钥（接入方），要么根本不入库（推送私钥）。平台预配凭证不属于任何账号，不下发给用户，不能调用短信接收或账号绑定接口。Ed25519 只证明"登记的服务端持有私钥并签署了该票据"，不替代用户登录会话，也不替代手机令牌认证。

## 5. 令牌的生成、入库与领取

Shortcut 文件必须在 macOS 上生成和签名，因此**令牌只能由 Mac 生成器创建，管理端不能生成令牌**。管理端只能撤销、回收和重新分配已存在的令牌。生成器侧的完整流程见 [生成器文档](shortcut-generator.md)。

生成器在每次运行开始时调用 `GET /api/sms/shortcut-tokens?action=config`（凭平台预配凭证认证），获取要写进 Shortcut 的短信接收接口完整地址。该地址由服务端按当前站点配置和 `siteConfig.apiSuffix` 拼出，**不下发给生成器保存**：它会被烤进文件并分发到用户手机，做成快照就会静默过期。服务端改动接收路径后无需重新下发 `.env`，下一批生成自动使用新地址。

### 5.1 入库（四步收敛，无事务）

生成器上传文件并调用 `commit` 后，服务端验签上传票据、校验对象存在与摘要一致，然后：

1. 以 `status = 'pending'` 插入 `sms_shortcut_tokens`，带 `idempotency_token`；重复提交在唯一约束处被挡下。
2. 按 `idempotency_token` 读回 `token_id`。
3. 插入 `sms_shortcut_artifacts`，`status = 'ready'`。
4. 把令牌由 `pending` 改为 `available`。

任一步之后中断都不产生有害中间态：`pending` 令牌不可领取，孤儿对象由生命周期规则清理。重试同一 `idempotency_token` 会收敛到同一结果。同一 `idempotency_token` 携带与首次不同的 `token_sha256` 或 `file_sha256` 时必须拒绝，不得覆盖也不得返回成功。

### 5.2 领取（单条条件更新）

```sql
UPDATE sms_shortcut_tokens SET owner_uid = ?, phone_id = ?, status = 'bound'
WHERE id = ? AND status = 'available'
```

影响行数为 0 表示令牌已被他人领取或状态不符，按失败处理。

> 该语句由业务代码直接写 `owner_uid`。是否应改为公共层的归属变更操作，见 [数据行归属需求](../base/row-level-data-ownership.md) §5.5，待主人确认。

### 5.3 换绑（先撤旧、后绑新）

手机更换令牌时，两步的顺序是强制的：**先把旧令牌置为 `revoked`，再领取新令牌**。中间态是"手机暂时没有有效令牌"，无害；反序则会短暂出现两个有效令牌，可能被同时用于写入。

## 6. 绑定流程

### 6.1 会话路径（用户在 SMS 站点内操作）

1. 用户在已登录的 SMS 页面发起绑定，提交手机号与设备名称。
2. 后端取**当前会话**的 `base_users.id` 作为归属，忽略请求中的任何用户编号。
3. 校验手机号格式与归属冲突，创建或复用 `sms_phones` 记录。
4. 按 §5.2 领取一个 `available` 令牌。
5. 在同一响应中返回短期下载动作，前端不根据 API 路径自行推断跳转或刷新。

### 6.2 票据路径（用户服务端代为绑定）

签名放请求头，请求体是普通 JSON——与推送方向（SMS → 用户服务端，§4.9）同一套方案，只是
反过来。用户服务端验证收到的推送时用的是这一套，签自己的绑定请求用的还是这一套。

1. 用户服务端验证自己的登录状态和手机号归属，拼好请求体 JSON 字符串（不再重新序列化），
   取当前时间戳，按 §7.1 对 `"${timestamp}.${请求体字节}"` 签名。
2. 服务端直接把请求头（`X-Sms-Public-Key`/`X-Sms-Timestamp`/`X-Sms-Nonce`/`X-Sms-Signature`）
   与请求体一起 POST 给统一 API；也可以把这四样东西编码进绑定页面 URL 的片段交给用户在
   浏览器里打开，例如 `/panel/user/sms/bind.html#public_key=...&timestamp=...&nonce=...&signature=...&body=...`。
3. 走片段这条路时，静态页面只读取片段，读取后立即用 `history.replaceState` 清除地址栏
   中的内容，不写入埋点、控制台或 Referer；`body` 部分要原样 `decodeURIComponent`，不得
   重新序列化，否则字节对不上、签名验不过。
4. 后端**按 `X-Sms-Public-Key` 反查出接入方与归属账号**，校验签名（对着请求体原始字节）、
   时间戳新鲜度（容差 60 秒，不再有调用方声明的过期时间）、手机号格式。
5. **消费 nonce**：向 `sms_ticket_nonces` 执行 `ignoreInsert`，影响行数为 0 即判定这个
   nonce 已经用过，直接失败。该步不使用事务，一次性由唯一约束保证。
6. nonce 消费成功后创建或更新手机绑定关系。写入时必须显式绑定归属上下文（`withDatabaseActors(database, { baseUserId: <公钥反查出的账号> })`），此路径没有本站会话，否则 `owner_uid` 会被填成 `NULL`。
7. 按 §5.2 领取令牌，并在同一响应中返回短期下载动作。

第 5 步先于第 6 步是有意的：nonce 一旦消费成功，这次请求即作废；后续步骤失败时用户需要
重新签一次（新的 nonce、新的 timestamp），而不是能用同一个签名重试。这样避免了在无事务
环境下出现"绑定失败但 nonce 已消费"与"绑定成功但 nonce 未消费"两种更糟的组合中的后者。

## 7. Ed25519 签名请求

### 7.1 签名方式

**签名放请求头，请求体是普通 JSON——与推送方向（SMS → 用户服务端，§4.9）完全对称，只是
方向相反。** 早前版本把身份字段（`v`/`aud`/`public_key`/`iat`/`exp`/`nonce`）与业务字段
（`phone`/`key`/`client_ref`/`title`）一起塞进一段签名 JSON、再包进请求体唯一字段 `ticket`
里；现在改成推送方向已经在用的那一套：签名与身份放请求头，请求体就是要处理的业务数据本身，
不包一层。

```http
POST /api/client/phone-bind
X-Sms-Public-Key: <接入方登记的公钥>
X-Sms-Timestamp: <Unix 秒>
X-Sms-Nonce: <高熵随机串，同一接入方内不得重复>
X-Sms-Signature: ed25519=<对 "timestamp.请求体原始字节" 的签名>

{"phone":"+8613800000000","key":"order-8842","client_ref":"order-8842","title":"客户的机器"}
```

| 位置 | 字段 | 说明 |
| --- | --- | --- |
| 头 | `X-Sms-Public-Key` | 对应 `sms_integration_client_keys.public_key`，**全库唯一**。唯一的身份字段：验签公钥、接入方、归属账号全由它反查 |
| 头 | `X-Sms-Timestamp` | Unix 秒，容差 60 秒——不再有调用方声明的独立过期时间，窗口大小由本站固定 |
| 头 | `X-Sms-Nonce` | 接入方生成的高熵随机数，同一接入方不得重复 |
| 头 | `X-Sms-Signature` | `ed25519=` 前缀加 Base64URL 签名。签名输入是 `"${timestamp}.${请求体原始字节}"` |
| 体 | `phone` | 规范化后的 E.164 手机号，对应 `sms_phones.number` |
| 体 | `key` | 可选，接入方自己指定的行标识，驱动去重，详见 §4.3 |
| 体 | `client_ref` | 可选，接入方自己的引用串，随推送带回，不参与去重 |
| 体 | `title` | 可选，给手机起的名字 |

**请求体没有"这个字段该不该签"的判断。** 整个请求体的原始字节都是签名输入的一部分，往里
加任何业务字段都天然被签了进去——不设"签名之外还能带不受保护的元数据"这个口子。这堵住了
一类问题：如果业务字段能在签名之外自由提交，中间的任何一环（网络、代理、接入方自己的转发
服务）理论上都能在不破坏签名的前提下篡改它们；全部纳入签名之后，篡改任何一个字节都会让
验签失败。

**签名的输入是拼接后的字符串，不是重新序列化的 JSON**：验证方（本站）与签发方（接入方）
必须用同一份请求体原始字节，中途任何一次重新 `JSON.stringify`／`json_encode`，键序或空格
差一点，验签就过不去——理由与推送方向完全一致（见 §4.9.2）。

### 7.2 失败规则

以下情况必须返回确定性错误，不得返回内部异常，也不得继续绑定。

**唯一的身份字段是 `X-Sms-Public-Key`**（同 GitHub 的 SSH 公钥）：服务端据它反查接入方与归属账号，调用方不填 `client_id`、`kid`、`base_user_id`。

这不是省字段，是消除一整类错误与一道校验：归属账号由公钥定出来，「填错成别人」与「越权绑到别人名下」都不再是可能的形态，原先那道「这个账号是不是你名下的」的交叉校验也就不必存在了。

冒充只有一种形态——填别人的公钥，而那要求拿别人的私钥来签，私钥不出签发方的门。也因此这里的失败提示可以说得很直白（「这把公钥没有登记」），不存在枚举风险：公钥是 32 字节随机值，能拿到一把的人本来就知道它长什么样。

| 情况 | 提示 |
| --- | --- |
| 缺少 `X-Sms-Public-Key` / `X-Sms-Nonce` 请求头 | 缺少 X-Sms-Public-Key（或 X-Sms-Nonce）请求头 |
| `X-Sms-Public-Key` 格式不对 | X-Sms-Public-Key 必须是 Ed25519 原始字节的 Base64URL，43 个字符 |
| `X-Sms-Timestamp` 缺失、格式不对，或超出 60 秒容差 | X-Sms-Timestamp 请求头缺失或格式不对 / 绑定请求已过期或尚未生效 |
| `X-Sms-Signature` 格式不对（缺少 `ed25519=` 前缀） | X-Sms-Signature 请求头缺失或格式不对 |
| 公钥未登记或已 `retired` | 这把公钥没有登记，或者已经退役 |
| 公钥所属接入方已停用 | 这把公钥所属的接入方已停用 |
| 验签失败 | 绑定请求签名无效 |
| nonce 已消费 | 这个 nonce 已经用过 |
| 请求体不是合法 JSON | 请求体不是合法 JSON |
| 手机号格式错误 | 手机号码格式不正确 |
| `key` 格式不对（不是字母数字下划线连字符，或超过 36 位） | 标识格式不对 |
| `key` 已被**别的**接入方占用 | 这个标识已经被占用，换一个 |
| 命中已有行（按 `key`，或没传 `key` 时按号码） | 幂等返回成功，不产生重复记录 |

去重规则见 §4.3：传了 `key` 只看 key，不传时退回按号码。命中当前接入方自己的一行时按
幂等处理，返回成功、不产生重复记录，并把原来那份快捷指令的下载地址再给一次。**别的账号
绑过同一个号不算冲突，同一接入方用不同 `key` 绑同一个号也不算冲突**——两家服务商服务
同一位客户是常事，同一家服务商名下也可能有好几个客户共用同一个号码。

归属账号由票据里的公钥反查（公钥 → 接入方 → `owner_uid`），调用方给不出账号，因此没有
「绑到别人名下」这一种失败——原先那道「这个账号是不是签名接入方名下的」交叉校验随之删除。

## 8. Shortcut 接收短信流程

接收接口的规范路径：

```http
POST /api/shortcut/message-receive
Authorization: Bearer <原始令牌>
Content-Type: application/json
```

```json
{
  "content": "短信正文",
  "recipients": ["+8613800000000"],
  "sender": "+8613900000000"
}
```

实际下发给生成器的是带域名与 `siteConfig.apiSuffix` 的完整地址，由 §5 的 `action=config` 拼出，Shortcut 内烤的是那个完整值。

- 只允许 `POST`，经 HTTPS 并使用 `Authorization: Bearer <token>` 认证。
- 原始令牌只放在 `Authorization` 头，不得进入 URL 或 JSON 正文；接收时间与设备关系由服务端补充。
- 服务端先对收到的原始令牌计算 SHA-256，再查找令牌、检查手机状态、去重并写入；查询不得把摘要当作可重放凭证，比较使用恒时算法。
- 令牌被撤销、手机被禁用或已解绑时拒绝写入并返回确定性错误。
- **自检**：手机的主人手动运行快捷指令时没有短信触发，`content`、`sender`、`message_id` 三个都为空。这时回 200，一句话告诉他这份快捷指令绑的是哪个号码（完整号码加设备名称，不打码——持有令牌者本就能收到这部手机的全部短信），并**提醒他在「自动化」里建一条「收到信息时运行」**——快捷指令不会自己在收到短信时运行，而自检判断不出建没建，所以每次都提醒；并刷新 `sms_phones.last_check_at`；不写 `sms_messages`、不刷新令牌的 `last_used_at`、不推送。回执不提推送地址与项目：读它的是手机的主人，那是平台用户的概念，放在后台「我的手机」里提示。
- **只有三个都空才算自检。** 正文为空而发送人有值，是真短信没取到正文（例如系统更新后快捷指令读不到了），照旧报错；若也当自检收下，每条真短信都会静默丢失，而后台显示「最近自检：刚刚」。
- 失败响应不得回显令牌、完整手机号、短信正文或数据库内部异常。
- **限流按来源而非按令牌**：无效令牌查不到记录，没有可冻结的对象，只能按来源 IP 或接入点限流。已知令牌的连续失败才可触发该令牌冻结，且不影响用户的其他登录会话。

## 9. 管理与用户操作

### 9.1 管理面与用户面的划分

页面分在两棵子树下，**这个划分同时决定要不要走审批**：`operationScope` 只认
`/api/panel/admin/` 前缀，用户面一律是自助——立即生效、照常留痕、不进队列。

| 面 | 路径 | 页面 | 写入 |
| --- | --- | --- | --- |
| 管理面 | `/panel/admin/sms/` | 生成器机器、Shortcut 令牌、全站短信、推送密钥 | 进审批队列 |
| 用户面 | `/panel/user/sms/` | 我的手机、我的短信、推送地址、接入方与它的公钥 | 立即生效 |

**手机绑定必须落在用户面。** 走审批的话那一行会带着非 0 的 `queued_at`，对正常查询
不可见，而 Shortcut 发来的短信正要靠查这一行认领归属——手机还在队列里排队时，短信会被
拒收。管理面因此只保留撤销、停用这类**修改**（`update` 不写数据行，不产生 `queued_at`），
不提供「替用户绑一部手机」的入口；那本来也做不到，绑定需要用户手上的 Shortcut 与令牌。

三个管理页面都**不提供新增以外的越权口子**，且各有一处刻意的缺省：

- **生成器机器**能新增。凭证由服务端生成，明文只在这一次的响应里给出（§4.10 的 `.env`）。
  **机器标识限 `[a-z0-9-]`**：它直接拼进对象键 `shortcuts/<name>/…`，放开 `/` 或 `.`
  就能把文件写进另一台机器的目录，而领取者会拿到他人的令牌与短信（§4.5）。
- **Shortcut 令牌**不能新增：令牌连同 `.shortcut` 文件由生成器一起产出，凭空登记一条
  哈希，对应的文件并不存在，领的人下载不到东西。能做的是撤销。
（接入方与它的公钥原先也在管理面，已经挪到用户面——见 §4.1：那是用户自己的项目。）

用户面两页同样各缺一样东西：**我的手机**不能新增（绑定要靠手机上的 Shortcut 与令牌走
一遍），**我的短信**只读加删除（写入只走 `/api/shortcut/message-receive`，在页面上插一条
只是伪造收件记录）。

### 9.2 审批穿过响应的那一处

创建生成器机器时，凭证明文与「这条登记已提交审批」要一起回给管理员，而公共层的兜底
（`worker.mts`）会把**任何非 202 的响应**改写成「修改已提交审批」——那是对的，数据确实
没动，回「已保存」就是撒谎；但它会连带把凭证吞掉，而凭证**只有这一次机会**。

因此这条路由自己回 202：状态码已经是 202，兜底就不再改写。被驳回时这份凭证不会生效，
管理员照着它配的机器调不通，文案里说明了这一点。

### 9.3 其余约定


- 管理端可以撤销、回收和重新分配令牌；已绑定的令牌重新分配前必须显式撤销原关系。**管理端不能创建令牌**，令牌只能由 Mac 生成器产生，见 §5。
- 用户可以查看手机名称、**完整**号码、最近接收时间、令牌状态和推送地址——那是他自己的
  手机，没有对自己打码的道理。
- 用户可以解绑自己的手机。解绑确认文案必须显示手机名称和完整号码，不能只说"该设备"或"该身份"。
- 接入方的公钥、`kid`、绑定能力、状态由管理端维护；私钥只由接入方保管。
- 所有令牌、公钥、绑定和撤销操作写入统一审计字段；敏感值不进入日志。

## 10. 安全与运行时要求

- 接入方若使用 PHP，用 `ext-sodium` 的 `sodium_crypto_sign_detached` 生成签名；Composer 不是协议依赖。SMS 服务端使用对应的 Ed25519 验签实现。
- Ed25519 在 Node 与 Cloudflare Workers 上的 Web Crypto 支持存在差异，实施前必须先用同一测试向量在两端各跑通一次，再进入 §12 的其余验收。
- 所有 API 使用参数化数据库助手，不拼接 SQL；固定审计字段由公共层补充。
- Node、Worker 与接入方必须使用同一套编码规则：摘要为小写十六进制，公钥与签名为 Base64URL（去 `=`），时间为 Unix 秒，请求响应为 UTF-8 JSON。
- 绑定票据只能在片段中传递，不得放入查询参数；片段属于敏感短期凭证，页面必须尽快清除。
- 生产环境只接受 HTTPS；CORS、来源校验、限流与请求体大小限制由公共 API 层处理。

## 11. 无事务约束汇总

`server/database/d1.mts` 只实现了 `prepare` 与 `batch`，**没有 `transaction`**（`sqlite.mts`、`mysql.mts`、`postgresql.mts` 三个适配器均有）。Cloudflare 部署下无事务可用，因此本需求全部改用单语句原子性与唯一约束。开发时凡是想写"在一个事务里……"的地方，先回到本节。

| 场景 | 做法 | 中断后的状态 |
| --- | --- | --- |
| 令牌与文件元数据入库（§5.1） | 四步收敛，`idempotency_token` 唯一约束保证幂等 | 停在 `pending`，不可领取，重试收敛 |
| 领取令牌（§5.2） | 单条 `UPDATE ... WHERE status='available'`，看影响行数 | 要么领到要么没领到，无中间态 |
| 换绑令牌（§5.3） | 先撤旧、后绑新，顺序强制 | 手机暂时无有效令牌，无害 |
| 消费 nonce（§6.2） | `ignoreInsert` 到 `sms_ticket_nonces`，看影响行数 | 一次性由唯一约束保证 |
| 短信去重（§4.6） | `ignoreInsert`，`(phone_id, payload_hash)` 唯一 | 不会产生重复记录 |
| 令牌与手机的关系 | 只用 `sms_shortcut_tokens.phone_id` 单向维护 | 不存在双边不一致 |
| 抢占待推送记录（§4.9.4） | 单条 `UPDATE ... WHERE status='pending' AND next_attempt_at <= ?` | 要么抢到要么没抢到，不会重复投递 |
| 短信到期清理（§4.6） | 分批物理删除，可重入 | 删了一部分，下次继续 |

## 12. 验收标准

- 接入方、Node 与 Worker 能用同一测试向量互相验签；签名内容有一个字节差异时必须失败。
- 有效票据只能成功绑定一次；重复提交、修改手机号、修改身份、修改受众或修改过期时间都失败。
- 绑定页面刷新或清除片段后，已消费票据不能再次提交。
- 公钥置为 `retired` 后新票据立即失败；轮换期间新旧 `kid` 的行为符合各自登记状态。
- 会话路径绑定时，请求中携带的任何用户编号都被忽略，归属始终是当前会话账号。
- 票据路径绑定成功后，`sms_phones.owner_uid` 等于票据公钥所属接入方的 `owner_uid`，不为 `NULL`。
- Shortcut 用正确令牌能写入短信，令牌撤销后立即失败；重复消息不产生重复记录。
- 写入的短信 `owner_uid` 等于所属手机的 `owner_uid`，不为 `NULL`。
- 并发领取同一令牌时只有一个成功，其余按失败处理。
- 管理端没有创建令牌的入口。
- 非 `admin` 账号读不到 `sms_generator_machines`（行级判定与路由层各自都能拦下）。
- 绑定、解绑、撤销、令牌失败与验签失败都有明确反馈；日志中没有私钥、原始令牌、`token_sha256`、签名或短信正文。
- 超过保留期的短信被物理删除，未到期的不受影响；清理任务中断后重跑能继续删完。
- 保留期配置为 `0` 时不发生任何自动删除。
- 推送目标解析到回环、私有网段或 `169.254.169.254` 时，保存被拒绝；保存后把 DNS 改指内网，下一次投递同样被拒绝。
- 推送请求的签名可由接收方用同一密钥复算通过；改动请求体任意一个字节后校验失败。
- 推送失败后按退避重试，次数用尽置为 `failed`；手动重投沿用原 `delivery_id`。
- 同一条短信对同一推送目标只产生一条投递记录，并发工作进程不会重复投递。
- 推送日志与 `last_error` 中不出现签名密钥或短信正文。
- 未来 SMS 分库后，站点只依赖本站 `base_users` 和登记的服务 API，不读取其他站点数据库。
